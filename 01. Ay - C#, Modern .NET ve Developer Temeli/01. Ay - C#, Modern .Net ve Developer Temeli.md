## 01. .NET Geliştirme Ortamı: IDE, Terminal ve .NET SDK

### 📌 Temel Tanım
Modern .NET geliştirme ortamı üç temel bileşenin uyumuna dayanır:
1. **IDE (Integrated Development Environment):** Visual Studio, JetBrains Rider veya VS Code; sözdizimi renklendirme, akıllı kod tamamlama (IntelliSense), görsel hata ayıklama (debugging) ve refactoring kolaylığı sunar.
2. **Terminal (CLI):** Otomasyon, CI/CD süreçleri, Docker container'ları ve sunucu yönetiminin ortak ve kesin dilidir.
3. **.NET SDK (Software Development Kit):** Kodun derlenmesi, paketlenmesi ve çalıştırılması için gereken Roslyn derleyicisini, MSBuild motorunu, CLI araçlarını ve BCL (Base Class Library) şablonlarını içeren ana üretim paketidir.

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                           .NET SDK (Üretim Kiti)                        │
│  ┌───────────────────────┐  ┌─────────────────┐  ┌───────────────────┐  │
│  │ Roslyn (C# Derleyici) │  │  MSBuild Motoru │  │  .NET CLI Araçları│  │
│  └───────────────────────┘  └─────────────────┘  └───────────────────┘  │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │                     .NET Runtime (Çalıştırma Zamanı)              │  │
│  │  ┌─────────────────────────────┐   ┌───────────────────────────┐  │  │
│  │  │ CLR (CoreCLR Execution)     │   │ BCL (Temel Sınıf Kütüph.) │  │  │
│  │  └─────────────────────────────┘   └───────────────────────────┘  │  │
│  └───────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────┘
```

### 🎯 En Önemli Kullanım Amacı & Mimari Önemi
- **SDK vs Runtime Ayrımı:** Production ortamına (sunucuya veya Docker container'ına) asla SDK kurulmaz; yalnızca hafif olan **.NET Runtime** kurulur. SDK geliştirici makinesinde ve CI build sunucusunda yaşar.
- **global.json ile Sürüm Sabitleme:** Büyük ekiplerde ve CI/CD pipeline'larında derleyicinin ve SDK sürümünün herkes için birebir aynı olmasını garanti eder.

```json
{
  "sdk": {
    "version": "9.0.100",
    "rollForward": "latestFeature"
  }
}
```

### ⚡ Kritik CLI Komutları
```powershell
# Yüklü SDK'ları ve Runtime sürümlerini listeleme
dotnet --list-sdks
dotnet --list-runtimes

# Detaylı ortam, mimari (x64/ARM64) ve işletim sistemi raporu

# Yeni bir konsol projesi oluşturma ve çalıştırma
```

- `global.json` dosyasını repoya eklemeyip takım arkadaşlarının farklı SDK sürümleriyle derleme uyumsuzlukları yaşamasına yol açmak.

## 02. .NET Proje Mimarisi: Solution, Project, Assembly ve .csproj Anatomisi

### 📌 Temel Tanım
- **Solution (`.sln`):** Birden fazla projeyi mantıksal bir kümede toplayan, IDE ve CLI araçlarının projeler arası referansları tanımasını sağlayan organizasyonel dosyadır.
- **Project (`.csproj`):** Bağımsız olarak derlenebilen, hedef framework'ü, paket bağımlılıklarını ve derleme direktiflerini tanımlayan XML tabanlı bildirim sözleşmesidir.
- **Assembly (`.dll` / `.exe`):** C# kodunun Roslyn tarafından derlenmesi sonucunda üretilen, içinde IL (Ara Dil) ve Metadata barındıran fiziksel dağıtım birimidir.

```text
E-Ticaret Çözüm Mimarisi (Bağımlılık Yönü Daima İçe Doğru):
Shop.sln
├── src/
│   ├── Shop.Domain/Shop.Domain.csproj           <── (Sıfır Dış Bağımlılık - Çekirdek)
│   ├── Shop.Application/Shop.Application.csproj ──> Referans: Shop.Domain
│   ├── Shop.Infrastructure/Shop.Infrastructure.csproj ──> Referans: Shop.Application & Domain
│   └── Shop.Api/Shop.Api.csproj                 ──> Referans: Shop.Application & Infrastructure
└── tests/
    └── Shop.UnitTests/Shop.UnitTests.csproj     ──> Referans: Shop.Application
```

### 🎯 .csproj Anatomisi ve Modern Özellikler
```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>

  <!-- Proje Referansı (İç Bağımlılık) -->
  <ItemGroup>
    <ProjectReference Include="..\Shop.Domain\Shop.Domain.csproj" />
  </ItemGroup>

  <!-- NuGet Paket Referansı (Dış Bağımlılık) -->
  <ItemGroup>
    <PackageReference Include="FluentValidation" Version="11.9.0" />
  </ItemGroup>
</Project>
```

### ⚡ Kritik Kurallar & Bağımlılık İlkeleri
- **Bağımlılık Kuralı (Dependency Inversion):** Domain katmanı asla Infrastructure veya Presentation (API/Console) katmanına referans veremez. Çekirdek iş kuralları veritabanından, UI'dan ve üçüncü parti araçlardan tamamen izole olmalıdır.
- **Döngüsel Bağımlılık (Circular Dependency):** Proje A Proje B'ye bağımlıyken, Proje B doğrudan ya da dolaylı olarak Proje A'ya bağımlı olamaz; MSBuild derleme hatası verir.
- **Nullable & ImplicitUsings:** `Nullable: enable` referans tiplerin null güvenliğini denetler; `ImplicitUsings: enable` ise sık kullanılan temel namespace'leri (`System`, `System.Collections.Generic`, `System.Threading.Tasks`) dosya başına `using` yazmadan görünmez olarak dahil eder.

### ⚠️ Sık Yapılan Hatalar
- Her klasör veya katman için gereksiz yeni proje açmak. Ayrı derleme, test, dağıtım veya paketleme sınırı yoksa gereksiz proje açmak build süresini dramatik şekilde uzatır.
- Farklı projelerde aynı NuGet paketinin çakışan sürümlerini kullanmak (Modern çözüm: `Directory.Packages.props` ile Central Package Management).

## 03. .NET CLI ve Uygulama Yaşam Döngüsü

### 📌 Yaşam Döngüsü Aşamaları
Bir .NET projesinin geliştirilmesinden yayına alınmasına kadar geçen deterministik döngü şu 5 adımdan oluşur:

```text
┌──────────┐     ┌───────────┐     ┌─────────┐     ┌──────────┐     ┌───────────┐
│ dotnet   │ ──> │ dotnet    │ ──> │ dotnet  │ ──> │ dotnet   │ ──> │ dotnet    │
│ new      │     │ restore   │     │ build   │     │ test     │     │ publish   │
└──────────┘     └───────────┘     └─────────┘     └──────────┘     └───────────┘
 Proje Şablonu    NuGet Paketleri    Sözdizimi ve    Davranışsal      Dağıtıma Hazır
 Oluşturulur      İndirilir          IL Üretimi      Doğrulama        Paket Çıktısı
```

### 🎯 Komutlar ve Optimizasyon Bayrakları
```powershell
# 1. Solution ve Projeleri Oluşturma
dotnet new sln -n EnterpriseApp
dotnet new classlib -n EnterpriseApp.Domain -o src/EnterpriseApp.Domain
dotnet new webapi -n EnterpriseApp.Api -o src/EnterpriseApp.Api
dotnet sln add src/EnterpriseApp.Domain src/EnterpriseApp.Api

# 2. Proje Referansı Bağlama
dotnet add src/EnterpriseApp.Api reference src/EnterpriseApp.Domain

# 3. Restore (Paket İndirme)
dotnet restore EnterpriseApp.sln

# 4. Derleme (Build) - Release ve Restore Yapmadan
dotnet build EnterpriseApp.sln -c Release --no-restore

# 5. Test Çalıştırma - Derlemeyi Tekrar Yapmadan
dotnet test tests/EnterpriseApp.Tests -c Release --no-build

# 6. Yayınlama (Publish) - Hedef klasöre optimize çıktı alma
dotnet publish src/EnterpriseApp.Api -c Release --no-build -o ./app-dist
```

### ⚡ Kritik Kurallar
- `build` sözdizimsel doğruluğu ve tip kurallarını denetler; sistemin iş kuralları bakımından doğru çalıştığını kanıtlamaz. Doğrulamayı yalnızca `test` yapar.
- `dotnet run` geliştirme ortamı (`Development`) aracıdır; arka planda build tetikler. Production ortamında doğrudan `dotnet MyApp.dll` çalıştırılır.
- CI/CD boru hatlarında `--no-restore` ve `--no-build` bayraklarını kullanmak, adımların birbirini mükerrer derlemesini engelleyerek build süresini %40-%60 oranında kısaltır.

> [!NOTE]
> **Build Artefaktları:** `obj/` klasörü derleyicinin ara dosyalarını ve NuGet çözümleme haritalarını tutar; `bin/` klasörü ise nihai assembly (`.dll`) ve sembol (`.pdb`) dosyalarını barındırır.

## 04. Git Temelleri, 3 Katmanlı Model ve Atomik Commit Döngüsü

### 📌 3 Katmanlı Durum Modeli
Git bir dosya sistemini değil, dosyaların anlık görüntülerini (snapshot) 3 ana bölgede yönetir:

```text
┌────────────────────────┐      ┌────────────────────────┐      ┌────────────────────────┐
│   Working Directory    │ ──>  │     Staging Area       │ ──>  │    Local Repository    │
│  (Çalışma Alanı / Disk)│ git  │ (Index / Hazırlık Alanı│ git  │  (.git Veritabanı /    │
│                        │ add  │                        │commit│   Commit Geçmişi)      │
└────────────────────────┘      └────────────────────────┘      └────────────────────────┘
            ▲                                                                │
            └─────────────────────── git checkout / restore ─────────────────┘
```

### 🎯 Atomik Commit ve Conventional Commits Standardı
İyi bir commit; tek bir amaca hizmet eden, parçalanamaz (atomik), derlenebilir ve bağımsız olarak geri alınabilir (revert) olmalıdır.

```text
Format: <tip>(<kapsam>): <kısa açıklama>

Örnekler:
feat(order): add idempotency key check to order creation
fix(billing): prevent negative invoice total calculation
refactor(auth): simplify JWT claim extraction logic
test(customer): add unit tests for VIP discount threshold
```

### ⚡ Kritik Git Akışı
```powershell
# Durumu kontrol et: Hangi dosyalar değişti?
git status

# Farkları incele: Satır bazında ne eklendi, ne silindi?
git diff

# Etkileşimli (Patch) Ekleme: Sadece istenen satırları sahneye al
git add -p

# Sahneye alınan değişikliklerin teyidi
git diff --staged

# Anlamlı ve konvansiyonel commit mesajı ile mühürle
git commit -m "fix(payment): prevent duplicate transaction on timeout"

# Uzak repoya güvenle aktar
git push origin feature/payment-retry
```

### ⚠️ Sık Yapılan Hatalar
- `git add .` komutunu düşüncesizce çalıştırarak geçici dosyaları, `.env` dosyalarını veya `bin/`/`obj/` klasörlerini repoya sokmak.
- "Fix bug", "Update", "Changes" gibi içeriği açıklamayan, 6 ay sonra kimsenin ne olduğunu anlayamayacağı commit mesajları yazmak.

## 06. Değişkenler, Veri Tipleri, Operatörler ve Sayısal Hassasiyet

### 📌 Tip Güvenliği ve Bellek Hassasiyeti
C# statik ve güçlü tipli (strongly-typed) bir dildir. Bir değişkenin tipi yalnızca bellekte kaç byte kaplayacağını değil; üzerinde hangi matematiksel işlemlerin geçerli olduğunu ve iş kuralı sınırlarını belirler.

```text
Finansal ve Sayısal Hassasiyet Farkı:
┌─────────────────┬──────────┬────────────────────────────────────────────────────────┐
│ Tip             │ Boyut    │ Kullanım Amacı & Hassasiyet Davranışı                  │
├─────────────────┼──────────┼────────────────────────────────────────────────────────┤
│ int / long      │ 4/8 byte │ Tam sayılar, kimlikler, sayaçlar. (İnt bölmesi tehlikeli)│
│ float / double  │ 4/8 byte │ IEEE 754 Kayan Noktalı (İkili Taban). Bilimsel/Grafik.  │
│ decimal         │ 16 byte  │ 128-bit 10'luk Taban Sabit Noktalı. Para/Finans için ŞART│
└─────────────────┴──────────┴────────────────────────────────────────────────────────┘
```

### 🎯 Kritik Kod Örnekleri ve Operatör Semantiği
```csharp
// 1. Finansal Hesaplamalarda Kesinlikle decimal Kullanımı
decimal unitPrice = 149.99m;
int quantity = 3;
decimal total = unitPrice * quantity;

// 2. Tamsayı Bölmesi Tuzağı (Integer Division Trap)
int completedTasks = 3;
int totalTasks = 4;
// YANLIŞ: 3 / 4 tamsayı bölmesi 0 sonucunu verir!
// decimal rateWrong = completedTasks / totalTasks; // 0m
// DOĞRU: En az bir operand açıkça cast edilmelidir:
decimal completionRate = (decimal)completedTasks / totalTasks; // 0.75m

// 3. Kısa Devre (Short-Circuit) Operatörleri: && ve ||
// Eğer müşteri null ise sağ taraf ASLA çalıştırılmaz, NullReferenceException engellenir!
Customer? customer = GetCustomer();
if (customer is not null && customer.IsActive && customer.Balance > 0m)
{
    // Güvenli işlem alanı
}

// 4. Taşırma (Overflow) Kontrolü
checked
{
    int max = int.MaxValue;
    // max++; // checked bloğu içinde OverflowException fırlatır; unchecked sessizce eksiye döner!
}
```

### ⚡ Kritik Kurallar
- Para, bakiye, fatura, faiz gibi finansal alanlarda asla `float` veya `double` kullanılmaz; `decimal` kullanılmalıdır. `double` ikili tabanda `0.1 + 0.2 != 0.3` hatasına yol açar.
- Yuvarlama kuralları iş kuralı olarak netleştirilmelidir: `Math.Round(val, 2, MidpointRounding.AwayFromZero)`.

## 07. Koşullu İfadeler, Switch Expressions ve Guard Clause Yaklaşımı

### 📌 Okunabilirlik ve Dallanma Yönetimi
Geleneksel iç içe geçmiş `if-else` blokları kodda "Ok Anti-Pattern'i" (Arrow Anti-Pattern) oluşturur, bilişsel yükü (cognitive load) katlar. Modern C# kodunda geçersiz durumlar en başta **Guard Clause** ile elenir; ana akış sola yaslanır, değer üretiminde ise **Switch Expression** ve **Pattern Matching** kullanılır.

```text
Geleneksel İç İçe If (Arrow Anti-Pattern)          Modern Guard Clause & Pattern Matching
┌────────────────────────────────────────┐        ┌──────────────────────────────────────┐
│ if (order != null) {                   │        │ ArgumentNullException.ThrowIfNull(..);│
│    if (order.IsActive) {               │ ──>    │ if (!order.IsActive) return;         │
│       if (order.Total > 0) {           │        │ if (order.Total <= 0) return;        │
│          // Asıl İş Mantığı            │        │ // Asıl İş Mantığı Sola Yaslı        │
│       }                                │        │                                      │
│    }                                   │        └──────────────────────────────────────┘
│ }                                      │
└────────────────────────────────────────┘
```

### 🎯 Modern Pattern Matching ve Switch Expression Örneği
```csharp
public enum CustomerTier { Standard, Silver, Gold, Platinum }

public static decimal CalculateOrderDiscount(Customer customer, decimal orderTotal)
{
    // 1. Guard Clauses: Hatalı veya sınır durumları erkenden püskürt
    ArgumentNullException.ThrowIfNull(customer);
    if (orderTotal < 0m)
        throw new ArgumentOutOfRangeException(nameof(orderTotal), "Sipariş tutarı negatif olamaz.");

    // 2. Switch Expression + Property & Relational Pattern Matching
    return (customer.Tier, orderTotal) switch
    {
        (CustomerTier.Platinum, >= 5_000m) => orderTotal * 0.25m,
        (CustomerTier.Platinum, _)         => orderTotal * 0.20m,
        (CustomerTier.Gold, >= 2_500m)     => orderTotal * 0.15m,
        (CustomerTier.Gold, _)             => orderTotal * 0.10m,
        (CustomerTier.Silver, _)           => orderTotal * 0.05m,
        _                                  => 0m // Standard veya eşleşmeyen durumlar
    };
}
```

### ⚡ Kritik Kurallar
- Switch ifadelerinde default discard (`_`) dalını bilinçsizce boş bırakmayın. Bilinmeyen veya tanımsız enum değerleri geldiğinde hatayı sessizce yutmak yerine `ArgumentOutOfRangeException` fırlatın.
- Guard Clause yöntemiyle kontrol edilen koşullarda metot erken sonlandırıldığı için kodun geri kalanı girintisiz, akıcı ve rahat okunur.

```csharp
// 2. Koleksiyon İterasyonu ve Güvenli Eleman Silme
var expiredTokens = new List<string> { "tok_1", "tok_2", "tok_3" };
```

## 09. Metotlar, Parametre Semantiği (ref, out, in), CancellationToken ve Pure Functions

### 📌 Metot Sözleşmesi ve CQS İlkesi
Bir metodun imzası (adı, aldığı parametreler ve dönüş tipi) onun dış dünyayla yaptığı resmi sözleşmedir.
- **Command-Query Separation (CQS):** Bir metot ya sistemin durumunu değiştirmeli (Command) ya da dışarıya veri döndürmelidir (Query). İkisini aynı anda yapan metotlar yan etkileri gizler ve öngörülemez hatalar doğurur.
- **Pure Function (Saf Fonksiyon):** Yalnızca girdilerine bağımlı olan, dış dünyada (veritabanı, static alan, dosya) hiçbir yan etki yaratmayan ve aynı girdiye daima aynı çıktıyı veren fonksiyonlardır; birim test yazımı en kolay mimari birimlerdir.

```text
Parametre İletim Semantiği:
┌───────────┬────────────────────────────────────────────────────────────────────────┐
│ Anahtar   │ Çalışma Mantığı ve Bellek Davranışı                                    │
├───────────┼────────────────────────────────────────────────────────────────────────┤
│ (varsayılan) Değer kopyalanır (Value type için veri, Reference type için adres kopyası)│
│ ref       │ Değişkenin doğrudan bellek adresi iletilir; içerideki değişim dışa yansır│
│ out       │ Çağrılan metot değişkene ilk değer atamak ZORUNDADIR (örn. TryParse)    │
│ in        │ Bellek adresini salt okunur (readonly) geçirir; struct kopyalamayı önler│
│ params    │ Değişken sayıda parametreyi dizi/span olarak kabul eder               │
└───────────┴────────────────────────────────────────────────────────────────────────┘
```

### 🎯 Modern Metot Tasarımı Örneği
```csharp
public sealed record ProcessInvoiceResult(Guid InvoiceId, decimal PaidAmount, DateTime ProcessedAt);

public static class InvoiceProcessor
{
    // CancellationToken iletimi ve parametre doğrulaması
    public static async Task<ProcessInvoiceResult> ProcessPaymentAsync(
        Guid invoiceId,
        decimal amount,
        CancellationToken cancellationToken = default)
    {
```

- Arka uç (backend) kodunda asla `async void` kullanılmaz; daima `Task` veya `Task<T>` dönülmelidir (`async void` istisnaları yakalanamaz ve süreci doğrudan çökertebilir).
- Asenkron I/O çağrılarında (veritabanı, HTTP, dosya) `CancellationToken` metod zincirinin en derinine kadar eksiksiz iletilmelidir.

## 10. Null Güvenliği, Nullable Reference Types (NRT) ve Defansif Kodlama

### 📌 Nullable Reference Types Devrimi
C# 8.0 ile gelen NRT (`#nullable enable`), referans tiplerin çalışma zamanında null olmasını engellemez; ancak derleyici seviyesinde statik kod analizi yaparak `NullReferenceException` oluşabilecek her noktada derleme uyarısı/hatası verir.

```text
┌────────────────────┬───────────────────────────────────────────────────────────────┐
│ Sözdizimi          │ Anlamı ve Derleyici Davranışı                                 │
├────────────────────┼───────────────────────────────────────────────────────────────┤
│ string             │ Non-nullable: Kesinlikle null değer alamaz.                   │
│ string?            │ Nullable: Değer null OLABİLİR, erişmeden önce kontrol şarttır.│
│ obj?.Property      │ Null-Conditional: obj null ise işlem yapma, null dön.         │
│ value ?? fallback  │ Null-Coalescing: value null ise fallback değerini kullan.      │
│ target ??= factory │ Null-Coalescing Assignment: target null ise hesapla ve ata.   │
│ variable!          │ Null-Forgiving (Bang): "Derleyici sus, ben null olmadığını    │
│                    │ biliyorum" demek; tehlikelidir, runtime garantisi vermez!      │
└────────────────────┴───────────────────────────────────────────────────────────────┘
```

### 🎯 Defansif Programlama ve NRT Kullanımı
```csharp

public sealed class MemberService
{
    public string FormatMemberDisplayName(Member? member)
    {
        // 1. Guard ile Null Kontrolü

    public void RegisterMember(string email, string fullName)
    {

        // email ve fullName kesinlikle geçerlidir
    }
}
```

### ⚠️ Sık Yapılan Hatalar
- Derleyicinin verdiği null uyarılarını düzeltmek yerine her satıra körlemesine `!` (bang) operatörü koyarak uyarıları susturmak ve çalışma zamanında patlamaya davetiye çıkarmak.
- `null`, `""` (boş string) ve `"   "` (boşluklardan oluşan string) durumlarını aynı zannetmek.

## 11. Class ve Object Mimarisi, Bellek Gösterimi ve Yaşam Döngüsü

### 📌 Class vs Object
- **Class (Sınıf):** Bir veri modelinin ve davranış kümesinin şablonu, tip tanımıdır.
- **Object (Nesne / Örnek):** Bu şablondan `new` anahtar sözcüğüyle Heap belleğinde somutlaştırılan, kimliği (identity) ve yaşayan durumu (state) olan varlıktır.

```text
Bellek Dağılımı ve Referans Eşleşmesi:
STACK (Yerel Değişkenler)                  HEAP (Yönetilen Bellek Alanı)
┌─────────────────────────┐               ┌──────────────────────────────────────────┐
│ firstRef: 0x00A1F0      │ ────────────> │ Obje #1 (Customer)                       │
│                         │               │ Header (SyncBlock + TypeHandle)          │
│ secondRef: 0x00A1F0     │ ────────────> │ Name: "Ada"  ──> Name: "Ece" (Değişti!)  │
└─────────────────────────┘               └──────────────────────────────────────────┘
(İki referans değişkeni de Heap'teki AYNI adrese işaret eder!)
```

### 🎯 Referans Semantiği Kanıtı
```csharp
public sealed class Customer
{
    public string Name { get; private set; }
    public Customer(string name) => Name = name;
    public void Rename(string newName) => Name = newName;
}

// Kullanım:
var firstRef = new Customer("Ada");
var secondRef = firstRef; // Yeni nesne üretilmez, heap adresi kopyalanır!

secondRef.Rename("Ece");

Console.WriteLine(firstRef.Name); // Ekrana "Ece" yazar!
Console.WriteLine(object.ReferenceEquals(firstRef, secondRef)); // True
```

### ⚡ Kritik Kurallar
- Referans tipler atandığında nesnenin kopyası değil, bellekteki işaretçisi (pointer) kopyalanır. Bir değişken üzerinden yapılan durum değişikliği diğer tüm referansları etkiler.
- Nesneler Stack'teki referansları tükendiğinde Garbage Collector (GC) tarafından sahipsiz (unreachable) kabul edilir ve uygun bir GC döngüsünde bellekten temizlenir.

## 12. Field, Property (init, required), Backing Field ve Constructor Mimarisi

### 📌 Sınıf Üyelerinin Görev Paylaşımı
- **Field:** Sınıfın iç durumunu tutan, dış dünyaya doğrudan açılmaması gereken gizli değişkenlerdir (`private readonly`).
- **Property:** Kontrollü erişim (getter/setter) sağlayan, kapsülleme uygulayan akıllı erişim kapılarıdır.
- **Constructor:** Nesnenin bellekte geçerli (valid) bir başlangıç durumuyla doğmasını garanti eden kurucu metottur.

```text
Property ve Constructor Anatomisi:
┌────────────────────────────────────────────────────────────────────────┐
│ BankAccount Sınıfı                                                     │
│ ┌──────────────────────┐  ┌─────────────────────┐  ┌─────────────────┐ │
│ │ Private Field        │  │ Property (init)     │  │ Constructor     │ │
│ │ _balance: decimal    │  │ Iban: string        │  │ Başlangıç State │ │
│ │ (Doğrudan Erişilemez)│  │ (Doğumda Atanır)    │  │ Doğrulamasını   │ │
│ └──────────────────────┘  └─────────────────────┘  │ Yapar           │ │
│                                                    └─────────────────┘ │
└────────────────────────────────────────────────────────────────────────┘
```

### 🎯 Modern C# 12/13 Sınıf Mimarisi
```csharp
public sealed class BankAccount
{
    // Backing Field
    private decimal _balance;

    // init: Sadece nesne inşa edilirken atanabilir, sonrasında salt okunurdur.
    public string Iban { get; init; }

    // required: Nesne new'lenirken çağrıcı tarafından atanması ZORUNLUDUR.
    public required string OwnerName { get; init; }

    // Dışarıya sadece okuma açık; durum ancak metotlar üzerinden değişebilir
    public decimal Balance => _balance;

    // Primary Constructor ve Doğrulama
    public BankAccount(string iban, decimal initialBalance)
    {

            throw new ArgumentException("Açılış bakiyesi negatif olamaz.", nameof(initialBalance));

        Iban = iban;
        _balance = initialBalance;
    }

    public void Deposit(decimal amount)
    {

            throw new ArgumentOutOfRangeException(nameof(amount), "Yatırılan tutar sıfırdan büyük olmalıdır.");
        _balance += amount;
    }
}
```

## 13. Encapsulation (Kapsülleme), Invariant Korunması ve Domain Bütünlüğü

### 📌 Invariant Nedir?
**Invariant (Değişmez Kural):** Bir iş nesnesinin (Domain Entity) yaşam döngüsü boyunca her zaman doğru ve geçerli kalması zorunlu olan kuralıdır. (Örn: "Bir sipariş onaylandıktan sonra içeriği değiştirilemez", "Fatura toplamı sıfırın altına düşemez").

```text
Anemic Domain Model (Kötü)               Rich Encapsulated Domain Model (Doğru)
┌────────────────────────────────┐        ┌────────────────────────────────────────┐
│ class Order {                  │        │ class Order {                          │
│    public List<Item> Items;    │ ──>    │    private readonly List<Item> _items; │
│    public string Status;       │        │    public IReadOnlyCollection<Item>    │
│ }                              │        │       Items => _items.AsReadOnly();    │
│ (Dışarıdan herkes bozabilir!)  │        │    public void AddItem(...) { ... }    │
└────────────────────────────────┘        └────────────────────────────────────────┘
```

### 🎯 Zırhlı Kapsülleme Uygulaması
```csharp
public enum OrderStatus { Draft, Confirmed, Cancelled }

public sealed class Order
{
    private readonly List<OrderItem> _items = [];

    public Guid Id { get; } = Guid.NewGuid();
    public OrderStatus Status { get; private set; } = OrderStatus.Draft;

    // Koleksiyon kapsüllemesi: Dışarıya asla List<T> verilmez; IReadOnlyCollection verilir!
    public IReadOnlyCollection<OrderItem> Items => _items.AsReadOnly();

    public decimal TotalAmount => _items.Sum(x => x.Price * x.Quantity);

    public void AddItem(Guid productId, decimal price, int quantity)
    {
        // Invariant Savunması
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Onaylanmış veya iptal edilmiş siparişe yeni ürün eklenemez.");

        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity), "Miktar en az 1 olmalıdır.");

        _items.Add(new OrderItem(productId, price, quantity));
    }

    public void Confirm()
    {
        if (_items.Count == 0)
            throw new InvalidOperationException("Boş sipariş onaylanamaz.");

        Status = OrderStatus.Confirmed;
    }
}
```

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- UI veya API seviyesinde yapılan validasyonlar (FluentValidation / DataAnnotations) kapı güvenliğidir. Domain sınıfının içindeki invariant doğrulamaları ise sistemin son kalesidir; hangi kod çağırırsa çağırsın nesnenin geçersiz state'e düşmesini engeller.

## 14. Değer ve Referans Tipleri (Class vs Struct), Stack vs Heap Semantiği

### 📌 Kimlik (Identity) vs Değer (Value) Semantiği
- **Değer Tipi (Value Type):** `struct`, `enum`, `int`, `decimal`, `bool`, `DateTime`. Verinin kendisini taşır. Atandığında veya metoda parametre geçildiğinde bellekteki değeri kopyalanır.
- **Referans Tipi (Reference Type):** `class`, `interface`, `record class`, `string`, `delegate`. Nesnenin Heap adresini tutar. Atandığında sadece referans (işaretçi) kopyalanır.

| Özellik | Değer Tipleri (Struct) | Referans Tipleri (Class) |
| :--- | :--- | :--- |
| **Temel Anlam** | Değer Semantiği ("Ne tutuyor?") | Kimlik Semantiği ("Hangi nesne?") |
| **Bellek Yeri** | Çoğunlukla Stack (veya kapsayan nesnenin içi) | Yönetilen Heap (Stack'te işaretçi yaşar) |
| **Kopyalama Davranışı** | Bit seviyesinde tam değer kopyası | Yalnızca bellek referansının kopyası |
| **GC Yükü** | GC baskısı yaratmaz (kapsamı bitince ölür) | GC tarafından takip edilir ve temizlenir |
| **Kalıtım** | Başka struct'tan türeyemez (Interface uygular)| Başka bir sınıftan türeyebilir |

### 🎯 Boxing ve Unboxing Maliyeti
```csharp
// Boxing: Değer tipinin heap'e taşınıp object kılıfına sarılması (Allocation maliyeti!)
int number = 42;
object boxed = number; // Boxing gerçekleşir (Heap'te bellek ayrılır)

// Unboxing: Heap'teki değerin tekrar Stack'e kopyalanması
int unboxed = (int)boxed; // Unboxing gerçekleşir

// Modern Çözüm: Değişmez (Immutable) Değer Nesnesi Tasarımı
public readonly record struct Money(decimal Amount, string Currency)
{
    public static Money Zero(string currency) => new(0m, currency);
}
```

### ⚡ Kritik Kurallar
- Struct'lar küçük (genellikle 16 byte altı), kısa ömürlü, değişmez (immutable) ve mantıksal olarak tek bir değeri temsil eden senaryolarda (`Money`, `Coordinate`, `Point`) kullanılmalıdır.
- Büyük struct'lar metotlara değer olarak geçirilirken sürekli tüm byte'ları kopyalandığı için performansı düşürebilir. Böyle durumlarda `in` parametre niteleyicisi (`in Money amount`) kullanılmalıdır.

## 15. Record Tipleri, Immutability, Positional Records ve Değer Eşitliği

### 📌 Record Tiplerinin 4 Süper Yeteneği
C# 9.0 ile tanıtılan `record` tipleri, değişmez (immutable) veri taşıma modelleri (DTO, Command, Query, Event, Value Object) inşa etmek için biçilmiş kaftandır:
1. **Değer Eşitliği (Value-Based Equality):** İki farklı record nesnesinin tüm property değerleri eşitse, `Equals` ve `==` true döner.
2. **Derin ToString Desteği:** Nesnenin içeriğini görsel ve okunaklı biçimde metne döker.
3. **Tahribatsız Mutasyon (with Expression):** Mevcut nesneyi bozmadan, sadece belirli alanları değiştirilmiş yeni bir kopya üretir.
4. **Positional Records:** Tek satırda constructor, property ve deconstruct yapısını otomatik üretir.

```csharp
// Positional Record Tanımı
public sealed record Address(string City, string District, string PostalCode);

public sealed record CustomerDto(Guid Id, string FullName, Address Address);

// 1. Değer Eşitliği Kanıtı
var addr1 = new Address("İstanbul", "Kadıköy", "34710");
var addr2 = new Address("İstanbul", "Kadıköy", "34710");
Console.WriteLine(addr1 == addr2); // TRUE! (Class olsaydı referans farklılığından FALSE dönerdi)

// 2. Tahribatsız Değişim (with expression)
var updatedAddr = addr1 with { District = "Üsküdar" };
Console.WriteLine(addr1.District);       // Kadıköy (Orijinal nesne korundu!)
Console.WriteLine(updatedAddr.District); // Üsküdar (Yeni nesne üretildi)
```

### ⚠️ Kritik Record Tuzağı: Shallow Copy
`with` ifadesi yüzeysel kopyalama (shallow copy) yapar. Eğer bir record'un içinde mutable bir referans tipi (`List<T>`) varsa, üretilen yeni record kopyası da aynı listeyi gösterir. Bu yüzden record içinde mutable koleksiyonlar yerine `ImmutableArray<T>` veya `IReadOnlyList<T>` kullanılmalıdır.

## 16. Interface ve Sözleşme Tabanlı (Contract-Based) Tasarım

### 📌 Interface Nedir ve Neden Hayatidir?
**Interface (Arayüz):** Bir sınıfın dış dünyaya sunduğu yetenekleri ve davranış taahhütlerini bildiren soyut bir sözleşmedir (contract). İçinde verinin nasıl işleneceği (how) değil, tüketicinin ne beklediği (what) tanımlanır.

```text
Sözleşme Tabanlı Mimari:
┌─────────────────────────┐
│     Sipariş Servisi     │
│   (Tüketici Sınıf)      │
└─────────────────────────┘
             │ Bağımlıdır (Depends On)
             ▼
┌─────────────────────────┐
│   <<interface>>         │
│   IPaymentGateway       │
└─────────────────────────┘
             ▲
             │ Sözleşmeyi Uygular (Implements)
   ┌─────────┴─────────┐
   │                   │
┌─────────────────┐ ┌─────────────────┐
│ GarantiGateway  │ │ MockPaymentFake │
│ (Gerçek Banka)  │ │ (Birim Testleri)│
└─────────────────┘ └─────────────────┘
```

### 🎯 Temiz Interface Tasarımı
```csharp
public interface INotificationService
{
    Task SendEmailAsync(string to, string subject, string body, CancellationToken ct = default);
}

// Tüketici sınıf somut sınıfa değil, sözleşmeye bağımlıdır (DIP)
public sealed class OrderService(INotificationService notificationService)
{
    public async Task CompleteOrderAsync(Order order, CancellationToken ct)
    {
        // Sipariş tamamlama mantığı...
        await notificationService.SendEmailAsync(
            "musteri@test.com", 
            "Siparişiniz Alındı", 
            $"Sipariş No: {order.Id}", 
            ct);
    }
}
```

### ⚡ Kritik Kurallar
- **Interface Segregation Principle (ISP):** Şişkin, onlarca metot içeren "God Interface"lerden kaçının. Interface'leri istemcinin ihtiyacına göre küçük ve odaklı parçalara bölün (`IReadableRepository`, `IWritableRepository`).
- Interface içine asla veritabanı veya teknoloji bağımlılığı taşıyan tipler sızdırılmamalıdır (örn. Interface metodunda `DbContext` parametresi geçmek mimari bir suçtur).

## 17. Abstraction: Abstract Class vs Interface ve Composition over Inheritance

### 📌 Ne Zaman Hangisi Tercih Edilmeli?
- **Interface:** Sınıfların "ne yapabileceğini" (can-do) belirten sözleşmedir. Çoklu uygulanabilir (multiple implementation). State (alan) tutmaz.
- **Abstract Class:** Ortak kimliğe (is-a) sahip sınıfların ortak durumunu (state) ve varsayılan davranışlarını paylaşmasını sağlayan yarım kalmış temel sınıftır. Tekli kalıtım kuralına tabidir.

```text
Kalıtım Hiyerarşisi Tuzağı vs Kompozisyon (Composition over Inheritance):
Kötü (Kırılgan Kalıtım):                  Doğru (Esnek Kompozisyon):
┌───────────────────────────┐             ┌───────────────────────────┐
│ Document (Base)           │             │ InvoiceService            │
│  - Print()                │             │  - _validator: IValidator │
│  - ExportPdf()            │             │  - _pdfExporter: IPdfExp. │
└───────────────────────────┘             │  - _repository: IRepo     │
              ▲                           └───────────────────────────┘
              │                           (İhtiyaç duyulan yetenekler
┌───────────────────────────┐              bileşen olarak enjekte edilir!)
│ ReadOnlyArchiveDocument   │
│  - Print() -> Throw Exc!  │ (LSP İhlali!)
└───────────────────────────┘
```

### 🎯 Kompozisyon ile Tasarım
```csharp
public interface IPdfExporter
{
    byte[] Export(string htmlContent);
}

// Kalıtım yerine bağımlılıkları bileşen olarak içeriye almak (Has-a ilişkisi)
public sealed class InvoiceService(IPdfExporter pdfExporter)
{
    public byte[] GenerateInvoicePdf(Invoice invoice)
    {
        string html = $"<h1>Fatura: {invoice.Id}</h1>";
        return pdfExporter.Export(html);
    }
}
```

### ⚠️ Sık Yapılan Hatalar
- Salt kod tekrarını önlemek için birbirleriyle gerçek "is-a" ilişkisi olmayan sınıfları ortak bir Base sınıftan türetmek (Kırılgan Taban Sınıf / Brittle Base Class problemi).
- Türetilen sınıfta taban sınıftan gelen metotları desteklemeyip `throw new NotSupportedException();` atmak (Liskov Substitution Principle ihlali).

## 18. Dependency Injection (DI) Temelleri, Service Lifetime ve Captive Dependency

### 📌 IoC ve Dependency Injection
Bir sınıf ihtiyaç duyduğu bağımlılıkları (servisler, veritabanı bağlantıları) içeride `new` anahtar sözcüğüyle üretmek yerine, dışarıdan (çoğunlukla Constructor üzerinden) talep etmelidir.

```text
Service Lifetimes (Yaşam Döngüleri):
┌───────────┬────────────────────────────────────────────────────────────────────────┐
│ Lifetime  │ Davranış ve Yaşam Süresi                                               │
├───────────┼────────────────────────────────────────────────────────────────────────┤
│ Transient │ Her enjeksiyon talebinde (resolve) SIFIRDAN YENİ bir instance üretilir.│
│ Scoped    │ Bir HTTP isteği (veya tanımlı scope) boyunca TEK bir instance yaşar.   │
│ Singleton │ Uygulama ayağa kalktığından kapanana kadar SADECE BİR instance yaşar. │
└───────────┴────────────────────────────────────────────────────────────────────────┘
```

### 🎯 Servis Kaydı ve Constructor Injection
```csharp
// Program.cs Servis Kayıtları
builder.Services.AddTransient<IEmailSender, SmtpEmailSender>();
builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddSingleton<ISystemClock, SystemClock>();

// C# 12 Primary Constructor ile Servis Kullanımı
public sealed class OrderProcessor(IOrderRepository repository, IEmailSender emailSender)
{
    public async Task ProcessAsync(Guid orderId, CancellationToken ct)
    {
        var order = await repository.GetByIdAsync(orderId, ct);
        // ...
    }
}
```

### ⚠️ Ölümcül Hata: Captive Dependency (Tutsak Bağımlılık)
Bir **Singleton** servis, yaşam süresi kısa olan bir **Scoped** servisi (örneğin `DbContext`) constructor'ında doğrudan enjekte ederse; Scoped servis Singleton'ın ömrü boyunca bellekte tutsak kalır. Bu durum bellek sızıntısına, thread-safety ihlallerine ve veritabanı bağlantı kilitlenmelerine yol açar.

> [!IMPORTANT]
> Arka plan servislerinde (`BackgroundService`) Scoped servis kullanmak için `IServiceScopeFactory` ile manuel scope açılmalıdır:
> ```csharp
> using var scope = serviceScopeFactory.CreateScope();
> var repo = scope.ServiceProvider.GetRequiredService<IOrderRepository>();
> ```

## 19. Array ve List<T> Mimarisi, Kapasite Büyümesi ve Bellek Tahsis Maliyetleri

### 📌 Dizi vs Dinamik Liste
- **Array (`T[]`):** Bellekte bitişik (contiguous) olarak ayrılan, boyutu sabit, indeks erişimi $O(1)$ olan en ilkel ve en hızlı koleksiyon yapısıdır.
- **`List<T>`:** Arka planda bir `T[]` dizisi barındıran dinamik bir yapıdır. Kapasite dolduğunda mevcut dizinin 2 katı büyüklüğünde yeni bir dizi açar ve eski elemanları buraya kopyalar.

```text
List<T> Kapasite Büyümesi:
Başlangıç (Count=0, Capacity=0)
Add(1) ──> Arka Dizi [1, _, _, _] (Capacity=4)
Elemanlar eklendi, 4 doldu...
Add(5) ──> Yeni Dizi Açılır [1, 2, 3, 4, 5, _, _, _] (Capacity=8)
           (Eski dizi GC'ye terk edilir, kopyalama maliyeti oluşur!)
```

### 🎯 Kapasite Optimizasyonu
```csharp
// KÖTÜ: 10.000 eleman eklenirken arka dizi defalarca yeniden oluşturulur ve GC baskısı yaratır
var unoptimized = new List<int>();

// DOĞRU: Beklenen eleman sayısı belliyse kapasite en baştan belirtilmelidir
var optimized = new List<int>(capacity: 10_000);

// C# 12 Koleksiyon İfadeleri (Collection Expressions)
int[] numbers = [1, 2, 3, 4, 5];
List<string> days = ["Pazartesi", "Salı", "Çarşamba"];
```

### ⚡ Kritik Kurallar
- `ToList()` çağrısı bir LINQ sorgusunu anında tetikler (materialization) ve verilerin tamamını RAM'e kopyalar. Filtreleme ve sıralama bitmeden asla çağrılmamalıdır.
- Dışarıya liste dönerken `List<T>` yerine `IReadOnlyList<T>` veya `IEnumerable<T>` dönerek listenin dışarıdan izinsiz değiştirilmesini engelleyin.

## 20. Dictionary<TKey, TValue> ve HashSet<T>: Hash Tabloları ve Eşitlik Karşılaştırması

### 📌 Hash Tablosu Mimarisi
- **`Dictionary<TKey, TValue>`:** Anahtar-değer çiftlerini saklayan; anahtarın `GetHashCode()` ve `Equals()` metotlarını kullanarak arama, ekleme ve silme işlemlerini ortalama $O(1)$ karmaşıklığında gerçekleştiren yapıdır.
- **`HashSet<T>`:** Yalnızca benzersiz (unique) değerler tutan, küme işlemlerini (kesişim, birleşim) son derece hızlı yapan koleksiyondur.

```text
Hash Tablosu Mantığı:
Key ("urun-123") ──> Hash Fonksiyonu ──> Hash Kodu: 849204 ──> Kova İndeksi (Bucket): [4]
Kova [4]: [ Key: "urun-123", Value: 250.00m ]
```

### 🎯 Doğru Kullanım ve Karşılaştırıcılar
```csharp
// 1. Case-Insensitive String Anahtarlı Dictionary
var userRoles = new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase)
{
    ["admin@firma.com"] = "SystemAdmin"
};

// Güvenli Okuma: TryGetValue (KeyNotFoundException'ı Önler)
if (userRoles.TryGetValue("ADMIN@FIRMA.COM", out var role))
{
    Console.WriteLine($"Rol: {role}"); // SystemAdmin
}

// 2. HashSet ile Benzersizlik ve O(1) Varlık Kontrolü
var blacklistedUserIds = new HashSet<Guid>();
bool wasAdded = blacklistedUserIds.Add(userId); // Zaten varsa false döner

// List.Contains O(N) iken, HashSet.Contains O(1)'dir!
if (blacklistedUserIds.Contains(userId))
{
    throw new InvalidOperationException("Engellenmiş kullanıcı.");
}
```

### ⚠️ Sık Yapılan Hatalar
- Dictionary anahtarı olarak kullanılan nesnenin `GetHashCode` sonucunu değiştirebilecek mutable property'lere sahip olması. Nesne map'e eklendikten sonra property'si değişirse hash kodu değişir ve nesne dictionary içinde "kaybolur"!
- `Dictionary` ve `HashSet` eşzamanlı (multi-threaded) yazma işlemlerine karşı güvenli (thread-safe) değildir. Çok iş parçacıklı ortamlarda `ConcurrentDictionary<TKey, TValue>` kullanılmalıdır.

## 21. LINQ Temelleri: Deferred Execution, IEnumerable vs IQueryable ve Projeksiyon

### 📌 Tembel Çalışma (Deferred Execution)
LINQ (Language Integrated Query) sorguları tanımlandıkları satırda değil; sonuçları üzerinde iterasyon başladığında (`foreach`, `ToList()`, `Count()`) çalıştırılır.

```text
IEnumerable vs IQueryable Sınır Çizgisi:
┌────────────────────────────────────────────────────────┐
│ Database Sunucusu (SQL Engine)                         │
│   IQueryable<T>                                        │
│   SQL: SELECT Id, Total FROM Invoices WHERE Total > 100│
└────────────────────────────────────────────────────────┘
                           │
       ToList() Çağrısı ───┴─── (Materialization Çizgisi!)
                           │
┌──────────────────────────▼─────────────────────────────┐
│ Uygulama Belleği (RAM / C# Execution)                  │
│   IEnumerable<T>                                       │
│   Bellekte C# Filtreleri, Hesaplamaları ve Formatlama  │
└────────────────────────────────────────────────────────┘
```

### 🎯 Projeksiyon (Select) ile Bellek ve Ağ Tasarrufu
```csharp
// KÖTÜ: Tüm kolonları belleğe çekip ardından hesaplama yapmak
var badQuery = (await db.Invoices.ToListAsync()) // TÜM TABLO RAM'DE!
    .Where(x => x.IsActive)
    .Select(x => x.Total);

// DOĞRU: SQL'de filtrele, sadece gerekli kolonları çek (Projeksiyon)
var goodQuery = await db.Invoices
    .AsNoTracking()
    .Where(x => x.IsActive && x.Total > 1_000m)
    .Select(x => new InvoiceSummaryDto(x.Id, x.Total)) // SADECE 2 KOLON ÇEKİLİR
    .ToListAsync(cancellationToken);
```

### ⚠️ Sık Yapılan Hatalar: Multiple Enumeration
Bir `IEnumerable` dizisini art arda birden çok kez çalıştırmak sorgunun veya hesaplamanın tekrar tekrar yapılmasına yol açar:
```csharp
// YANLIŞ: Sorgu iki kez çalışır!
if (orders.Any())
{
    foreach (var o in orders) { ... }
}
```

## 22. LINQ Arama ve Varlık Operatörleri: Any, All, First vs Single Semantiği

### 📌 Karar Matrisi
Doğru LINQ operatörünü seçmek hem veri tutarlılığını sağlar hem de veritabanına giden SQL'i optimize eder:

| Operatör | Varlık Yoksa | 1 Eşleşme Varsa | 2+ Eşleşme Varsa | Veritabanı Eşdeğeri |
| :--- | :--- | :--- | :--- | :--- |
| `Any(p)` | `false` | `true` | `true` (İlkinde durur)| `IF EXISTS (...)` |
| `First(p)` | `InvalidOperationException` | Değeri döner | İlk bulduğunu döner | `SELECT TOP(1) ...` |
| `FirstOrDefault(p)`| `default` (veya `null`)| Değeri döner | İlk bulduğunu döner | `SELECT TOP(1) ...` |
| `Single(p)` | `InvalidOperationException` | Değeri döner | `InvalidOperationException`| `SELECT TOP(2) ...` |
| `SingleOrDefault(p)`| `default` (veya `null`)| Değeri döner | `InvalidOperationException`| `SELECT TOP(2) ...` |

### 🎯 Kritik Kod Örnekleri
```csharp
// 1. Varlık Kontrolünde Any() vs Count()
// YANLIŞ: Tüm tabloyu sayar!
// if (await db.Orders.CountAsync(x => x.IsPending) > 0)

// DOĞRU: İlk bulduğu anda durur (EXISTS mantığı)
bool hasPending = await db.Orders.AnyAsync(x => x.IsPending, ct);

// 2. Benzersizlik Kuralı: SingleOrDefault
// E-posta adresi tekil olmalıdır; sistemde ikinci kayıt varsa patlamalıdır!
var user = await db.Users
    .SingleOrDefaultAsync(x => x.Email == "ali@firma.com", ct);
```

### ⚡ Kritik Kurallar
- `SingleOrDefault` bir performans tercihi değildir; veritabanında o kayıttan en fazla 1 tane olabileceğini teyit eden bir **veri bütünlüğü güvencesidir**.
- `FirstOrDefault` bir sıralama garantisi vermez; deterministik bir sonuç için öncesinde mutlaka `OrderBy` kullanılmalıdır.

## 23. LINQ Sıralama, Gruplama (GroupBy) ve Toplama (Aggregate) Optimizasyonu

### 📌 Sıralama ve Gruplama Kuralları
- Sıralama zinciri daima `OrderBy` veya `OrderByDescending` ile başlar; ikincil ve üçüncül sıralamalar için **`ThenBy`** veya **`ThenByDescending`** kullanılır.
- İkinci bir `OrderBy` çağırmak, bir önceki sıralama sonucunu tamamen çöpe atar ve ezerek baştan sıralar!

```csharp
// Çoklu Sıralama ve Gruplamalı Rapor Sorgusu
var categoryReport = await db.Books
    .Where(b => b.IsActive)
    .GroupBy(b => b.Category)
    .Select(g => new CategoryReportDto(
        g.Key,
        g.Count(),
        g.Sum(b => b.Price),
        g.Average(b => b.Price)
    ))
    .OrderByDescending(r => r.TotalRevenue)
    .ThenBy(r => r.CategoryName)
    .ToListAsync(cancellationToken);
```

### ⚡ Sayfalama (Pagination) Öncesi Deterministik Sıralama
Sayfalama (`Skip` ve `Take`) yapılmadan önce deterministik bir sıralama yapılmazsa, sayfa geçişlerinde bazı kayıtlar mükerrer gelirken bazı kayıtlar tamamen atlanabilir. Bu nedenle sıralama ifadesinin sonunda mutlaka `Id` gibi tekil bir alan yer almalıdır.

## 24. Exception Handling: try-catch-finally, Exception Filtreleri ve throw vs throw ex

### 📌 Hata Yakalama Anatomisi
İstisnalar (Exceptions), uygulamanın normal işleyişini bozan ve öngörülemeyen başarısızlık durumlarını temsil eder.

```text
Doğru vs Yanlış Yeniden Fırlatma:
throw;      ──> Orijinal Stack Trace'i KORUR. Hatayı ilk fırlatan satırı net gösterir.
throw ex;   ──> Orijinal Stack Trace'i SİLER! Hatayı bu satırda doğmuş gibi gösterir.
```

### 🎯 Filtreli ve Güvenli Hata Yakalama
```csharp
try
{
    await fileService.ProcessLargeFileAsync(filePath, cancellationToken);
}
catch (FileNotFoundException ex)
{
    logger.LogWarning(ex, "Dosya bulunamadı: {Path}", filePath);
    throw; // Stack trace korunur
}
catch (IOException ex) when (ex.HResult == -2147024864) // Dosya kilitli filtresi
{
    logger.LogError(ex, "Dosya başka bir işlem tarafından kilitlenmiş.");
    throw;
}
finally
{
    // Kaynak temizliği (using kullanılmayan istisnai durumlar için)
}
```

### ⚠️ Ölümcül Hatalar
- Boş `catch { }` blokları ile hatayı yutmak (swallowing exceptions); hatanın kaynağını tamamen gizler.
- `throw ex;` yazarak hata ayıklama izini (stack trace) yok etmek.

## 25. Custom Exceptions, Domain Hataları ve Result Pattern Mimarisi

### 📌 İstisna vs Sonuç (Result Pattern)
- **Exception (İstisna):** Gerçekten istisnai, sistemin sürdürülemez olduğu teknik arızalarda (Disk doldu, DB çöktü, Network koptu) kullanılır. Pahalı bir stack trace maliyeti vardır.
- **Result Pattern:** Beklenen iş kuralı ve validasyon olumsuzluklarında ("Bakiye yetersiz", "Kullanıcı adı kullanımda") kullanılır. İstisna fırlatmaz, sonucu bir nesne olarak döner.

```text
┌────────────────────────────────────────────────────────────────────────┐
│ Result<T> Modeli                                                       │
│ ┌───────────────────────┐  ┌─────────────────────────────────────────┐ │
│ │ IsSuccess: true       │  │ IsSuccess: false                        │ │
│ │ Value: T              │  │ Error: "Bakiye yetersiz."                │ │
│ └───────────────────────┘  └─────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────┘
```

### 🎯 Basit ve Güçlü Result Pattern Uygulaması
```csharp
public readonly record struct Error(string Code, string Message);

public sealed class Result<T>
{
    public bool IsSuccess { get; }
    public T? Value { get; }
    public Error? Error { get; }

    private Result(T value) { IsSuccess = true; Value = value; Error = null; }
    private Result(Error error) { IsSuccess = false; Value = default; Error = error; }

    public static Result<T> Success(T value) => new(value);
    public static Result<T> Failure(Error error) => new(error);
}

// Servis İçinde Kullanımı
public Result<Guid> WithdrawMoney(decimal amount)
{
    if (amount > _balance)
        return Result<Guid>.Failure(new("Balance.Insufficient", "Yetersiz bakiye."));

    _balance -= amount;
    return Result<Guid>.Success(Guid.NewGuid());
}
```

## 27. Refactoring Teknikleri, Separation of Concerns (SoC) ve Kod Kokuları

## 28. Git Branching Stratejileri, Merge vs Rebase ve Conflict Çözümleme

### 📌 Dal (Branch) Yönetimi ve Birleştirme Yolları
- **Branch:** Projeyi bozmadan yeni bir özelliği veya hata düzeltmesini izole geliştirmeyi sağlar.
- **Merge (`git merge`):** İki dalın geçmişini birleştirme commit'i (`merge commit`) ile bağlar. Geçmiş olduğu gibi korunur.
- **Rebase (`git rebase`):** Dalın başlangıç noktasını hedef dalın en son commit'ine taşır; doğrusal (linear) ve tertemiz bir tarihçe sunar.

```text
Merge vs Rebase Tarihçe Görünümü:
Merge:                          Rebase:
A---B---C (main)                A---B---C---D'---E' (main)
     \         /                             (Tertemiz, doğrusal tarihçe)
      D---E---M (feature)
```

### 🎯 Çatışma (Conflict) Çözümleme Protokolü
```powershell
# 1. Ana dalı güncelle ve feature dalına geç
git switch main
git pull
git switch feature/order-api

# 2. Rebase başlat
git rebase main

# 3. Conflict oluşursa dosya içindeki işaretleri düzenle:
# <<<<<<< HEAD (Mevcut main durumu)
# =======
# >>>>>>> feature/order-api (Senin getirdiğin değişiklik)

# 4. Çözülen dosyayı ekle ve rebase'i sürdür
git add src/OrderService.cs
git rebase --continue

# Acil iptal gerekirse:
git rebase --abort
```

> [!WARNING]
> Ortak kullanılan, başkalarının da çalıştığı public branch'lerde asla `git rebase` yapmayın ve `git push --force` atmayın.

```csharp
// 1. Domain Entity & Encapsulation
public sealed class Book
{
    public Guid Id { get; } = Guid.NewGuid();
    public string Title { get; private set; }
    public string Author { get; private set; }
    public bool IsAvailable { get; private set; } = true;

    public Book(string title, string author)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(title);
        ArgumentException.ThrowIfNullOrWhiteSpace(author);
        Title = title;
        Author = author;
    }

    public void MarkAsLoaned()
    {
        if (!IsAvailable)
            throw new InvalidOperationException("Kitap zaten ödünç verilmiş.");
        IsAvailable = false;
    }

    public void MarkAsReturned() => IsAvailable = true;
}

// 2. Application DTO Record ve Servis Sözleşmesi
public sealed record LoanRequest(Guid MemberId, Guid BookId);
public sealed record OverdueLoanDto(Guid LoanId, string MemberName, string BookTitle, int OverdueDays);

public interface ILoanService
{
    Task<Result<Guid>> BorrowBookAsync(LoanRequest request, CancellationToken ct = default);
    Task<IReadOnlyList<OverdueLoanDto>> GetOverdueLoansReportAsync(CancellationToken ct = default);
}
```

## Hızlı Tekrar: 30 Hafıza Cümlesi

1. **IDE** konforlu direksiyon, **Terminal** ortak dil, **SDK** derleme fabrikası, **Runtime** çalıştırma motorudur.
2. **Solution** projeleri gruplar, **Project** derlenir, **`.csproj`** bağımlılık sözleşmesidir.
3. **Restore** indirir, **Build** derler, **Test** doğrular, **Publish** dağıtıma hazırlar.
4. **`git add -p`** atomik seçim yapar, **`commit`** yerelde mühürler, **`push`** ekiple paylaşır.
5. **AI** hızlandırır ve taslak önerir; kodu anlama, test etme ve doğrulama sorumluluğu **mühendise** aittir.
6. **Veri tipi** bir iş kuralıdır; finansal hesaplamalarda `float`/`double` değil, daima **`decimal`** kullanılır.
7. **Guard Clause** yolu temizler; **Switch Expression** seçimleri görünür ve zarif kılar.
8. **Döngünün** bitiş şartını bil; `foreach` içinde koleksiyonu değiştirmekten ve N+1 sorgularından kaçın.
9. **Metot** tek bir amaca hizmet eden sözleşmedir; I/O zincirinde **`CancellationToken`** mutlaka iletilmelidir.
10. **`?`** null olasılığını bildirir, **`?.`** güvenli erişir, **`!`** yalnızca derleyiciyi susturan bir risktir.
11. **Class** şablon, **Object** yaşayan örnektir; referans kopyası aynı heap nesnesini gösterir.
12. **Field** saklar, **Property** denetler, **Constructor** geçerli başlangıç durumunu kurar.
13. **Encapsulation** veriyi gizlemekten öte, nesnenin **invariant** kurallarını dış müdahalelere karşı korumaktır.
14. **Struct** değeri, **Class** kimliği temsil eder; küçük ve immutable değilse struct tercih edilmemelidir.
15. **Record** değer eşitliği ve değişmez veri akışı sunar; `with` yüzeysel kopyalama yapar.
16. **Interface** uygulayıcının kim olduğunu değil, tüketicinin ne beklediğini belirten bir sözleşmedir.
17. Önce **Composition**, sonra ihtiyaç kadar Abstraction; derin kalıtım ağaçlarından kaçının.
18. Bağımlılığını üretme, **DI**'dan talep et; Singleton'a Scoped bağlayıp **Captive Dependency** tuzağına düşme.
19. **Array** sabit ve hızlıdır; **`List<T>`** dinamik büyür; **`ToList()`** veriyi anında RAM'e indirir.
20. **Dictionary** anahtarla, **HashSet** benzersizlikle $O(1)$ sürede konuşur; thread-safe değillerdir.
21. **IQueryable** SQL'de düşünür; **materialization** çizgisinden sonrası uygulama belleğinde (RAM) yaşar.
22. **`Any()`** ilk eşleşmede durur; **`SingleOrDefault()`** tekillik garantisidir; **`Count() > 0`** gereksiz sayım yapar.
23. Önce filtrele, projeksiyonla kolonları küçült, grupla, deterministik sırala ve en son materialize et.
24. Hatayı sessizce yutma; yeniden fırlatacaksan stack trace'i korumak için sadece **`throw;`** de.
25. Beklenen doğrulama hataları **Result Pattern**, öngörülemeyen teknik felaketler **Exception**'dır.
26. **Temiz Kod** bilgisayara ne yapacağını, geliştiriciye hangi niyetle yaptığını açıkça anlatır.
27. **Refactoring** evin odalarını çoğaltmaz, planını ve borularını düzeltir; test güvencesi olmadan yapılamaz.
28. **Branch** ayırır, **Rebase** doğrusal tarihçe sunar; çatışmayı (conflict) doğru iş mantığını bilen geliştirici çözer.
29. İyi bir **PR** küçük, test edilmiş ve tek amaçlıdır; **Code Review** ekip aklını koda taşır.
