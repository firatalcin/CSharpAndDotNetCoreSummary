## 01. HTTP Protokolü, Request-Response Modeli ve REST URI Tasarımı

### 📌 Temel Tanım
**HTTP (Hypertext Transfer Protocol)**, istemci (client) ile sunucu (server) arasındaki iletişimin kurallarını belirleyen metin tabanlı, durumsuz (**stateless**) bir uygulama katmanı protokolüdür. İletişim daima istemcinin bir istek (**Request**) başlatması ve sunucunun buna bir yanıt (**Response**) dönmesi esasına dayanır.

```text
HTTP Request İskeleti:
POST /api/v1/loans HTTP/1.1              ──> [Başlangıç Satırı: Metot + Path + Protokol Sürümü]
Host: api.kutuphane.com                  ──┐
Authorization: Bearer eyJhbGci...         ├──> [Header'lar: Metadata, Kimlik, İçerik Türü]
Content-Type: application/json           ──┘
                                         ───> [Boş Satır (CRLF)]
{"bookId": 7, "memberId": 3}             ───> [Message Body: Asıl Yük (Payload)]

HTTP Response İskeleti:
HTTP/1.1 201 Created                     ──> [Başlangıç Satırı: Protokol + Status Code + Reason]
Location: /api/v1/loans/88               ──┐
Content-Type: application/json           ──┴─> [Header'lar]
                                         ───> [Boş Satır]
{"id": 88, "bookId": 7, "status": "Active"} ─> [Message Body]
```

### 🎯 En Önemli Kullanım Amacı & Veri Yerleşim Kuralları
- **Path (Yol):** Kaynağın tekil kimliği ve hiyerarşisi (`/api/v1/members/3/loans`).
- **Query String:** Filtreleme, sıralama ve sayfalama (`?status=overdue&page=1&size=20`).
- **Request Body:** Oluşturulacak ya da güncellenecek veri yükü (JSON nesnesi).
- **Headers:** Kimlik doğrulama token'ı (`Authorization`), veri biçimi (`Content-Type`, `Accept`), correlation ID veya özel izleme bilgileri.

### ⚡ Kritik Kurallar
- **Stateless Mimari:** Sunucu iki istek arasında istemci durumunu belleğinde tutmaz. Her istek kendini tanıtan kimlik bilgisini (`Authorization: Bearer <token>`) taşır. Kalıcı durum veritabanında (SQL Server) yaşar; bu sayede sunucular yatayda (horizontal scaling) serbestçe çoğaltılabilir.
- **HTTPS & TLS:** Tüm HTTP paketlerini TLS tüneli içinde şifreler; gizlilik (confidentiality), veri bütünlüğü (integrity) ve sunucu doğrulaması (authentication) sağlar. Path ve query URL'leri de şifrelenir; ancak sunucu/proxy erişim loglarına düştüğü için hassas bilgiler (şifre, token, kimlik no) asla URL'ye konulmaz.
- **RESTful URI İlkeleri:**
  1. URI'lar fiil değil **isim (noun)** içermelidir: `/lendBook` (YANLIŞ) $\to$ `/loans` (DOĞRU).
  2. Koleksiyonlar **çoğul** yazılmalıdır (`/loans`, `/books`, `/members`).
  3. Küçük harf ve **kebab-case** kullanılmalıdır (`/loan-agreements`).
  4. Hiyerarşik derinlik en fazla 1-2 seviye olmalıdır: `/members/3/loans` (üye 3'ün ödünç aldıkları).
  5. İşlem fiilini URI değil, **HTTP Metodu** belirler.

### ⚠️ Sık Yapılan Hatalar
- REST yerine gizli RPC yapmak: `POST /api/deleteOrder?id=5` yerine `DELETE /api/orders/5` kullanılmalıdır.
- Hata durumunda HTTP 200 dönüp gövdede hata bildirmek: `200 OK` + `{"success": false, "error": "Kargo çıktı iptal edilemez"}` YANLIŞTIR. Sunucudaki mevcut durumla çakışma durumunda **`409 Conflict`** dönülmelidir.
- Filtre parametrelerini path içine gömmek: `/loans/overdue` yerine `/loans?status=overdue` tercih edilmelidir.

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- API gateway ve load balancer arkasında loglanan URI'ların hassas veri sızdırmaması için URL tasarımını güvenlik denetiminden geçirin.
- Status kodları yalnızca istemciye değil, aradaki APM araçlarına (Dynatrace, Datadog), CDN'lere ve log indeksleyicilere sistemin sağlığı hakkında kesin metrikler verir.

> [!TIP]
> **Zihinsel Model:** URI "nerede/hangi kaynak" sorusuna cevap veren isimdir; HTTP metodu o kaynak üzerinde "ne yapılacağını" söyleyen eylemdir.

## 02. HTTP Metodları, Safety, Idempotency ve Status Code Semantiği

### 📌 Temel Tanım
HTTP metodları istemcinin niyetini, durum kodları (status codes) ise sunucunun işlem sonucunu ifade eden evrensel sözlüktür.

| Metot | İşlev | Safety (Güvenli mi?) | Idempotency (Eşgüçlü mü?) | Başarılı Yanıtlar |
| :--- | :--- | :---: | :---: | :--- |
| **GET** | Kaynağı okur | **EVET** | **EVET** | `200 OK` |
| **POST** | Yeni kaynak yaratır / İşlem tetikler | **HAYIR** | **HAYIR** | `201 Created` (+ Location) |
| **PUT** | Kaynağı bütünüyle değiştirir / Belirtilen URI'da oluşturur | **HAYIR** | **EVET** | `200 OK`, `204 No Content`, `201 Created` |
| **PATCH** | Kaynağın sadece belirtilen alanlarını kısmi günceller | **HAYIR** | **GARANTİSİ YOK** | `200 OK`, `204 No Content` |
| **DELETE**| Kaynağı siler | **HAYIR** | **EVET** | `200 OK`, `204 No Content`, `404 Not Found` |

### 🎯 Safety ve Idempotency Neden Hayatidir?
- **Safety:** Bir metodun çalıştırılması sunucunun kaynak durumunda istemcinin göreceği bir değişiklik yaratmamalıdır (loglama, metrik artırma gibi yan etkiler safety'yi bozmaz).
- **Idempotency (Eşgüçlülük):** Aynı isteğin bir kez ya da 10 kez art arda gönderilmesi durumunda sunucuda **aynı son durumun** kalmasıdır. 
  - *Örnek Senaryo:* İstemci mobil ağda sipariş gönderirken bağlantı koptu. Eğer `PUT /api/orders/7c9e` kullandıysa isteği güvenle tekrar gönderebilir; ilk çağrı siparişi oluşturur, ikinci çağrı var olanı ezer, sonuçta yine tek sipariş vardır. Fakat `POST /api/orders` kullanılırsa iki kez basıldığında çift sipariş oluşur. POST işlemlerinde eşgüçlülük için **`Idempotency-Key`** başlığı kullanılır.

### ⚡ Status Code Semantiği
- **2xx (Başarı):**
  - `200 OK`: İstek başarılı, gövdede veri dönüyor.
  - `201 Created`: Yeni kaynak oluşturuldu, `Location: /api/orders/42` başlığı ile yeni kaynağın adresi verildi.
  - `204 No Content`: İşlem başarılı ama istemciye dönecek gövde yok (örneğin DELETE veya bazı PUT işlemleri).
- **4xx (İstemci Hatası):**
  - `400 Bad Request`: Sözdizimi hatalı istek (bozuk JSON, geçersiz tip).
  - `401 Unauthorized`: Kimlik doğrulanmadı ("Sen kimsin?").
  - `403 Forbidden`: Kimlik doğrulandı ama yetki yetersiz ("Seni tanıyorum ama buraya giremezsin").
  - `404 Not Found`: İstenen URI'da kaynak yok.
  - `409 Conflict`: İstek sunucunun mevcut durumuyla çakışıyor (örn. DB unique index ihlali, kargodaki siparişin iptali).
  - `422 Unprocessable Entity`: İstek biçimi doğru ama anlamsal iş kurallarına aykırı (örn. İndirimli fiyat > normal fiyat).
- **5xx (Sunucu Hatası):**
  - `500 Internal Server Error`: Sunucuda öngörülmeyen arıza. Asla form validasyonu için dönülmez ve production'da asla stack trace içermez.

> [!IMPORTANT]
> `401` ile `403` farkı mülakatlarda en sık sorulan konudur: Token yoksa veya geçersizse $\to$ `401`; geçerli User token'ı ile Admin endpoint'ine gidilirse $\to$ `403`.

## 03. ASP.NET Core Hosting, Program.cs ve İlk Minimal Endpoint

### 📌 Temel Tanım & Hosting Modeli
ASP.NET Core uygulaması iki aşamalı bir yaşam döngüsüne sahiptir:
1. **Builder Aşaması ("Neyim var?"):** `WebApplication.CreateBuilder(args)` çağrısıyla başlar. Kestrel sunucusu ayarlanır, konfigürasyon kaynakları okunur, DI konteyneri (`builder.Services`) hazırlanır ve loglama altyapısı kurulur.
2. **App Aşaması ("Gelen isteğe ne yapacağım?"):** `builder.Build()` ile servis konteyneri kilitlenir. Middleware boru hattı (`app.Use...`) ve endpoint yönlendirmeleri (`app.Map...`) yapılandırılır. `app.Run()` ile Kestrel dinlemeye başlar.

```csharp
var builder = WebApplication.CreateBuilder(args);

// 1. AŞAMA: BUILDER (Servisler / DI)
builder.Services.AddOpenApi();

var app = builder.Build(); // <-- Sınır Çizgisi! Buradan sonra servis eklenemez.

// 2. AŞAMA: APP (Pipeline & Endpoints)
if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
    app.UseSwaggerUI(o => o.SwaggerEndpoint("/openapi/v1.json", "v1"));
}

app.MapGet("/kitaplar/{id:int}", (int id) =>
{
    return TypedResults.Ok(new { Id = id, Baslik = "ASP.NET Core Mimarisi" });
});

app.Run();
```

### ⚡ Kritik Kurallar ve Kestrel
- **Build Sonrası Kilit:** `builder.Build()` çağrısından sonra `builder.Services.Add...` çağırmak `InvalidOperationException` fırlatır.
- **Kestrel Web Sunucusu:** Platformlar arası, in-process çalışan yüksek performanslı web sunucusudur. Ağ soketlerinden gelen byte dizilerini okur, her istek için bir `HttpContext` nesnesi oluşturup pipeline'a verir.
- **Docker ve Dış Erişim:** `localhost` sadece makine içi iletişime izin verir. Docker container'larında dış dünyadan istek alabilmek için Kestrel `0.0.0.0` IP'sini dinlemelidir.
- **launchSettings.json:** Yalnızca lokal geliştirme ortamında (`dotnet run`) kullanılır. IIS Express / Kestrel portlarını ve ortam değişkenlerini tanımlar. Publish çıktısına girmez; production'da bu dosya yoktur.
- **Route Constraints (`{id:int}`):** Rota uyuşmazlığında isteği endpoint'e hiç sokmadan `404 Not Found` döner. Bu bir doğrulama aracı değildir; rotayı eşleme mekanizmasıdır.

### ⚠️ Sık Yapılan Hatalar
- Production ortamında Swagger'ı `app.Environment.IsDevelopment()` kontrolü olmadan açık bırakıp API saldırı yüzeyini genişletmek.
- `app.Run()` satırını unutmak veya içine delegate verip (`app.Run(async ctx => ...)`) terminal middleware olarak pipeline'ı istemeden sonlandırmak.
- Hassas şifre ve bağlantı cümlelerini `launchSettings.json` veya `appsettings.json`'a açık metin yazmak (Lokalde *User Secrets*, sunucuda *Ortam Değişkenleri / Key Vault* kullanılmalıdır).

## 04. Controller Mimarisi, Attribute Routing ve ActionResult Yapısı

### 📌 Temel Tanım
Controller mimarisi; gelen HTTP isteklerini karşılayan, model bağlama (model binding) ve dönüşüm işlerini framework'e devredip iş mantığını organize eden modüler bir yapıdır.

- `AddControllers()`: Controller servislerini DI'a kaydeder.
- `MapControllers()`: Attribute routing haritasını HTTP pipeline'ına bağlar (unutulursa tüm controller istekleri `404` alır).
- `ControllerBase`: API controller'ları için temel sınıftır. MVC sayfaları için gereken HTML View altyapısını içermez, hafiftir.

```csharp
[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    private static readonly List<Product> _products = [];
    private static readonly Lock _lock = new(); // In-memory liste için thread-safety

    [HttpGet("{id:int}")]
    public ActionResult<Product> GetById(int id)
    {
        lock (_lock)
        {
            var product = _products.FirstOrDefault(p => p.Id == id);
            return product is null ? NotFound() : product; // Otomatik 200 OK veya 404
        }
    }

    [HttpPost]
    public ActionResult<Product> Create(CreateProductRequest request)
    {
        var product = new Product(Guid.NewGuid().GetHashCode(), request.Name, request.Price);
        lock (_lock) { _products.Add(product); }

        return CreatedAtAction(nameof(GetById), new { id = product.Id }, product);
    }
}
```

### ⚡ [ApiController] Attribute'unun 4 Kritik Yeteneği
1. **Zorunlu Attribute Routing:** Route attribute'u olmayan action'lara izin vermez.
2. **Otomatik Model Validasyonu:** `ModelState.IsValid` kontrolünü kendisi yapar; geçersiz isteklerde action metodunu hiç çalıştırmadan `400 Bad Request` (`ValidationProblemDetails`) döner.
3. **Akıllı Binding Çıkarımı:** Karmaşık tipleri (complex types) body'den, şablonda geçenleri route'tan, basit tipleri query string'den otomatik eşler.
4. **Standart Hata Cevapları:** `NotFound()`, `BadRequest()` gibi çağrılarda gövdeye RFC uyumlu `ProblemDetails` ekler.

### 🎯 IActionResult vs ActionResult<T>
- `IActionResult`: Esnektir ancak dönüş tipini açıkça belirtmediği için compile-time tip güvenliği sağlamaz ve Swagger/OpenAPI dokümanı dönüş tipini otomatik çıkaramaz.
- `ActionResult<T>`: C# implicit operator sayesinde ya doğrudan `T` (200 OK) ya da bir `ActionResult` (`NotFound()`, `BadRequest()`) dönebilir. Hem derleyici tip denetimi sağlar hem de OpenAPI'ya başarılı durumda `T` döneceğini bildirir.

> [!NOTE]
> `CreatedAtAction`: `Location: https://localhost:7001/api/Products/3` gibi bir yanıt başlığını dinamik olarak üretir. Action adı olarak `nameof(GetById)` kullanılması, şablondaki parametre isimleriyle anonim nesnedeki (`new { id = product.Id }`) isimlerin birebir eşleşmesi şarttır.

## 05. Model Binding, Content Negotiation ve System.Text.Json Ayarları

### 📌 Model Binding Kargo Kolisi Modeli
Model binding mekanizması, gelen HTTP isteğindeki ham metinleri okuyup metot parametrelerine dönüştürür.

```text
HTTP İsteği (Kargo Kolisi)
├── Adres Etiketi       ──>  URL Path   ──> [FromRoute]
├── Üstteki Notlar      ──>  Query      ──> [FromQuery]
├── Kolinin İçi         ──>  Body       ──> [FromBody] (Yalnızca 1 adet olabilir!)
└── Gönderici Damgası   ──>  Headers    ──> [FromHeader]
```

```csharp
[HttpGet("{customerId:int}/orders")]
public IActionResult ListOrders(
    [FromRoute] int customerId,
    [FromQuery] OrderFilter filter,
    [FromHeader(Name = "X-Tenant-Id")] string tenantId)
{
    // ...
}
```

### ⚡ Kritik Bağlama ve JSON Kuralları
- **Stream Kuralı:** HTTP Request Body bir stream'dir ve ağdan parça parça bir kez okunur. Bu sebeple bir action metodunda birden fazla `[FromBody]` parametresi **kesinlikle bulunamaz**.
- **Header Tahmini:** `[ApiController]` route ve body'yi tahmin edebilir ama header'ları asla otomatik tahmin etmez; `[FromHeader]` mutlaka açıkça yazılmalıdır.
- **GET ve Kompleks Tip Tuzağı:** GET metodunda `OrderFilter` gibi bir nesne alırken `[FromQuery]` yazılmazsa, framework bunu gövdeden okumaya çalışır ve istemci `415 Unsupported Media Type` hatası alır.
- **Content Negotiation:** İstemci `Accept: application/xml` gönderirse sunucu uygun formatter (`AddXmlSerializerFormatters`) varsa XML döner. `ReturnHttpNotAcceptable = true` ayarlanırsa üretilemeyen formatlarda `406 Not Acceptable` verilir.

### 🛠️ System.Text.Json Yapılandırması
```csharp
builder.Services.AddControllers().AddJsonOptions(options =>
{
    // Enum'ları sayı (0, 1) yerine metin ("Pending", "Shipped") olarak yazar/okur
    options.JsonSerializerOptions.Converters.Add(new JsonStringEnumConverter());
    // Null olan property'leri JSON çıktısından eler
    options.JsonSerializerOptions.DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull;
});
```

> [!WARNING]
> `WhenWritingDefault` kullanmayın! Bu ayar `0`, `false` gibi varsayılan değerleri de çıktıdan gizleyerek veri kaybı yanılgısına yol açar. Null alanlar için daima `WhenWritingNull` kullanılmalıdır.

## 06. API Contract, DTO Tasarımı ve Over-Posting Koruması

### 📌 Entity vs API Contract vs DTO
- **Domain Entity:** Veritabanı tablosuna karşılık gelen iç iş modelidir (`Order`, `User`). Dış dünyaya asla açılmamalıdır.
- **API Contract:** API'nin dış dünyayla imzaladığı "Bu formatta alırım, bu formatta veririm" sözleşmesidir.
- **DTO (Data Transfer Object):** Sözleşmeyi kod tarafında temsil eden, mantık içermeyen hafif veri taşıyıcı nesnelerdir.

```text
Restoran Analojisi:
Domain Entity ──> Mutfak & Aşçı (İç dünya, müşteriye kapalı)
API Contract  ──> Restoran Menüsü (Müşteriye sunulan resmi sözleşme)
DTO           ──> Sipariş Fişi (Müşteri ile mutfak arasında taşınan sınırlı veri)
```

### ⚠️ Entity'yi Doğrudan API'ye Açmanın 4 Büyük Riski
1. **Hassas Veri Sızıntısı:** `User` entity'sindeki `PasswordHash`, `RefreshToken` gibi alanların istemciye gitmesi.
2. **Döngüsel Referans (Circular Reference):** `Order.Items` ve `OrderItem.Order` arasındaki ilişkilerin JSON serializer'ı sonsuz döngüye sokup patlatması.
3. **Kırılgan Sözleşme:** Veritabanındaki bir kolon adının değişmesinin tüm mobil ve web istemcilerini bozması.
4. **Over-Posting (Mass Assignment) Saldırısı:** İstemcinin oluşturma veya güncelleme esnasında göndermemesi gereken alanları göndermesi. Model binder JSON'daki her alanı entity setter'ı ile eşleştirdiği için saldırgan JSON'a `"isAdmin": true` ekleyerek yetkisini yükseltebilir.

### 🛡️ DTO Tasarımı ve Mapping Çözümü

## 08. Dependency Injection (DI) ve Service Lifetime Yönetimi

### 📌 Temel Tanım
**Dependency Injection (DI)**, bir sınıfın bağımlı olduğu nesneleri `new` anahtar kelimesiyle kendisinin üretmesi yerine, bu nesnelerin dışarıdan (genellikle constructor üzerinden) sınıfa verilmesidir. **Inversion of Control (IoC)** prensibinin somut bir uygulamasıdır.

```text
      [IServiceCollection] ──(builder.Build())──> [IServiceProvider]
                                                          │
                    ┌─────────────────┬───────────────────┴───────────────────┐
                    ▼                 ▼                                       ▼
              [Transient]          [Scoped]                              [Singleton]
           (Her istekte yeni)   (HTTP İsteği Başına 1 Tane)          (Uygulama Boyunca Tek)
```

### ⏳ 3 Servis Yaşam Döngüsü (Service Lifetimes)
1. **Transient (`AddTransient`):** Servis her talep edildiğinde yeni bir instance üretilir. Durumsuz (stateless), hafif yardımcı sınıflar için uygundur.
2. **Scoped (`AddScoped`):** Her HTTP isteği (request scope) için tek bir instance üretilir; aynı istek içerisindeki tüm bileşenler aynı nesneyi paylaşır. `DbContext` ve iş servisleri (`OrderService`) kesinlikle Scoped olmalıdır.
3. **Singleton (`AddSingleton`):** Uygulama ayağa kalktığında bir kez üretilir ve uygulama kapanana kadar tüm isteklerde aynı instance kullanılır. Bellek içi önbellek veya konfigürasyon servisleri için uygundur; **kesinlikle thread-safe olmak zorundadır** (`ConcurrentDictionary`).

### ⚠️ En Tehlikeli Hata: Captive Dependency (Tutsak Bağımlılık)
Daha uzun ömürlü bir servisin, daha kısa ömürlü bir servisi constructor'ında alıp hapsetmesidir.
- *Örnek Felaket:* `Singleton` bir `OrderCacheService`'in constructor'ında `Scoped` olan `AppDbContext`'i alması. `DbContext` singleton nesnenin içinde hapsolur; uygulama boyunca tek bir context yaşar. Sonuç: Eşzamanlı isteklerde DbContext concurrency çakışmaları, şişen bellek ve bayat (stale) veriler.
- *Çözüm:* Kısa ömürlü servisi tutmak yerine `IServiceScopeFactory` alıp gerektiğinde geçici bir scope açmaktır:

```csharp
public class OrderStatsBackgroundService(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var scope = scopeFactory.CreateScope();
        var orderService = scope.ServiceProvider.GetRequiredService<IOrderService>();
        await orderService.ProcessDailyStatsAsync(stoppingToken);
    }
}
```

> [!TIP]
> `builder.Host.UseDefaultServiceProvider(o => o.ValidateScopes = true);` ayarını açarak Captive Dependency hatalarını uygulamanın açılış anında yakalayabilirsiniz.

## 09. Async/Await, CancellationToken ve Asenkron Endpoint Tasarımı

### 📌 Thread Pool Starvation ve Async Mantığı
Web API'ye gelen her HTTP isteği .NET ThreadPool'dan bir iş parçacığı (worker thread) alır. Senkron kodda veritabanı sorgusu veya dış API cevabı beklenirken bu thread uyur (bloklanır). Yoğun yük altında tüm thread'ler bloklandığında yeni isteklere cevap verilemez; buna **Thread Pool Starvation (Thread Açlığı)** denir.

```text
Senkron Model (Thread Bloklanır):
İstek ──> [Thread #1] ───(DB Sorgusu Bekleniyor: 200ms Boşta Bekleme)───> Yanıt

Asenkron Model (Thread Havuza İade Edilir):
İstek ──> [Thread #1] ──(await)──┐ Thread serbest kalır, başka isteğe koşar!
                                 │ DB yanıtı geldiğinde boştaki [Thread #4] işi devralır.
                                 └─> [Thread #4] ───> Yanıt
```

### ⚡ "Async All The Way" İlkeleri
1. **Bloklama Yapmayın:** Asenkron bir görevi beklerken `.Result`, `.Wait()` veya `GetAwaiter().GetResult()` kullanmayın. Bu çağrılar thread açlığına ve deadlock riskine yol açar.
2. **Task.Run Kullanmayın:** Web API action metotlarında I/O işlemlerini `Task.Run` içine sarmak anlamsızdır; thread havuzundan ekstra thread harcar.
3. **async void Asla Kullanmayın:** Sadece UI event handler'larında geçerlidir. Web API'de fırlatılan exception yakalanamaz ve tüm process'i çökertebilir.

### 🛑 CancellationToken ile Kooperatif İptal
Kullanıcı sekmeyi kapattığında veya mobil istemci bağlantıyı kestiğinde veritabanındaki 30 saniyelik ağır sorgunun boşuna çalışmasını engeller.

```csharp
[HttpGet]
public async Task<ActionResult<List<OrderResponse>>> GetOrders(CancellationToken ct)
{
    // HttpContext.RequestAborted otomatik olarak ct parametresine bağlanır.
    var orders = await _orderService.GetAllOrdersAsync(ct);
    return Ok(orders);
}
```

- İptal kooperatiftir; token metot zinciri boyunca alt katmanlara (`ToListAync(ct)`) iletilmezse hiçbir işe yaramaz.
- İptal gerçekleştiğinde `OperationCanceledException` fırlatılır. Bu bir sistem arızası değil, olağan bir durumdur.
- **İstisna Durum:** Ödeme alındıktan sonra sipariş kaydetmek gibi geri dönüşü olmayan atomik yazma işlemlerinde `CancellationToken.None` kullanılmalıdır.

### 📌 Konfigürasyon Katmanları ve Ezme (Override) Sırası
ASP.NET Core'da konfigürasyon `IConfiguration` adı verilen hiyerarşik bir anahtar-değer sözlüğünde birleşir. Değerler şu öncelik sırasıyla birbirini ezer (en son okunan kazanır):

Konfigürasyon bölümlerini doğrudan kodun içinde string anahtarlarla (`config["OrderSettings:MinAmount"]`) okumak yerine güçlü tipli sınıflara bağlarız:

| Tip | Yaşam Döngüsü | Çalışma Mekanizması | Kullanım Yeri |
| :--- | :--- | :--- | :--- |
| **`IOptions<T>`** | Singleton | Uygulama açılışında 1 kez okunur, dosya değişse de güncellenmez. | Değişmeyen ayarlar, Singleton servisler |

## 11. API Validation Mimarisi ve FluentValidation

### 📌 Input Validation vs Business Rule Validation
- **Input Validation (Girdi Doğrulaması):** İsteğin biçim, format ve aralık kontrolleridir. Sistemin o anki durumuna bakmaya gerek yoktur (örn. `Email` formatı, `Quantity > 0`). Hatası daima **`400 Bad Request`** döner.
- **Business Rule Validation (İş Kuralı Doğrulaması):** Biçimsel olarak doğru olan isteğin, sistemin veritabanı durumuna göre geçerli olup olmadığıdır (örn. Stok yeterli mi? Müşteri bakiye limiti aşıldı mı?). Hatası tercihen **`422 Unprocessable Entity`** veya **`409 Conflict`** döner.

```text
İstek ──> [Input Validation: FluentValidation] ──(Hata: 400 Bad Request)
               │ (Geçerli)
               ▼
          [Business Rules: Service Katmanı]     ──(Kural İhlali: 422 veya 409)
               │ (Geçerli)
               ▼
          [Database Kısıtları: CHECK / UNIQUE]  ──(Son Savunma Hattı: 409 Conflict)
```

### 🛠️ FluentValidation Kullanımı
Kurallar DTO'dan tamamen ayrılarak `AbstractValidator<T>` sınıflarına yazılır:

```csharp
public class CreateOrderRequestValidator : AbstractValidator<CreateOrderRequest>
{
    public CreateOrderRequestValidator()
    {
        RuleFor(x => x.CustomerId).NotEmpty();
        RuleFor(x => x.Items).NotEmpty().WithMessage("Sipariş en az bir ürün içermelidir.");
        RuleForEach(x => x.Items).SetValidator(new OrderItemDtoValidator());
    }
}

public class OrderItemDtoValidator : AbstractValidator<OrderItemDto>
{
    public OrderItemDtoValidator()
    {
        RuleFor(x => x.ProductId).NotEmpty();
        RuleFor(x => x.Quantity).GreaterThan(0).WithMessage("Miktar 0'dan büyük olmalıdır.");
        RuleFor(x => x.UnitPrice).GreaterThan(0).WithMessage("Birim fiyat 0'dan büyük olmalıdır.");
    }
}
```

### 📋 RFC 9457 ValidationProblemDetails
FluentValidation sonuçları doğrudan RFC 9457 standardındaki hata formatına dönüştürülür:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",

  "errors": {
```

## 12. Request Pipeline, Middleware Mimarisi ve Custom Middleware

### 📌 Middleware Boru Hattı Mantığı
Gelen her HTTP isteği, matruşka bebekleri gibi iç içe geçmiş bir middleware zincirinden geçer. Pipeline çift yönlüdür: istek kaydolma sırasıyla içeri doğru akar; yanıt ise aynı zincirden geriye doğru çıkar.

```text
HTTP Request  ──> [Middleware 1 (Örn: Exception)]  ──(await next)──┐
                      [Middleware 2 (Örn: Routing)]                 │
                          [Middleware 3 (Örn: Auth)]                ▼
                              └──> [Endpoint / Controller Action] ──┘
HTTP Response <── [Geri Dönüş Yolu: Cevap Header'ları ve Body Yazımı]
```

### ⚡ Doğru Middleware Sıralaması (Kritik!)
Sıralama hatalı kurulursa uygulama güvenlik zaafiyeti verir veya beklenmedik `401/500` hataları üretir:

```csharp
app.UseExceptionHandler(); // 1. En dışta: Tüm pipeline'daki hataları yakalar
app.UseHsts();
app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();          // 2. Rotayı belirler

app.UseCors();             // 3. Preflight istekleri için Routing'den hemen sonra!

app.UseAuthentication();   // 4. "Sen kimsin?" (Kimlik Doğrulama)
app.UseAuthorization();    // 5. "Yetkin var mı?" (Yetkilendirme)

app.UseMiddleware<AuditLogMiddleware>(); // 6. Custom Middleware'ler

app.MapControllers();      // 7. En içte: Controller action'ları çalışır
```

### 🛠️ Custom Middleware ve Scoped Servis Tuzağı
Bir middleware sınıfı singleton gibi davranır. Constructor'da `DbContext` gibi scoped servisler istenirse **Captive Dependency** oluşur. Scoped servisler **`InvokeAsync` metodunun parametresine** eklenmelidir:

```csharp
public class PerformanceLoggingMiddleware(RequestDelegate next, ILogger<PerformanceLoggingMiddleware> logger)
{
    public async Task InvokeAsync(HttpContext context)
    {
        var sw = Stopwatch.StartNew();
        
        await next(context); // İsteği bir sonraki middleware'e devret
        
        sw.Stop();
        if (sw.ElapsedMilliseconds > 500)
        {
            logger.LogWarning("Yavaş İstek: {Path} ({Elapsed} ms)", context.Request.Path, sw.ElapsedMilliseconds);
        }
    }
}
```

## 13. Merkezi Hata Yönetimi, IExceptionHandler ve ProblemDetails

### 📌 Try-Catch Kirliliği ve Çözümü
Controller metotlarına yüzlerce `try-catch` yazmak kod tabanını kirletir, tutarsız hata formatları üretir ve en kötüsü `ex.ToString()` ile veritabanı şemasını / stack trace'i dışarıya sızdırır. Doğru yaklaşım: controller'da sadece mutlu yolu yazmak, hataları fırlatıp merkezi bir **`IExceptionHandler`** ile yakalamaktır.

### 🛡️ RFC 9457 ProblemDetails Alanları
- **`type`**: Hata türünü tanımlayan URI referansı.
- **`title`**: Hataya dair kısa, insan tarafından okunabilir özet.
- **`status`**: HTTP durum kodu (`404`, `409`, `422`, `500`).
- **`detail`**: O olaya özgü açıklayıcı mesaj.
- **`instance`**: Hatanın oluştuğu request URI'si (`/api/v1/orders/12`).
- **`traceId`**: Loglar ile hatayı eşleştiren korelasyon numarası.

### ⚙️ .NET 8/10 IExceptionHandler Mimarisi
```csharp
public class GlobalExceptionHandler(ILogger<GlobalExceptionHandler> logger) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext, Exception exception, CancellationToken cancellationToken)
    {
        logger.LogError(exception, "Beklenmeyen bir hata oluştu: {Message}", exception.Message);

        var (statusCode, title) = exception switch
        {
            OrderNotFoundException => (StatusCodes.Status404NotFound, "Sipariş Bulunamadı"),
            BusinessRuleException  => (StatusCodes.Status422UnprocessableEntity, "İş Kuralı İhlali"),
            _                      => (StatusCodes.Status500InternalServerError, "Sunucu Hatası")
        };

        var problemDetails = new ProblemDetails
        {
            Status = statusCode,
            Title = title,
            Detail = statusCode == 500 ? "Sistemsel bir hata oluştu." : exception.Message,
            Instance = httpContext.Request.Path
        };

        httpContext.Response.StatusCode = statusCode;
        await httpContext.Response.WriteAsJsonAsync(problemDetails, cancellationToken);
        return true; // Hatanın işlendiğini ve pipeline'ın kapandığını bildirir
    }
}
```

> [!CAUTION]
> 500 hatalarında `exception.Message` veya `exception.StackTrace` asla istemciye dönülmez! Detay güvenli log sunucusuna yazılır, istemciye yalnızca `traceId` verilir.

## 15. Pagination (Sayfalama) Tasarımı ve PagedResponse Modeli

### 📌 Neden Sayfalama Zorunludur?
Binlerce satırlık bir tabloyu tek seferde dönmek; SQL sunucusunu kilitler, API sunucusunda yüksek RAM allocation'ına yol açar, ağı boğar ve istemci uygulamasını dondurur.

```text
Felaket Senaryosu (In-Memory Pagination):
db.Orders.ToListAsync(); ──> (1.000.000 satır RAM'e çekildi!) ──> .Skip(20).Take(10) (YANLIŞ!)

Doğru Mimari (Database-Level Pagination):
db.Orders.Skip(20).Take(10).ToListAsync(); ──> SQL: OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY
```

### ⚖️ Offset vs Cursor Tabanlı Sayfalama
| Özellik | Offset-Based (`pageNumber`, `pageSize`) | Cursor-Based (`afterCursor`, `pageSize`) |
| :--- | :--- | :--- |
| **SQL Karşılığı** | `OFFSET 40 ROWS FETCH NEXT 20 ROWS ONLY` | `WHERE Id > @lastSeenId ORDER BY Id` |
| **Büyük Veride Hız**| Sayfa derinleştikçe yavaşlar (Skip maliyeti) | İndeks ile her zaman sabit hızlı ($O(1)$) |
| **Veri Kayması (Drift)**| Yeni kayıt eklenirse satırlar sonraki sayfaya kayar | Veri kayması yaşanmaz, kararlıdır |
| **Sayfaya Atlama** | Sayfa 5'e doğrudan atlayabilir | Yalnızca "Önceki / Sonraki" gezinebilir |
| **Uygun Alanlar** | Yönetim panelleri, numaralı tablolar | Sosyal medya akışları, loglar, sonsuz kaydırma |

### 📦 Genel Zarf Modeli: PagedResponse<T>
```csharp
public sealed record PagedResponse<T>(
    IReadOnlyList<T> Items,
    int PageNumber,
    int PageSize,
    int TotalCount)
{
    public int TotalPages => (int)Math.Ceiling(TotalCount / (double)PageSize);
    public bool HasPrevious => PageNumber > 1;
    public bool HasNext => PageNumber < TotalPages;
}
```

> [!WARNING]
> İstemcinin gönderdiği `pageSize` değerine mutlaka bir üst tavan (örn. `Math.Clamp(pageSize, 1, 50)`) koyun. Sınırsız sayfa boyutu istemciden gelen bir DoS saldırı vektörüdür.

## 16. Filtering, Sorting ve Güvenli Sorgu Parametreleri

### 📌 Değer (Value) vs Sorgu Yapısı (Structure) Güvenliği
- **Filtre Değerleri (`status`, `minPrice`):** Bunlar basit veri değerleridir. EF Core bunları parametreli SQL sorgusuna (`@p0`) çevirir; bu nedenle SQL Injection riski taşımaz.
- **Sıralama Sütunu (`sortBy`):** Kolon isimleri ve sıralama yönü (`ASC/DESC`) SQL parametresi yapılamaz. Kullanıcıdan gelen metni doğrudan SQL'e veya dinamik LINQ'e yapıştırmak **SQL Injection** açığı doğurur.

```csharp
// Güvenli Whitelist (İzin Listesi) Sözlüğü
private static readonly Dictionary<string, Expression<Func<Order, object>>> _sortColumns = new(StringComparer.OrdinalIgnoreCase)
{
    ["createdAt"] = x => x.CreatedAt,
    ["totalAmount"] = x => x.TotalAmount
};
```

### ⚡ Dinamik ve Ertelenmiş Çalışma (Deferred Execution)
`IQueryable` henüz çalıştırılmamış bir SQL ifadesi tarifidir. Filtreler `if` bloklarıyla koşullu eklenir, SQL veritabanında yalnızca `ToListAsync` çağrıldığında yürütülür:

```csharp
IQueryable<Order> query = _dbContext.Orders.AsNoTracking();

if (filter.Status.HasValue)
    query = query.Where(x => x.Status == filter.Status.Value);

if (filter.MinTotal.HasValue)
    query = query.Where(x => x.TotalAmount >= filter.MinTotal.Value);

// Kararlı Sıralama (Deterministic Ordering)
if (_sortColumns.TryGetValue(filter.SortBy ?? "createdAt", out var sortExpr))
{
    query = filter.SortDirection?.ToLower() == "desc" 
        ? query.OrderByDescending(sortExpr).ThenBy(x => x.Id)
        : query.OrderBy(sortExpr).ThenBy(x => x.Id);
}
else
{
    throw new BadHttpRequestException("Geçersiz sıralama alanı!"); // 400 Bad Request
}
```

## 18. Structured Logging, ILogger ve Hassas Veri Güvenliği

### 📌 String Interpolation Tuzağı vs Structured Logging
Metin tabanlı loglarda bir siparişi aramak için regex yazmak gerekir. Yapısal loglamada ise log bir JSON nesnesidir ve alanlarına göre doğrudan indekslenir.

```csharp
// YANLIŞ! (String Interpolation - CA2254 Uyarısı)
// Alan bilgisi kaybolur, her sipariş için bellekte boşuna string üretilir.
_logger.LogInformation($"Order {order.Id} created for {order.CustomerId}");

// DOĞRU! (Message Template & Structured Logging)
// Şablon sabit kalır, parametreler SQL/Elasticsearch içinde aranabilir alan olur.
_logger.LogInformation("Order {OrderId} created for {CustomerId}", order.Id, order.CustomerId);
```

### 🛑 Loglarda PII (Kişisel Veri) Güvenliği
Log dosyaları kalıcıdır, diskte saklanır ve sistem yöneticileri dahil birçok kişi tarafından incelenir.
- **Asla Loglanmayacaklar:** Şifreler, kredi kartı numaraları, JWT token'lar, TC Kimlik numaraları.
- **Doğru Yaklaşım:** Kişinin e-postasını veya adını değil, yalnızca ID'sini (`UserId`) loglayın.
- Production ortamında EF Core'un `EnableSensitiveDataLogging()` ayarını kesinlikle kapalı tutun.

## 19. Correlation ID ve Log Scope ile İstek İzlenebilirliği

### 📌 Dağıtık Sistemlerde İzlenebilirlik
Mikroservis mimarisinde veya çok kullanıcılı bir Web API'de tek bir saniyede yüzlerce log satırı iç içe geçer. Bir kullanıcının aldığı hatayı loglardan bulabilmek için her isteğe kapıda bir takip numarası verilir: **`X-Correlation-ID`**.

```text
İstemci İsteği ──> [CorrelationIdMiddleware]
                          │ (Header varsa al, yoksa Guid v7 üret)
                          ▼
                   logger.BeginScope("CorrelationId", id)
                          │
                          ├──> [Controller Logu: "Sipariş alındı" (Scope: ID-123)]
                          ├──> [Service Logu:    "Stok rezerve edildi" (Scope: ID-123)]
                          └──> [Database Logu:   "Kayıt eklendi" (Scope: ID-123)]
```

### ⚙️ AsyncLocal ve Log Scope Mimarisi
- `logger.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id })` çağrısı, `using` bloğu boyunca alt katmanlarda atılan tüm loglara bu alanı otomatik iliştirir.
- Farklı thread'lerin birbirine karışmamasını sağlayan şey .NET'in **`AsyncLocal<T>`** yapısıdır; asenkron bağlam `await` sıçramalarında da korunur.
- `CorrelationIdMiddleware`, `UseExceptionHandler`'dan daha dışta (en başta) yer almalıdır; aksi halde oluşan bir unhandled exception'da scope kapanır ve hata logu ID'siz kalır.

## 22. Authentication Temelleri ve JWT Bearer Doğrulama

### 📌 Authentication vs Authorization
- **Authentication ("Kimsin?"):** İstemcinin kimliğini kanıtlama sürecidir. Başarısızlık durumunda dönen kod: **`401 Unauthorized`**.
- **Authorization ("Yetkin var mı?"):** Kimliği bilinen kullanıcının istenen eylemi yapmaya izninin olup olmadığıdır. Başarısızlık durumunda dönen kod: **`403 Forbidden`**.

```text
JWT (JSON Web Token) Yapısı:
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NSIsIm5hbWUiOiJGaXJhdCIsInJvbGUiOiJBZG1pbiIsImV4cCI6MTcxOTk5OTk5OX0.4Z8B9...
[       1. HEADER (Algoritma)       ].[              2. PAYLOAD (Claim'ler)              ].[     3. SIGNATURE (İmza)     ]
```

### ⚡ JWT'nin 4 Kritik Doğrulama Kuralı
1. **İmza Şifreleme Değildir:** JWT Payload'u şifreli değildir; sadece **Base64Url** ile kodlanmıştır. Token'ı olan herkes içindeki claim'leri okuyabilir. Bu yüzden token içine şifre veya hassas veri konmaz. İmza yalnızca **bütünlük (integrity)** sağlar; bir claim değiştirilirse gizli anahtarla üretilen imza tutmaz.
2. **ClockSkew:** Varsayılan olarak .NET JWT doğrulayıcısı 5 dakikalık bir saat kayması toleransı (`ClockSkew = TimeSpan.FromMinutes(5)`) uygular. Yani 15 dakikalık bir token gerçekte ~20 dakika geçerlidir.
3. **MapInboundClaims = false:** .NET'in JWT içindeki standart `sub` ve `role` claim'lerini uzun SOAP URI'lerine (`http://schemas.xmlsoap...`) çevirmesini engeller.
4. **FallbackPolicy:** Tüm API'yi tek satırla varsayılan olarak kilitler; yalnızca istenen endpoint'ler `AllowAnonymous()` ile dışarı açılır:

```csharp
builder.Services.AddAuthorization(options =>
{
    options.FallbackPolicy = new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build();
});
```

## 23. Authorization 1: Role-Based ve Claim/Policy-Based Yetkilendirme

### 📌 Rol Tabanlı Yetkilendirmenin Sınırları
`[Authorize(Roles = "Admin,Manager")]` attribute'u kuralın kod içine dağılmasına yol açar. `"Adimn"` gibi yazım hataları derleme zamanında fark edilemez ve rollere dayalı mantık karmaşıklaştıkça yönetilemez hale gelir.

### 🛡️ Modern Policy-Based Yetkilendirme
Kurallar `AddAuthorizationBuilder` içinde isimli kurallar (Policy) olarak tanımlanır:

```csharp
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("RequireAdminRole", p => p.RequireRole("Admin"))
    .AddPolicy("FinanceDepartment", p => p.RequireRole("Manager").RequireClaim("department", "Finance"));

// Endpoint Kullanımı
[Authorize(Policy = "FinanceDepartment")]
[HttpGet("financial-reports")]
public IActionResult GetReports() => Ok();
```

> [!CAUTION]
> **IDOR (Insecure Direct Object Reference) Koruması:** Kullanıcı kimliğini (`UserId`) asla URL'den veya Request Body'den okumayın! İstemcinin gönderdiği ID sahte olabilir. Kullanıcı ID'si daima doğrulanmış JWT içindeki `sub` claim'inden (`User.FindFirstValue(ClaimTypes.NameIdentifier)`) okunmalıdır.

## 24. Authorization 2: Resource-Based Authorization (Kaynak Bazlı Yetki)

### 📌 BOLA ve [Authorize] Yetersizliği
`[Authorize]` attribute'u action çalışmadan önce çalışır; o anda henüz veritabanından veri okunmamıştır. Bu sebeple "Giriş yapmış her kullanıcı sipariş görebilir AMA yalnızca kendi siparişini görebilir" kuralını `[Authorize]` tek başına sağlayamaz.
Saldırganın URL'deki ID'yi değiştirerek başkasının verisine erişmesine **BOLA (Broken Object Level Authorization)** denir ve OWASP API Güvenliği listesinin 1 numaralı tehdididir.

```csharp
// 1. Kural Tanımı (Requirement)
public class SameOwnerRequirement : IAuthorizationRequirement;

// 2. Kuralın İşleyicisi (Handler)
public class OrderAuthorizationHandler : AuthorizationHandler<SameOwnerRequirement, Order>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, SameOwnerRequirement requirement, Order resource)
    {
        var userId = context.User.FindFirstValue(ClaimTypes.NameIdentifier);
        
        // Kullanıcı siparişin sahibiyse veya Admin ise izin ver
        if (resource.CustomerId.ToString() == userId || context.User.IsInRole("Admin"))
        {
            context.Succeed(requirement);
        }
        return Task.CompletedTask;
    }
}
```

```csharp
// 3. Controller İçinde Kullanımı
[HttpGet("{id:guid}")]
public async Task<IActionResult> GetById(Guid id, [FromServices] IAuthorizationService authService)
{
    var order = await _orderService.GetByIdAsync(id);
    if (order is null) return NotFound();

    var authResult = await authService.AuthorizeAsync(User, order, new SameOwnerRequirement());
    if (!authResult.Succeeded)
    {
        // 403 Forbidden dönülür (veya kaynağın varlığını gizlemek için 404 Not Found)
        return Forbid();
    }

    return Ok(order);
}
```

## 25. CORS (Cross-Origin Resource Sharing) ve Browser Güvenliği

### 📌 Origin Nedir ve CORS Ne İşe Yarar?
Origin; **Protokol + Domain + Port** üçlüsüdür. Biri bile farklıysa (`http://localhost:3000` ile `https://localhost:5001`) farklı origin sayılır.
- **Same-Origin Policy (SOP):** Tarayıcının, bir kaynaktan yüklenen JavaScript'in başka bir kaynağın yanıtını okumasını engellemesidir.
- **CORS:** Sunucunun belirli origin'lere izin verdiğini tarayıcıya bildirmesidir (`Access-Control-Allow-Origin`).
- **En Büyük Yanılgı:** CORS bir sunucu güvenlik duvarı **değildir**! CORS tarayıcıdaki kullanıcıyı korur. Saldırgan `curl` veya `Postman` ile API'nize doğrudan istek attığında CORS devrede değildir.

### ⚡ Preflight (OPTIONS) İsteği ve Middleware Sırası
Tarayıcı, JSON gövdesi veya `Authorization` başlığı taşıyan istekleri göndermeden önce sunucuya `OPTIONS` metoduyla bir ön uçuş (**Preflight**) isteği gönderir.
- Bu sebeple `app.UseCors()` middleware'i **`UseRouting`'den sonra ve `UseAuthentication`'dan önce** yer almalıdır! Aksi halde preflight isteği token taşımadığı için kimlik doğrulamaya takılır ve CORS hatası verir.

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("FrontendClient", policy =>
    {
        policy.WithOrigins("https://b2b.orderclient.com")
              .WithMethods("GET", "POST", "PATCH", "DELETE")
              .WithHeaders("Content-Type", "Authorization");
    });
});
```

## 26. Rate Limiting (Hız Sınırlama) ve Kota Yönetimi

### 📌 Neden Rate Limiting?
API'yi brute-force (kaba kuvvet) saldırılarından, scraping botlarından ve kaynakların aşırı tüketilmesinden korur.
- **429 Too Many Requests:** Limit aşıldığında dönülmesi gereken standart durum kodudur (.NET varsayılanı 503 olduğu için `RejectionStatusCode = 429` açıkça ayarlanmalıdır).
- **Partitioning (Bölümleme):** Tüm kullanıcıları tek bir sayaca bağlamak bir kullanıcının herkesi kilitlemesine yol açar. Sayaç **User ID** veya **İstemci IP** bazında bölünmelidir.

### ⚙️ 4 Temel Hız Sınırlama Algoritması
1. **Fixed Window (Sabit Pencere):** Zamanı 1 dakikalık bloklara böler. Basittir ama pencere geçiş anlarında 2 katı istek geçebilir.
2. **Sliding Window (Kayan Pencere):** Pencereyi dilimlere bölerek geçiş anındaki yığılmayı engeller.
3. **Token Bucket (Jeton Kovası):** Kova sabit hızla dolar. Ani istek patlamalarına (burst) izin verirken uzun vadedeki hızı sınırlar. Gerçek kullanıcılar için en ideal modeldir.
4. **Concurrency Limiter:** Zamana değil, o anda aynı anda işlenen aktif istek sayısına sınır koyar (örn. Ağır raporlama endpoint'leri).
