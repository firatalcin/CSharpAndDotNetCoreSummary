### S1. HTTP request ve response yapısında hangi temel parçalar bulunur?

HTTP mesajları istemci ve sunucu arasındaki iletişimi sağlayan metin tabanlı paketlerdir. Bir **HTTP Request**, sunucuya eylemi bildiren **Start Line (Request Line)** ile başlar; bu satırda HTTP metodu (`GET`, `POST`), hedeflenen adres yolu (`/api/v1/orders`) ve protokol sürümü (`HTTP/1.1`) yer alır. Ardından istemci ve mesaj hakkında metaveri taşıyan **Headers** (örn: `Host`, `Authorization`, `Content-Type`), başlıkların bittiğini gösteren zorunlu bir **boş satır (CRLF)** ve en altta oluşturulacak veya işlenecek veriyi taşıyan **Body (Payload)** bölümü bulunur (`GET` isteklerinde gövde çoğunlukla boştur).

Bir **HTTP Response** ise ilk satırında protokol sürümü, işlem sonucunu özetleyen 3 haneli durum kodu ve kısa açıklamasını barındıran **Status Line** (`HTTP/1.1 201 Created`) ile açılır. Hemen altında sunucu ve yanıt özelliklerini belirten **Headers** (`Content-Type`, `Location`, `Date`), bir **boş satır** ve istemciye dönen asıl içeriğin yer aldığı **Body** bloğu yer alır.

```http
--> HTTP REQUEST ÖRNEĞİ
POST /api/v1/orders HTTP/1.1
Host: api.magaza.com
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json

{"productId": 101, "quantity": 2}

<-- HTTP RESPONSE ÖRNEĞİ
HTTP/1.1 201 Created
Location: /api/v1/orders/5501
Content-Type: application/json

{"id": 5501, "totalAmount": 250.00, "status": "Pending"}
```

> [!NOTE]
> **Özet:** Request ve Response iskeleti simetriktir: `Başlangıç Satırı + Header'lar + Boş Satır + Body`. Tek fark; request'in metot ve path ile, response'un ise status code ile başlamasıdır.

### S2. GET, POST, PUT, PATCH ve DELETE metodlarının temel farkları nelerdir?

Bu metotlar istemcinin sunucuya niyetini bildiren fiillerdir ve iki kritik kavramla ayrışırlar: **Safety (Güvenlik)** ve **Idempotency (Eşgüçlülük)**. `GET`, yalnızca veri okumak için kullanılır; hem safe'tir (sunucu durumunu değiştirmez) hem de idempotent'tir. `POST`, sunucuda yeni bir alt kaynak yaratmak veya bir iş sürecini tetiklemek için kullanılır; ne safe ne de idempotent'tir, her çağrıldığında yeni bir kayıt veya yan etki üretebilir.

`PUT`, istemcinin belirttiği URI'daki kaynağın tamamını verilen gövde ile değiştirmesini (veya yoksa sıfırdan o adreste oluşturmasını) sağlar; safe değildir ancak **idempotent**'tir (aynı PUT isteği 10 kez de atılsa sunucudaki son durum aynı kalır). `PATCH`, kaynağın sadece belirli alanlarını kısmi güncellemek içindir; idempotent garantisi bulunmaz. `DELETE` ise belirtilen adresteki kaynağı siler; safe değildir ama **idempotent**'tir, çünkü silinmiş bir kaynağı tekrar silmeye çalışmak sunucudaki nihai durumu değiştirmez (kaynak yine yoktur).

```text
┌─────────┬──────────────────────┬──────────┬──────────────┬────────────────────────────┐
│ Metot   │ İşlev                │ Safe mi? │ Idempotent?  │ Tipik Başarılı Yanıt       │
├─────────┼──────────────────────┼──────────┼──────────────┼────────────────────────────┤
│ GET     │ Kaynak okuma         │ EVET     │ EVET         │ 200 OK                     │
│ POST    │ Yeni kaynak üretme   │ HAYIR    │ HAYIR        │ 201 Created (+ Location)   │
│ PUT     │ Tam güncelleme       │ HAYIR    │ EVET         │ 200 OK / 204 No Content    │
│ PATCH   │ Kısmi güncelleme     │ HAYIR    │ GARANTİ YOK  │ 200 OK / 204 No Content    │
│ DELETE  │ Kaynak silme         │ HAYIR    │ EVET         │ 200 OK / 204 No Content    │
└─────────┴──────────────────────┴──────────┴──────────────┴────────────────────────────┘
```

> [!TIP]
> **Örnek:** `PUT /api/users/5` tüm kullanıcı profilini gönderilen JSON ile ezerken, `PATCH /api/users/5` gövdesinde sadece `{"email": "yeni@mail.com"}` göndererek tek bir alanı günceller.

### S3. 200, 201, 204, 400, 401, 403, 404, 409 ve 500 status code’ları hangi durumlarda kullanılır?

HTTP durum kodları, sunucunun istemciye verdiği standart sonuç özetleridir. İlk rakam genel aileyi (2xx: Başarı, 4xx: İstemci Hatası, 5xx: Sunucu Hatası) belirtir:
- **`200 OK`:** İstek başarıyla tamamlandı ve yanıt gövdesinde veri dönüyor (örn: `GET /orders` listesi).
- **`201 Created`:** Yeni bir kaynak oluşturuldu; yanıt gövdesinde yeni nesne, `Location` header'ında ise ona erişilecek URL yer alır (`POST /orders`).
- **`204 No Content`:** İşlem başarılı oldu ancak istemciye dönecek bir gövde yok (örn: başarılı bir `DELETE` işlemi).
- **`400 Bad Request`:** İstemcinin isteği sözdizimsel olarak hatalı veya geçersiz (bozuk JSON, string beklenen yere dizi gönderme).
- **`401 Unauthorized`:** Kimlik doğrulanmadı ("Kim olduğunu bilmiyorum"; token eksik veya geçersiz).
- **`403 Forbidden`:** Kimlik doğrulandı ancak o kaynağa erişim yetkisi yok ("Seni tanıyorum ama buraya giremezsin").
- **`404 Not Found`:** İstenen URI'da herhangi bir kaynak bulunamadı (`/orders/99999`).
- **`409 Conflict`:** İstek geçerli olsa da sunucudaki mevcut durumla çakışıyor (örn: veritabanında zaten kayıtlı bir T.C. Kimlik / SKU ile ekleme yapmaya çalışmak veya kargoya verilmiş siparişi iptal etmeyi denemek).
- **`500 Internal Server Error`:** Sunucu tarafında beklenmeyen, yakalanmamış sistemsel istisna (asla validasyon hatası için kullanılmaz ve canlıda stack trace içermez).

> [!NOTE]
> **Mülakat Klasiği:** `401` ile `403` arasındaki fark kimlik (authentication) ile yetki (authorization) ayrımıdır. Token yoksa $\to$ `401`; normal kullanıcı token'ı ile admin paneline gidilirse $\to$ `403`.

### S4. REST API’de resource kavramı ne anlama gelir?

REST (Representational State Transfer) mimarisinde **Resource (Kaynak)**, bir URI (Uniform Resource Identifier) üzerinden tekil olarak adreslenebilen, üzerinde durum takibi ve CRUD işlemleri yapılabilen her türlü kavramsal varlıktır. Bir kaynak fiziksel bir veritabanı kaydı (`Product`, `Order`), mantıksal bir koleksiyon (`Orders`) veya soyut bir işlem/süreç (`Loan`, `Payment`, `Cancellation`) olabilir.

RESTful tasarımda kaynaklar daima **isim (noun)** ile ve çoğul olarak adlandırılır; eylemler ise URI'ya değil HTTP metodlarına bırakılır. Örneğin kitap ödünç verme senaryosunda RPC tarzı `POST /lendBook?bookId=7` yaklaşımı yerine, ödünç alma eylemi bağımsız bir kaynak kabul edilerek `POST /api/v1/loans` şeklinde modellenir.

```text
RPC Tarzı (Anti-Pattern):
POST /api/createOrder
POST /api/cancelOrder?id=5

RESTful Kaynak Modellemesi:
POST   /api/v1/orders          ──> Yeni sipariş kaynağı oluştur
GET    /api/v1/orders/5        ──> 5 numaralı sipariş kaynağını getir
DELETE /api/v1/orders/5        ──> 5 numaralı sipariş kaynağını sil / iptal et
GET    /api/v1/customers/3/orders ──> 3 numaralı müşterinin siparişleri (Hiyerarşi)
```

> [!TIP]
> **Zihinsel Model:** URI "hangi kaynak üzerinde çalıştığınızı" (isim), HTTP Fiili ise o kaynak üzerinde "ne yaptığınızı" (eylem) belirtir.

### S5. Idempotency nedir? PUT ve POST arasındaki farkı idempotency üzerinden açıkla.

**Idempotency (Eşgüçlülük)**; bir HTTP isteğinin sunucuya bir kez veya art arda birden çok kez gönderilmesinin, sunucunun nihai veri durumunda (state) tamamen aynı sonucu bırakması özelliğidir. Ağın koptuğu, istemcinin zaman aşımına (timeout) uğradığı senaryolarda isteğin güvenle yeniden gönderilip (retry) gönderilemeyeceğini belirler.

`PUT` doğası gereği **idempotent**'tir; çünkü `PUT /api/orders/7c9e` isteği o adresteki sipariş verisini gönderilen gövde ile bütünüyle günceller veya o ID ile oluşturur. İstemci cevabı alamayıp aynı isteği 5 kez tekrarlasa bile veritabanında aynı veriye sahip tek bir sipariş kalır (ilk çağrı 201, sonrakiler 200 dönebilir ama veritabanı durumu aynıdır). Buna karşın `POST /api/orders` **idempotent değildir**; çünkü her çağrıda sunucu yeni bir ID üretip yeni bir kayıt oluşturur ve 5 tekrar 5 farklı sipariş yaratır. Bu yüzden POST işlemlerinde eşgüçlülük sağlamak için gövdeye veya başlığa istemci tarafından üretilen tekil bir `Idempotency-Key` iliştirilir.

```text
PUT Akışı (İdempotent):
İstemci ──(PUT /orders/10)──> Sunucu [Sipariş 10 güncellendi]
İstemci ──(PUT /orders/10)──> Sunucu [Sipariş 10 tekrar aynı veriyle güncellendi] (Nihai Durum: 1 Kayıt)

POST Akışı (Non-İdempotent):
İstemci ──(POST /orders)───> Sunucu [Sipariş #101 oluşturuldu]
İstemci ──(POST /orders)───> Sunucu [Sipariş #102 oluşturuldu!] (Nihai Durum: Çift Sipariş Hatası!)
```

### S6. ASP.NET Core’da Program.cs dosyasının görevi nedir?

`Program.cs`, bir ASP.NET Core uygulamasının giriş noktası (entry point) olup uygulamanın yaşam döngüsünü başlatan, yapılandıran ve çalıştıran ana orkestrasyon merkezidir. Modern .NET sürümlerinde bu süreç iki temel aşamadan oluşur: **Builder Aşaması** ve **App Aşaması**.

Builder aşaması (`WebApplication.CreateBuilder(args)`) ile Kestrel sunucusu hazırlanır, konfigürasyon dosyaları (`appsettings.json`, ortam değişkenleri) sırayla taranır, loglama altyapısı ve Dependency Injection konteyneri (`builder.Services`) kurulur. `builder.Build()` çağrısı bu listenin kilit sınırıdır; buradan sonra `app.Use...` metotlarıyla gelen HTTP isteklerinin geçeceği **Middleware Boru Hattı (Request Pipeline)** ve `app.Map...` ile rotalar (endpoints) tanımlanır. En sonda yer alan `app.Run()` ise Kestrel'i başlatarak gelen soket bağlantılarını dinlemeye alır.

```csharp
var builder = WebApplication.CreateBuilder(args);

// 1. AŞAMA: Servislerin ve Bağımlılıkların Kaydı (DI)
builder.Services.AddControllers();
builder.Services.AddScoped<IOrderService, OrderService>();

var app = builder.Build(); // <-- Kilit Noktası: Servis listesi kilitlenir

// 2. AŞAMA: İstek İşleme Boru Hattı (Middleware Pipeline)
if (app.Environment.IsDevelopment())
{
    app.UseSwaggerUI();
}
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run(); // <-- Kestrel dinlemeye başlar
```

> [!NOTE]
> Eski sürümlerdeki `Startup.cs` içindeki `ConfigureServices` metodu bugünkü Builder aşamasına, `Configure` metodu ise App aşamasına karşılık gelir.

### S7. Kestrel nedir?

**Kestrel**; ASP.NET Core uygulamaları için varsayılan olarak gelen, doğrudan uygulama süreci içinde (in-process) çalışan, açık kaynaklı, platformlar arası (Windows, Linux, macOS), son derece hafif ve asenkron I/O tabanlı yüksek performanslı web sunucusudur.

Kestrel'in birincil görevi; işletim sisteminin ağ soketlerini (TCP/IP) dinlemek, ağdan gelen ham byte akışlarını okuyarak HTTP sözdizimine göre ayrıştırmak, her istek için bir `HttpContext` nesnesi oluşturup bunu ASP.NET Core middleware boru hattına iletmek ve pipeline'ın ürettiği yanıtı soket üzerinden istemciye geri yazmaktır. Kestrel tek başına doğrudan internete açılabildiği gibi, kurumsal üretim (production) ortamlarında genellikle önünde IIS, Nginx veya Cloudflare gibi bir **Reverse Proxy** konumlandırılarak SSL sonlandırma, statik dosya önbellekleme ve saldırı filtreleme (WAF) görevleri paylaşılır.

```text
İnternet / İstemci  ──>  [ Reverse Proxy (Nginx / IIS) ]  ──>  [ Kestrel Web Server ]  ──>  [ HttpContext & Pipeline ]
```

### S8. Middleware nedir? Middleware sırası neden önemlidir?

**Middleware**; bir HTTP isteği uygulamaya ulaştığında controller'a varmadan önce ve controller bir yanıt ürettikten sonra istemciye dönerken devreye giren, her isteği sırayla işleyen boru hattı (request pipeline) bileşenleridir. Loglama, kimlik doğrulama, CORS denetimi ve merkezi hata yakalama gibi tüm endpoint'leri ilgilendiren çapraz kesen konular (cross-cutting concerns) middleware'ler ile merkezi olarak çözülür.

Middleware sıralaması hayatidir; çünkü pipeline **çift yönlü bir matruşka zinciri** gibi çalışır ve her middleware yalnızca kendisinden sonra gelen bileşenlerin davranışını ve hatalarını kontrol edebilir. Örneğin `UseExceptionHandler` en dışta (en başta) yer almalıdır ki tüm pipeline'da çıkabilecek istisnaları yakalayabilsin. Aynı şekilde `UseAuthentication` (Kimsin?) mutlaka `UseAuthorization` (Yetkin var mı?) çağrısından önce gelmelidir; sıra ters yazılırsa framework kullanıcının kim olduğunu bilmeden yetkisini sorgular ve geçerli token taşıyan istekler dahi haksız yere `401/403` hatası alır.

```text
Gelen İstek  ──> [ ExceptionHandler ] ──> [ Routing ] ──> [ CORS ] ──> [ Authentication ] ──> [ Authorization ] ──> [ Controller Action ]
                                                                                                                           │
Dönen Yanıt <── [ ExceptionHandler ] <── [ Routing ] <── [ CORS ] <── [ Authentication ] <── [ Authorization ] <───────────┘
```

### S9. Custom middleware hangi durumlarda yazılır?

Custom middleware; uygulamanın tamamına veya belirli rota kalıplarına giren tüm HTTP isteklerine uygulanması gereken, MVC katmanından (controller/action) bağımsız küresel altyapı ihtiyaçlarında yazılır. İş kurallarını controller action'larına tek tek kopyalamak yerine tek bir noktada toplar.

En yaygın yazılma senaryoları şunlardır:
1. **İzlenebilirlik (Correlation ID):** Gelen istekteki `X-Correlation-ID` başlığını okuyup yoksa yenisini üreterek tüm log scope'una ve giden yanıta iliştirmek.
2. **Performans Takibi:** Gelen her isteğin çalışma süresini bir kronometre (`Stopwatch`) ile ölçüp, belirlenen eşik değerini (örn: 500 ms) aşan yavaş istekleri loglamak.
3. **Güvenlik ve Denetim (Audit Log):** `POST`, `PUT`, `DELETE` gibi veri değiştiren isteklerin kim tarafından ne zaman yapıldığını merkezi olarak denetim tablosuna kaydetmek.
4. **Kısa Devre (Short-Circuit):** Sistem bakımdayken veya belirli IP bloklarından gelen istekleri controller'a hiç sokmadan anında `503 Service Unavailable` ile reddetmek.

```csharp
public class PerformanceMiddleware(RequestDelegate next, ILogger<PerformanceMiddleware> logger)
{
    public async Task InvokeAsync(HttpContext context)
    {
        var sw = Stopwatch.StartNew();
        await next(context); // İsteği sonraki middleware'e aktar
        sw.Stop();

        if (sw.ElapsedMilliseconds > 500)
            logger.LogWarning("Yavaş İstek: {Path} ({Elapsed} ms)", context.Request.Path, sw.ElapsedMilliseconds);
    }
}
```

### S10. Controller, action ve route kavramlarını açıklayın.

- **Controller:** İlgili HTTP isteklerini mantıksal bir kümede toplayan, `ControllerBase` sınıfından türeyen ve uygulamanın dış dünyayla konuşan API arayüzünü oluşturan C# sınıfıdır.
- **Action:** Controller sınıfı içerisinde yer alan, belirli bir HTTP fiiline (GET, POST vb.) yanıt veren, gelen isteği işleyip geriye `IActionResult` veya `ActionResult<T>` dönen public metotlardır.
- **Route (Rota):** Gelen HTTP isteğinin URL yolu ile HTTP fiilinin eşleşerek hangi Controller ve hangi Action metodunun çalıştırılacağını belirleyen adres şablonudur.

```csharp
[ApiController]
[Route("api/[controller]")] // Route Şablonu: Sınıf adından "OrdersController" -> "/api/orders" üretir
public class OrdersController : ControllerBase // Controller
{
    [HttpGet("{id:guid}")] // Route Şablonu + HTTP Fiili: "/api/orders/{id}"
    public ActionResult<OrderResponse> GetById(Guid id) // Action Metodu
    {
        // ...
        return Ok(response);
    }
}
```

> [!TIP]
> **Hiyerarşi:** `Controller` binadır, `Action` binanın içindeki belirli bir işle ilgilenen ofistir, `Route` ise müşterinin o ofise ulaşmak için takip ettiği adrestir.

### S11. [FromBody], [FromRoute], [FromQuery] ve [FromHeader] farkları nelerdir?

Model binding, HTTP isteğindeki ham verileri action parametrelerine dönüştüren mekanizmadır. Bu öznitelikler (attributes) verinin isteğin hangi bölümünden okunacağını açıkça bildirir:
- **`[FromRoute]`:** Değeri doğrudan URL path şablonundan çeker (`/api/orders/{id}` $\to$ `[FromRoute] int id`).
- **`[FromQuery]`:** Değeri URL sonundaki soru işaretinden sonra gelen sorgu dizesinden okur (`/api/orders?page=2&status=Active`).
- **`[FromBody]`:** Değeri HTTP Request Body'sinden JSON/XML olarak okuyup C# nesnesine dönüştürür. HTTP body bir ağ akışı (**stream**) olduğu ve kural olarak yalnızca bir kez okunabildiği için, bir action metodunda **yalnızca bir adet `[FromBody]`** parametresi bulunabilir.
- **`[FromHeader]`:** Değeri gelen HTTP başlıklarından okur (`[FromHeader(Name = "X-Tenant-Id")] string tenantId`). `[ApiController]` route, query ve body kaynaklarını otomatik tahmin edebilirken; header'ları asla otomatik tahmin etmez, daima açıkça yazılmalıdır.

```csharp
[HttpGet("{customerId:int}/orders")]
public IActionResult GetCustomerOrders(
    [FromRoute] int customerId,
    [FromQuery] OrderFilterParameters filter,
    [FromHeader(Name = "X-Tenant-Id")] string tenantId)
{
    // customerId: URL path'inden
    // filter: URL query string'inden (?status=Pending&pageSize=10)
    // tenantId: HTTP Request Header'ından okunur
    return Ok();
}
```

### S12. Entity modellerini doğrudan API response olarak dönmek neden risklidir?

Entity modelleri doğrudan veritabanı tablolarını temsil eden iç dünya nesneleridir. Bunları doğrudan API yanıtı olarak dışarıya açmak 4 büyük risk doğurur:
1. **Hassas Veri Sızıntısı:** `User` tablosundaki `PasswordHash`, `TwoFactorSecretKey`, `SecurityStamp` veya şirket içi notlar istemciye JSON olarak iletilir (OWASP API3: BOPLA).
2. **Döngüsel Referans (Circular Reference) Çökmesi:** İlişkisel tablolarda (`Order` $\rightarrow$ `OrderItems` $\rightarrow$ `Order`) navigation property'ler JSON serializer'ı sonsuz döngüye sokarak uygulamanın `JsonException` ile çökmesine sebep olur.
3. **Kırılgan Sözleşme (Breaking Changes):** Veritabanında bir tablonun kolon adı değiştiğinde veya yeni bir kolon eklendiğinde, API'yi kullanan tüm mobil ve web istemcilerinin modelleri bozulur.
4. **Aşırı Veri Aktarımı (Over-fetching):** Yalnızca ürün adı ve fiyatı gerekirken ürünün tüm stok hareketlerinin ve tedarikçi bilgilerinin ağdan istemciye aktarılması bant genişliğini ve sunucu belleğini gereksiz yere tüketir.

> [!NOTE]
> **Çözüm:** Dış dünyaya asla veritabanı modelleri açılmamalı; yalnızca istemcinin bilmesi gereken alanları içeren amaca özel **Response DTO**'lar dönülmelidir.

### S13. DTO nedir? Request DTO ve Response DTO neden ayrı olabilir?

**DTO (Data Transfer Object)**; üzerinde herhangi bir iş mantığı barındırmayan, yalnızca katmanlar arasında veya ağ üzerinde veri taşımak amacıyla kullanılan hafif veri transfer nesneleridir (modern C#'ta genellikle değişmez `record` tipleriyle yazılır).

Request DTO ve Response DTO'nun ayrı olmasının temel sebebi, istemcinin sunucuya **sağladığı veri** ile sunucunun istemciye **sunduğu verinin** gereksinim ve güvenlik sınırlarının birbirinden tamamen farklı olmasıdır:
- Sipariş oluşturma isteğinde (`CreateOrderRequest`) istemci yalnızca `ProductId` ve `Quantity` gönderir; `Id`, `OrderNumber`, `CreatedAt`, `TotalAmount` veya `Status` gönderemez çünkü bu alanları sunucu iş kurallarına göre kendisi belirler.
- Sipariş sorgulama yanıtında (`OrderResponse`) ise istemcinin gönderdiği verilerin yanı sıra sunucunun ürettiği `Id`, hesaplanan `TotalAmount`, kargo durumu ve sipariş tarihi eksiksiz olarak dönülür. Modelleri ayırmak hem istemciye gönderilmemesi gereken verileri korur hem de API sözleşmesini netleştirir.

```csharp
// İstemcinin gönderdiği (Request DTO)
public sealed record CreateOrderRequest(
    Guid CustomerId,
    List<OrderItemDto> Items
);

// İstemcinin aldığı (Response DTO)
public sealed record OrderResponse(
    Guid Id,
    Guid CustomerId,
    string Status,
    decimal TotalAmount,
    DateTime CreatedAt
);
```

### S14. Validation neden sadece frontend’e bırakılmamalıdır?

Frontend (JavaScript, mobil UI vb.) tarafında yapılan form doğrulamaları yalnızca **kullanıcı deneyimini (UX)** iyileştirmek, kullanıcıya anında geri bildirim sunmak ve sunucuya gereksiz geçersiz istek gitmesini önlemek içindir; ancak **kesinlikle bir güvenlik mekanizması değildir**.

Kötü niyetli bir kullanıcı veya saldırgan; tarayıcı arayüzünü tamamen devre dışı bırakarak cURL, Postman veya Python script'leri ile doğrudan API endpoint'lerinize istek atabilir veya araya girme araçlarıyla (Burp Suite, Fiddler) giden HTTP paketindeki verileri dilediği gibi tahrif edebilir. Eğer backend tarafında sıkı bir doğrulama bulunmazsa; negatif adetli ürün siparişi (`Quantity: -5`), eksi fiyatlı sipariş veya SQL Injection dizgeleri doğrudan iş mantığına ve veritabanına ulaşır. Bu yüzden **"İstemciden gelen hiçbir veriye güvenilmez"** ilkesi gereği backend doğrulaması zorunludur.

```text
Tarayıcı / Mobil UI (UX Katmanı) ──(Postman / cURL ile Baypas Edilebilir!)──┐
                                                                            │
                                                                            ▼
                                                [ Backend API Doğrulaması (Güvenlik Katmanı) ]
                                                                            │ (Geçerli)
                                                                            ▼
                                                                [ Veritabanı ve İş Mantığı ]
```

### S15. DataAnnotations ve FluentValidation arasındaki temel fark nedir?

**DataAnnotations**; doğrulama kurallarını (`[Required]`, `[Range]`, `[EmailAddress]`) doğrudan DTO sınıfının özellikleri (properties) üzerine C# attribute'ları olarak yazar. Basit kurallarda hızlıdır; ancak kurallar karmaşıklaştıkça DTO sınıfını kirletir, Single Responsibility Principle'ı (SRP) çiğner, koşullu kuralları (`When`) yönetmekte zorlanır ve kuralların bağımsız olarak birim testine (unit test) tabi tutulmasını zorlaştırır.

**FluentValidation** ise kuralları DTO'dan tamamen soyutlayarak `AbstractValidator<T>` sınıfından türeyen bağımsız sınıflara taşır. Kurallar akıcı bir API (`RuleFor(x => x.Price).GreaterThan(0)`) ile yazılır; Dependency Injection ile harici servisleri constructor'dan alabilir, koleksiyon elemanlarını (`RuleForEach`) zahmetsizce doğrular ve HTTP pipeline'ına ihtiyaç duymadan doğrudan `validator.TestValidate(dto)` ile çok hızlı test edilebilir.

```csharp
// DataAnnotations: DTO kirlenir, karmaşık kurallar yazılamaz
public class UserDto
{
    [Required, EmailAddress]
    public string Email { get; set; } = string.Empty;
}

// FluentValidation: DTO temiz kalır, kurallar izole ve esnektir
public class UserDtoValidator : AbstractValidator<UserDto>
{
    public UserDtoValidator()
    {
        RuleFor(x => x.Email)
            .NotEmpty().WithMessage("E-posta boş olamaz.")
            .EmailAddress().WithMessage("Geçersiz e-posta formatı.");
    }
}
```

## Modül 4: Error Handling, Security ve API Quality

### S16. Global exception handling neden gereklidir?

Controller ve servis metotlarının her birini ayrı ayrı `try-catch` bloklarıyla sarmak; ciddi bir kod kirliliğine, geliştiriciler arasında tutarsız hata formatlarına ve yakalanmayan bir hatada uygulamanın çökmesine yol açar. Daha da tehlikelisi; acemi `catch` bloklarının `ex.ToString()` ile veritabanı bağlantı cümleleri, SQL sorguları, dosya yolları ve metod çağrı hiyerarşisini içeren **Stack Trace** bilgilerini istemciye açık metin olarak dönmesi, saldırganlara sistem mimarisini ifşa eden kritik bir güvenlik zafiyetidir.

Global exception handling (merkezi hata yönetimi); uygulamanın en dış çeperine yerleşen merkezi bir mekanizma (modern .NET'te `IExceptionHandler` arayüzü) ile tüm pipeline'ı dev bir try-catch gibi sarar. Controller'lar yalnızca "mutlu yolu" (happy path) kodlar; beklenmeyen bir istisna fırlatıldığında merkezi yönetici araya girer, hatanın tam teknik detayını stack trace ile birlikte güvenli log sunucusuna yazar, istemciye ise iç yapıyı gizleyen sade, standart bir hata yanıtı (`ProblemDetails`) ve loglarla eşleşen bir `traceId` döner.

```text
Action ──(Hata Fırlatır)──> [ Pipeline Yukarı Tırmanış ] ──> [ IExceptionHandler ]
                                                                     │
                                    ┌────────────────────────────────┴────────────────────────────────┐
                                    ▼                                                                 ▼
                     [ Güvenli Log Sunucusu ]                                            [ İstemciye Dönen Yanıt ]
             (Stack Trace + SQL + Tüm Detaylar)                                  (Status: 500, Sade Mesaj, TraceId: #019)
```

### S17. ProblemDetails nedir? Standart hata response’u neden önemlidir?

**ProblemDetails**; HTTP tabanlı API'lerde meydana gelen hataları insan ve makine tarafından kolayca anlaşılabilecek ortak bir sözlükle tarif etmek için IETF tarafından yayınlanan resmi bir endüstri standardıdır (RFC 7807 ve güncellenmiş RFC 9457). Standart bir ProblemDetails nesnesi `type` (hata türü URI'si), `title` (kısa başlık), `status` (HTTP durum kodu), `detail` (olaya özel açıklama), `instance` (hatanın oluştuğu request URI) ve `traceId` (izleme kimliği) alanlarını barındırır.

Standart hata formatı olmadığında bir endpoint `{"error": "Hata"}`, diğeri `{"message": "Geçersiz", "code": 102}` gibi rastgele yapılar döner; bu durum frontend ve mobil geliştiricilerin her istek için ayrı ayrı hata yakalama ve ayrıştırma (parsing) mantığı yazmasına sebep olur. Standart ProblemDetails sayesinde tüm istemci uygulamaları tek bir jenerik hata işleyicisi (global error handler) yazarak hataları tutarlı şekilde ekrana yansıtabilir ve kullanıcı elindeki `traceId` ile destek ekibine başvurduğunda sorun loglarda saniyeler içinde bulunur.

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title": "Sipariş Bulunamadı",
  "status": 404,
  "detail": "8a7c-412e ID'li sipariş sistemde kayıtlı değildir.",
  "instance": "/api/v1/orders/8a7c-412e",
  "traceId": "00-9f8a3c2b1a-4c2e"
}
```

### S18. CORS nedir? Her origin’e izin vermek neden risklidir?

**CORS (Cross-Origin Resource Sharing)**; tarayıcıların varsayılan olarak uyguladığı Same-Origin Policy (SOP - Aynı Köken İlkesi) kısıtlamasını kontrollü bir biçimde esneten HTTP başlıkları (`Access-Control-Allow-Origin`) tabanlı bir mekanizmadır. Bir sayfanın kökeni (Origin); **Protokol + Domain + Port** üçlüsüdür. Tarayıcı, bir sitedeki JavaScript kodunun farklı bir origin'den gelen API cevabını okumasını varsayılan olarak engeller; CORS sunucunun tarayıcıya "Şu origin'lerin bu yanıtı okumasına izin veriyorum" demesini sağlar.

`AllowAnyOrigin()` (`*`) kullanarak her origin'e izin vermek, internet üzerindeki herhangi bir zararlı web sitesinin kullanıcının tarayıcısı üzerinden sizin API'nizle konuşup dönen yanıtları serbestçe okuyabilmesi anlamına gelir. Eğer API kurum içi yerel ağda (intranet) çalışıyorsa veya kimlik doğrulaması oturum cookie'leri/özel mekanizmalarla sağlanıyorsa; kullanıcının tıkladığı kötü niyetli bir web sitesi, kullanıcının tarayıcısını bir atlama tahtası gibi kullanarak kurum içi hassas API verilerini kendi sunucusuna sızdırabilir. CORS sunucuyu değil, tarayıcıdaki kullanıcıyı korur.

```text
Güvenli Senaryo:
API Tanımı: WithOrigins("https://portal.magazam.com")
Kullanıcı portal.magazam.com'da iken  ──> API yanıtı okunabilir (İZİN VERİLDİ).
Kullanıcı zararlisite.com'da iken      ──> Tarayıcı yanıtı okutmaz (BLOKLANDI).
```

### S19. Authentication ile Authorization arasındaki fark nedir? 401 ve 403 farkını da açıklayın.

- **Authentication (Kimlik Doğrulama):** Sisteme gelen isteğin arkasındaki aktörün "Kim olduğunu" tespit etme ve kanıtlama sürecidir (örn: Kullanıcının JWT Bearer token sunması veya API Key iletmesi).
- **Authorization (Yetkilendirme):** Kimliği doğrulanmış olan kullanıcının, talep ettiği kaynağa erişmeye veya işlemi gerçekleştirmeye "Hakkı/İzni olup olmadığını" denetleme sürecidir (Rol, Policy veya Kaynak Sahipliği kontrolleri).

Bu iki kavram HTTP durum kodlarına şu şekilde yansır:
- **`401 Unauthorized`:** İstekte kimlik bilgisi hiç yoktur veya geçersizdir ("Seni tanımıyorum, önce kimliğini doğrula"). Örneğin token göndermeden korumalı bir endpoint'e çağrı yapıldığında döner.
- **`403 Forbidden`:** Kullanıcının kimliği başarıyla doğrulanmıştır ancak o işlemi yapmaya yetkisi yetersizdir ("Seni tanıdım, sen Müşteri 'Ahmet'sin; ancak bu işlem sadece 'Admin' rolüne açıktır").

```text
İstek Geldi
   │
   ▼
[ Authentication ] ──(Token Yok / Geçersiz)──> 401 Unauthorized ("Kimsin?")
   │ (Kimlik Doğrulandı: Kullanıcı = Mehmet)
   ▼
[ Authorization ]  ──(Yetki Yetersiz: Rolü User, Endpoint Admin İstiyor)──> 403 Forbidden ("Giremezsin!")
   │ (Yetki Var)
   ▼
[ 200 OK - İşlem Başarılı ]
```

### S20. Overposting / mass assignment saldırısı nedir? ASP.NET Core API’de nasıl önlenir?

**Overposting (veya Mass Assignment)**; istemcinin, bir oluşturma veya güncelleme isteği gönderirken sunucuya göndermesi beklenmeyen ya da yetkisi dışındaki ek veri alanlarını HTTP Request Body'sine (JSON) gizlice eklemesi ve sunucu tarafındaki model bağlayıcının (model binder) bu alanları da otomatik olarak hedef nesneye eşleyerek veritabanına kaydetmesiyle oluşan kritik bir zafiyettir (OWASP API3: BOPLA).

Örneğin kullanıcının yalnızca adını ve telefonunu güncellemesini bekleyen bir action metodunda, parametre olarak doğrudan veritabanı `User` entity'si alınırsa; saldırgan JSON içerisine `"isAdmin": true` veya `"accountBalance": 100000` ekler. Model binder reflection ile bu alanları entity üzerindeki setter'lara yazar ve saldırgan yetkisini admin seviyesine yükseltir.

ASP.NET Core API'de bu saldırıyı önlemenin en kesin ve kurumsal yolu **DTO (Data Transfer Object) ile Beyaz Liste (Whitelist) yaklaşımıdır**:
1. Action metotlarında **kesinlikle entity modelleri parametre olarak kabul edilmemelidir**.
2. Yalnızca istemcinin değiştirmesine izin verilen alanları barındıran katı DTO sınıfları (`UpdateUserProfileRequest`) tanımlanmalıdır.
3. DTO'dan Entity'ye aktarım yapılırken yalnızca izin verilen alanlar kontrollü olarak eşitlenmelidir (`user.PhoneNumber = request.PhoneNumber`). Saldırgan JSON'a `isAdmin` eklese dahi DTO'da bu alan tanımlı olmadığı için serializer tarafından tamamen yok sayılır.

```csharp
// GÜVENSİZ KOD (Overposting Açığı!):
[HttpPut("{id}")]
public async Task<IActionResult> UpdateUser(int id, [FromBody] User user) // Entity doğrudan alınıyor!
{
    _db.Update(user); // Saldırganın JSON'a eklediği "IsAdmin: true" veritabanına yazılır!
    await _db.SaveChangesAsync();
    return NoContent();
}

// GÜVENLİ KOD (DTO ile Beyaz Liste Yaklaşımı):
public sealed record UpdateUserRequest(string FullName, string PhoneNumber); // IsAdmin alanı YOK!

[HttpPut("{id}")]
public async Task<IActionResult> UpdateUser(int id, [FromBody] UpdateUserRequest request)
{
    var user = await _db.Users.FindAsync(id);
    if (user is null) return NotFound();

    user.FullName = request.FullName;
    user.PhoneNumber = request.PhoneNumber; // Yalnızca izinli alanlar güncellenir

    await _db.SaveChangesAsync();
    return NoContent();
}
```

> **Sertifika Değerlendirme Özeti:** RESTful API tasarımında başarı; HTTP protokol standartlarına saygı göstermek, dış dünya sözleşmesini (DTO) iç veri modellerinden (Entity) kesin hatlarla ayırmak, merkezi hata ve validasyon mimarilerini kurmak ve güvenliği (Authentication, Authorization, BOLA, CORS, Rate Limiting) en dış katmandan itibaren bir savunma zinciri olarak kurgulamaktan geçer.
