## 01. .NET Uygulama Çalıştırma ve Execution Modeli

### 📌 Temel Tanım
.NET uygulamaları **managed environment** olan **CLR (Common Language Runtime)** üzerinde çalışır.

```text
Genel Akış:
C# Kodu  ──(Roslyn Compiler)──>  IL (Intermediate Language) + Metadata
                                          │
                                    (Assembly: .dll)
                                          │
                                         CLR
                                          │
                                    (JIT Compiler)
                                          │
                                     Native Code  ──>  CPU
```
- **C# Compiler (Roslyn):** C# kaynak kodunu platformdan bağımsız bir ara dile (`IL`) derler.
- **JIT Compiler (Just-In-Time):** `IL` kodunu çalıştırılan donanım ve işletim sistemine uygun makine koduna (`Native Code`) çevirir.

### 🎯 En Önemli Kullanım Amacı
- .NET'in platformdan bağımsız (cross-platform) ortak bir ara kod kullanabilmesini sağlar.
- CLR; kod çalıştırma (execution), bellek yönetimi (memory), istisna yönetimi (exceptions), iş parçacığı yönetimi (threading) ve çöp toplayıcı (GC) servislerini üstlenir.
- Runtime, üzerinde çalıştığı spesifik donanım mimarisine (x64, ARM64 vb.) özel optimize edilmiş native kod üretir.

### ⚡ Kritik Kurallar
- Üretilen `.dll` dosyası içerisinde yalnızca C# kaynak kodu bulunmaz; **IL (Intermediate Language)** ve **Metadata** bulunur.
- `dotnet` executable dosyası, uygulamayı ayağa kaldıran host sürecidir.
- CLR, assembly'leri belleğe yükler ve yönetilen yürütmeyi (managed execution) başlatır.
- JIT, metotları genellikle **ilk çağrıldıkları anda (on-demand)** derler.
- JIT her HTTP isteğinde yeniden derleme **yapmaz**; derlenen makine kodu bellekte saklanır ve sonraki çağrılarda doğrudan çalıştırılır.
- Modern .NET sürümleri çok katmanlı derleme (**Tiered Compilation**) kullanır.

### ⚠️ Sık Yapılan Hatalar
- C# kodunun doğrudan CPU tarafından çalıştırıldığını sanmak.
- **SDK** ile **Runtime** kavramlarını birbirine karıştırmak.
- `dotnet build` ile `dotnet run` süreçlerini aynı şey sanmak.
- JIT derleyicisinin her istekte tekrar çalıştığını zannetmek.
- Production ortamındaki runtime veya dependency kaynaklı hataları business logic hatası sanmak.

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- **Cold-start** (ilk açılış) ile **Steady-state** (kararlı durum) performansı arasındaki farkı net olarak ayırın.
- JIT, Tiered Compilation ve Native AOT seçeneklerinin sistem performansına etkisini iyi analiz edin.
- Runtime sürümü, hedef mimari (x64 / ARM64) ve işletim sistemi uyumluluğunu deployment aşamasında doğrulayın.
- Assembly yükleme (`AssemblyLoadException`, `FileNotFoundException`) problemlerini doğru sınıflandırın.
- Native AOT tercihini yalnızca startup veya bellek avantajına bakarak yapmayın; reflection ve kütüphane ekosistemi uyumluluğunu mutlaka değerlendirin.
- Production seviyesinde çıkan arızalarda şu katman ayrımını yapabilmelisiniz:
  ```text
  Application Code  vs  Runtime  vs  Deployment  vs  Operating System
  ```

> [!TIP]
> **Tek Cümlelik Özet:** .NET'te yazdığınız C# kodu önce IL'e derlenir; CLR uygulamayı yönetir, JIT derleyicisi ise gereken IL kodunu CPU'nun çalıştırabileceği native koda dönüştürür.

## 02. Assembly, IL ve Metadata Yapısı

### 📌 Temel Tanım
- **Assembly:** .NET'in temel dağıtım, güvenlik ve versiyonlama birimidir (genellikle `.dll` veya `.exe`).
- **IL (Intermediate Language):** C# derleyicisinin ürettiği, CPU'dan bağımsız düşük seviyeli yönerge kümesidir.
- **Metadata:** Assembly içindeki tüm tipler, metotlar, alanlar, arayüzler, öznitelikler (attributes) ve referans bilgilerini içeren ikili tablodur.
- **Manifest:** Assembly'nin adı, versiyonu, kültürü ve bağımlılıklarını tutan assembly düzeyindeki üst metadata bloğudur.

### 🎯 En Önemli Kullanım Amacı
- **IL:** Kodun farklı işletim sistemlerinde ve işlemci mimarilerinde tek bir derleme çıktısıyla çalışabilmesini sağlar.
- **Metadata:** CLR'ın ve framework bileşenlerinin assembly içindeki tipleri çalışma zamanında (runtime) anlayabilmesini sağlar.
- Dependency Injection (DI) taramaları, Reflection, API route keşifleri ve Attribute mekanizmaları tamamen metadata üzerinden çalışır.

### ⚡ Kritik Kurallar
- Derleme akışı: `C# → Assembly → IL + Metadata → CLR/JIT → Native Code`.
- Bir `.dll` dosyası doğrudan makine kodu (native machine code) anlamına gelmez.
- `Namespace ≠ Assembly`: Bir namespace birden çok assembly'ye yayılabilir; bir assembly içinde birden çok namespace barınabilir.
- Visual Studio projesi (`.csproj`) çoğunlukla bir assembly üretir ancak kavramsal olarak aynı şey değildir.
- Attribute verileri metadata tablolarına gömülür.
- Her assembly, ihtiyaç duyduğu diğer assembly bağımlılıklarını manifest'inde açıkça tanımlar.

### ⚠️ Sık Yapılan Hatalar
- DLL dosyasını doğrudan native binary zannetmek.
- Namespace ile Assembly kavramlarını eşanlamlı kabul etmek.
- Her HTTP isteğinde reflection veya assembly scanning (tip taraması) yapmak.
- Reflection işlemlerinin getirdiği CPU ve bellek maliyetini göz ardı etmek.
- `Could not load file or assembly` hatasını veritabanı veya iş mantığı arızası sanmak.

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- Reflection ve assembly scanning işlemlerini kesinlikle **uygulama ayağa kalkarken (startup)** bir kez yapın ve sonuçları cache'leyin / DI konteynerine kaydedin.
- Assembly versiyon uyuşmazlıklarını (binding redirect, version mismatch) hızlıca teşhis edin.
- Public API üzerinde yapılan imza değişikliklerinin assembly kontratını kırdığını (breaking change) unutmayın.
- **Native AOT** ve **Trimming** uygulanan projelerde reflection tabanlı kodların çalışma zamanında patlayabileceğini hesaba katın.
- Production'daki assembly arızalarında kontrol listesi:
  1. `Version` (Hedeflenen ve derlenen sürüm)
  2. `Dependency` (Eksik transitive bağımlılıklar)
  3. `Publish output` (Dağıtım klasöründeki dosyaların tamlığı)
  4. `Runtime` (Sunucudaki .NET sürümü)
  5. `Old / Stale DLL` (Eski kalmış, üzerine yazılmamış dosyalar)

> [!TIP]
> **Tek Cümlelik Özet:** Assembly taşıyıcı pakettir, IL çalıştırılacak talimatları barındırır, metadata ise runtime'a paketin içinde ne olduğunu anlatan kimlik kartıdır.

## 03. CLR ve Managed Execution

### 📌 Temel Tanım
**CLR (Common Language Runtime)**, .NET kodunun yürütüldüğü sanal çalışma zamanı ortamıdır. CLR gözetiminde ve denetiminde yürütülen koda **Managed Code (Yönetilen Kod)** denir.

### 🎯 En Önemli Kullanım Amacı
- Kod yürütme yaşam döngüsünü (execution lifecycle) baştan sona yönetmek.
- Otomatik bellek tahsisi ve temizliği (**Memory Management & GC**) sağlamak.
- Çalışma anında ihtiyaç duyulan IL kodlarını makine diline çevirmek (**JIT Compilation**).
- Tip güvenliğini (**Type Safety**) ve istisna yönetimini (**Exception Handling**) garanti altına almak.
- Assembly ve tip yükleme (**Type Loading**) işlemlerini organize etmek.

### ⚡ Kritik Kurallar
- CLR sadece bir Garbage Collector (GC) değildir; tüm çalışma motorunu kapsar.
- GC yalnızca **erişilemeyen (unreachable)** yönetilen nesneleri temizler.
- Managed code kullanmak, uygulamada bellek sızıntısı (**memory leak**) olmayacağı anlamına gelmez.
- `IDisposable` arayüzünü uygulayan unmanaged kaynaklar (dosya işaretçileri, soketler, connection'lar) GC'nin insafına bırakılmamalıdır.
- ASP.NET Core, CLR'ın üzerinde inşa edilmiş bir web uygulama çatısıdır.

### ⚠️ Sık Yapılan Hatalar
- .NET platformunu sadece CLR'dan ibaret sanmak.
- Yönetilen bellekte (managed heap) sızıntı oluşamayacağını düşünmek.
- Kaynak kapatma (`Dispose`) işini GC'nin otomatik olarak doğru zamanda halledeceğini varsaymak.
- Performans darboğazlarında yalnızca business logic koduna odaklanıp runtime davranışlarını incelememek.

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- **Allocation Rate → GC Frequency → Latency (Gecikme)** arasındaki doğrudan ilişkiyi kavrayın.
- JIT derlemesinin uygulama ilk açıldığındaki soğuk başlama (**cold-start**) maliyetini hesaba katın.
- Yönetilen (managed) kaynaklar ile yönetilmeyen (unmanaged) kaynakların yaşam döngüsünü kesin hatlarla ayırın.
- Production ortamındaki kararsızlıklarda; GC duraklamaları (pause time), ThreadPool kuyruk uzunluğu, allocation hızı ve first-chance exception metriklerini inceleyin.
- CLR mimarisini teorik bir ezber olarak değil, doğrudan performans profilleme ve root-cause analizinde bir araç olarak kullanın.

## 04. JIT, Tiered Compilation, PGO ve Native AOT

### 📌 Temel Tanım
| Teknoloji | Tanım | Temel Avantaj |
| :--- | :--- | :--- |
| **JIT (Just-In-Time)** | IL kodunu uygulama çalışırken ihtiyaç anında makine koduna çevirir. | Çalıştığı CPU'ya özel runtime optimizasyonu. |
| **Tiered Compilation** | Metotları önce hızlıca temel seviyede, sık çağrılırsa daha derin optimize ederek derler. | Hızlı başlangıç + yüksek tepe performansı. |
| **Dynamic PGO** | Çalışma anındaki gerçek kullanım profiline (çağrı sıklığı, tip dağılımı) göre kod üretir. | Hot-path kodlarda maksimum yürütme hızı. |
| **Native AOT** | Kodu yayınlama (publish) esnasında doğrudan native makine koduna dönüştürür; runtime'da JIT yoktur. | Anında başlama, minimum bellek tüketimi. |

### 🎯 En Önemli Kullanım Amacı
- **JIT:** Esneklik ve donanıma özel çalışma anı optimizasyonları sağlamak.
- **Tiered Compilation:** Uygulamanın açılış hızı ile uzun vadedeki tepe performansını dengelemek.
- **PGO (Profile-Guided Optimization):** Sık kullanılan kod yollarını (hot path) ve arayüz çağrılarını devirtualize ederek hızlandırmak.
- **Native AOT:** Mikroservislerde, CLI araçlarında ve serverless (Function) mimarilerinde ultra hızlı cold-start ve küçük disk/RAM alanı sağlamak.

### ⚡ Kritik Kurallar
- Modern .NET (.NET 8+) sürümlerinde **Tiered Compilation** ve **Dynamic PGO** varsayılan olarak açıktır.
- JIT bir metodu her çağrıldığında yeniden derlemez; derlenmiş kod bellek adresinde saklanır.
- Native AOT çıktısı platforma bağımlıdır (Linux için Linux üzerinde, Windows için Windows üzerinde derlenmelidir).
- Native AOT dinamik kod üretimine (`Reflection.Emit`) ve sınırsız reflection kullanımına kapalıdır.
- Tipik bir kurumsal ASP.NET Core API projesinde runtime derleyici ayarlarına dokunulmamalı, varsayılanlar korunmalıdır.

### ⚠️ Sık Yapılan Hatalar
- "Native AOT her zaman JIT'ten daha hızlıdır" yanılgısına düşmek (uzun süre çalışan uygulamalarda JIT + PGO çoğu zaman daha yüksek throughput sağlayabilir).
- JIT'in her HTTP isteğinde tekrar çalıştığını varsaymak.
- Somut bir metrik olmadan Tiered Compilation veya PGO ayarlarını kapatmak.
- Debug build sonuçları üzerinden performans ve derleme karşılaştırması yapmak.
- AOT veya trimming derleme uyarılarını (warnings) göz ardı edip production'a çıkmak.

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- **JIT + Tiered Compilation + Dynamic PGO** modern .NET'in varsayılan ve birbiriyle uyumlu çalışan optimizasyon motorudur.
- Native AOT bunların üzerine eklenen bir ayar değil; tamamen farklı bir dağıtım ve çalışma modelidir.
- Uzun ömürlü kurumsal Web API'ler için genellikle **JIT + PGO** idealdir.
- Kısa ömürlü, anında ayağa kalkması gereken container ve scale-to-zero iş yüklerinde **Native AOT** değerlendirilmelidir.
- AOT kararı popülerliğe göre değil; **Startup Süresi + Bellek Ayak İzi + Throughput** benchmarklarına ve NuGet paketlerinin AOT/trimming uyumluluğuna göre verilmelidir.

> [!NOTE]
> **Zihinsel Model:** JIT kodu çalışırken derler, Tiered Compilation sıcak kodu yeniden optimize eder, PGO neyin sıcak olduğunu çalışma anında öğretir; Native AOT ise tüm bu süreci publish zamanına taşır.

## 05. .NET SDK, Runtime, Host ve Deployment Modelleri

### 📌 Temel Tanım & Kavramlar
- **SDK (Software Development Kit):** .NET uygulaması geliştirmek, derlemek (`build`), test etmek ve paketlemek (`publish`) için kullanılan tüm araç setidir. Runtime'ı bünyesinde barındırır.
- **Runtime:** Yalnızca önceden derlenmiş .NET uygulamalarını çalıştırmaya yarayan yürütme motorudur (CLR ve temel kütüphaneler). SDK içermez.
- **Host (`dotnet.exe` / AppHost):** Uygulamanın ihtiyaç duyduğu runtime'ı bulur, yapılandırır ve CLR'ı belleğe yükleyerek `Main` metodunu tetikler. *(Not: .NET Host ile ASP.NET Core'daki `IHost` / `WebApplication` farklı kavramlardır).*
- **Target Framework (`net8.0`, `net10.0`):** Uygulamanın hedeflediği API setidir; makinede kurulu olan SDK sürümüyle birebir aynı olmak zorunda değildir.

### 💻 Temel Tanı ve Durum Komutları
```bash
dotnet --list-sdks       # Sistemde kurulu olan tüm SDK sürümlerini listeler
dotnet --list-runtimes   # Sistemde kurulu olan tüm Runtime sürümlerini listeler
dotnet --info            # Geçerli ortam, mimari ve aktif SDK/Runtime detaylarını döker
```

### 📦 Dağıtım (Deployment) Modelleri

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                          DEPLOYMENT MODELLERİ                           │
├────────────────────────────────────┬────────────────────────────────────┤
│ Framework-Dependent (FDD)          │ Self-Contained (SCD)               │
├────────────────────────────────────┼────────────────────────────────────┤
│ • Runtime sunucuda kurulu olmalı.  │ • .NET Runtime uygulamanın içine   │
│ • Dağıtım boyutu çok küçüktür.     │   gömülür; sunucuda runtime gerekmez│
│ • Sunucudaki runtime güncellenirse │ • RID (örn: linux-x64) şarttır.    │
│   tüm uygulamalar etkilenir.       │ • Dağıtım boyutu büyüktür.         │
└────────────────────────────────────┴────────────────────────────────────┘
```

- **RID (Runtime Identifier):** Uygulamanın çalışacağı işletim sistemi ve işlemci mimarisini belirler (örn: `win-x64`, `linux-x64`, `osx-arm64`).
- **Single File:** Bağımsız bir dağıtım modeli değil, bir paketleme seçeneğidir. Tüm DLL ve bağımlılıkları tek bir çalıştırılabilir dosya haline getirir; hem FDD hem de SCD ile kullanılabilir.
- **Docker Multi-Stage Build Best Practice:**
  ```dockerfile
  # Aşama 1: Derleme (Ağır SDK imajı)
  FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
  WORKDIR /src
  COPY . .
  RUN dotnet publish -c Release -o /app/publish

  # Aşama 2: Çalıştırma (Hafif ASP.NET Runtime imajı)
  FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
  WORKDIR /app
  COPY --from=build /app/publish .
  ENTRYPOINT ["dotnet", "MyApp.dll"]
  ```

### 🧠 Senior Seviye Prensip
Bir mimar veya senior geliştirici olarak dağıtım stratejisi belirlerken şu beşli zinciri birlikte düşünün:
$$\text{SDK Sürümü} \longleftrightarrow \text{TargetFramework} \longleftrightarrow \text{Runtime} \longleftrightarrow \text{RID} \longleftrightarrow \text{Dağıtım Modeli}$$

## 06. Stack, Heap ve Call Stack Yapısı

### 📌 Temel Tanım
- **Stack (Yığın):** Her bir işletim sistemi iş parçacığına (thread) özel, çok hızlı çalışan LIFO (Last-In-First-Out) bellek bölgesidir.
- **Stack Frame:** Bir metot çağrıldığında, o metodun parametreleri, yerel değişkenleri ve dönüş adresi için Stack üzerinde ayrılan geçici çalışma bloğudur. Metot bittiğinde frame bellekten anında düşer (pop edilir).
- **Call Stack:** Çalışmakta olan metotların çağrı sırasını gösteren aktif stack frameler zinciridir. Hata ayıklamadaki (debugging) `StackTrace` bu zincirin çıktısıdır.
- **Heap (Yığın):** Yönetilen nesnelerin (managed objects) yaşadığı, tüm thread'lerin ortak erişimine açık dinamik bellek alanıdır. Çöp toplayıcı (GC) tarafından yönetilir.

### 🎯 En Önemli Kullanım Amacı
- Bellek tahsisatlarının ve yaşam sürelerinin nasıl çalıştığını anlamak.
- Gereksiz heap tahsisatlarını (allocation) ve GC baskısını engellemek.
- Hata anlarında Stack Trace'i doğru okuyup kök nedeni hızlıca saptamak.
- Kontrolsüz özyineleme (**recursion**) kaynaklı `StackOverflowException` risklerini engellemek.

### ⚡ Kritik Kurallar
> [!CAUTION]
> **"Value type her zaman Stack'te, Reference type her zaman Heap'tedir" EZBERİ KESİNLİKLE YANLIŞTIR!**

- Değişkenin kendisi ile değişkenin işaret ettiği nesneyi birbirinden ayırın.
- Bir sınıfın (`class`) içindeki değer tipi (`int`, `bool`, `struct`) alanlar, **o sınıf örneğinin bir parçası olarak HEAP üzerinde yaşar**.
- Her thread'in kendine ait bağımsız bir stack boyutu vardır (varsayılan olarak 1 MB civarı).
- Yönetilen Heap tüm thread'ler tarafından paylaşılır; dolayısıyla heap üzerindeki verilere eşzamanlı erişim thread-safety gerektirir.
- JIT derleyicisi bazı yerel değişkenleri stack yerine doğrudan **CPU Register**'larında tutabilir.
- Stack üzerindeki nesne referansları, GC için hayati birer **GC Root** kaynağıdır.

### ⚠️ Sık Yapılan Hatalar
- `struct = Stack`, `class = Heap` ezberine göre mimari karar vermek.
- Heap üzerindeki her allocation'ı felaket sayıp kodu okunaksız mikro optimizasyonlara boğmak.
- Ölçüm yapmadan (profiler / benchmark kullanmadan) allocation optimizasyonuna girişmek.
- Büyük `struct` yapıları tanımlayıp metotlar arasında kopyalanırken oluşan CPU maliyetini unutmak.
- Çıkış koşulu zayıf olan recursion kullanarak thread stack'ini tüketmek.

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- Temel mühendislik hedefi veriyi zorla Stack'e tıkmak değil; **gereksiz allocation oranını ve GC pressure'ı düşürmektir**.
- `Span<T>`, `Memory<T>`, `ArrayPool<T>` ve `stackalloc` ileri düzey araçlardır; ölçülmüş bir darboğaz yoksa gereksiz yere karmaşıklık eklenmemelidir.
- `async / await` yapısı çalıştığında, derleyici metodu bir **state machine** sınıfına dönüştürdüğü için klasik Call Stack modelini dönüştürür; değişkenler heap'teki state machine nesnesine taşınabilir.

```text
Kavramsal Zincir:
Stack / Heap  ──>  Value / Reference Types  ──>  Boxing  ──>  GC Roots  ──>  GC Generations  ──>  Allocation Pressure
```

## 07. Value Type, Reference Type ve Parametre Aktarımı

### 📌 Temel Tanım
- **Value Type (Değer Tipi):** `int`, `double`, `decimal`, `bool`, `DateTime`, `Guid`, `enum`, `struct`, `record struct`. Değerin kendisini taşır. Bir değişkenden diğerine atandığında **tüm veri kopyalanır**.
- **Reference Type (Referans Tipi):** `class`, `string`, `array`, `interface`, `delegate`, `record`. Bellekteki nesnenin adresini (işaretçisini) taşır. Atama yapıldığında yalnızca adres kopyalanır; iki değişken aynı nesneyi gösterir.

### 🔄 Parametre Aktarım Mekanizmaları
C#'ta varsayılan kural: **Tüm parametreler aksi belirtilmedikçe PASS-BY-VALUE (değer olarak) aktarılır!**

```csharp
// 1. Reference Type varsayılan aktarım: Referansın kopyası geçer
void UpdateCustomer(Customer c) {
    c.Name = "Ahmet"; // Çağıran taraf ETKİLENİR (aynı nesne)
    c = new Customer(); // Çağıran taraf ETKİLENMEZ (kopya işaretçi yönlendirildi)
}

// 2. 'ref' kullanımı: Değişkenin doğrudan bellek gözü aktarılır
void ReplaceCustomer(ref Customer c) {
    c = new Customer(); // Çağıran taraf da ETKİLENİR
}

// 3. 'out' kullanımı: Metodun dışarıya mutlaka değer üretmesini zorunlu kılar
bool TryParse(string s, out int result);

// 4. 'in' kullanımı: Büyük struct'ları kopyalamadan, READ-ONLY referans olarak geçirir
void ProcessData(in BigStruct data);
```

### ⚡ Kritik Kurallar
- Reference type bir parametre metoda geçildiğinde, kopyalanan şey nesnenin kendisi değil **referansıdır (adresidir)**.
- `string` bir reference type'tır ancak **immutable** (değiştirilemez) davranış sergiler.
- `record` varsayılan olarak reference type; `record struct` ise value type'tır.
- `in` anahtar kelimesi, özellikle büyük `struct` yapılarının metotlara kopyalanma maliyetini önlemek için tasarlanmıştır.

### ⚠️ Sık Yapılan Hatalar
- Reference type parametrelerin metoda otomatik olarak `ref` ile geçtiğini zannetmek.
- `var b = a;` yazıldığında class nesnesinin klonlandığını sanmak.
- `string` tipini primitive olduğu gerekçesiyle value type zannetmek.
- Alanları değiştirilebilir (**mutable**) büyük `struct` tipleri tasarlamak (beklenmedik yan etkilere ve defensive copy maliyetine yol açar).

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- **Semantik Davranış (Değer vs Referans)** ile **Depolama Yeri (Stack vs Heap)** kavramlarını birbirine karıştırmayın.
- Metotlar arasında paylaşılan mutable (durumu değişebilen) nesneler çok kanallı (multithread) sistemlerde kontrolsüz yan etkiler (`side-effects`) üretir.
- Kurumsal iş uygulamalarında DTO, Domain Entity ve Servisler için doğal tercih **`class`** olmalıdır; `struct` kullanmak için somut bir bellek veya mikro-performans gerekçeniz bulunmalıdır.

> [!TIP]
> **Hafıza Kuralı:** C#'ta her şey varsayılan olarak *değeriyle* aktarılır; bir reference type aktarılırken aktarılan değer, o nesnenin bellek referansıdır.

## 08. Boxing, Unboxing ve Allocation Davranışları

### 📌 Temel Tanım
- **Boxing:** Bir değer tipinin (`value type`), `object` tipine veya uyguladığı bir `interface` tipine dönüştürülmesidir. Değer stack'ten kopyalanarak **yönetilen heap üzerinde yeni bir nesne olarak tahsis edilir (allocation)**.
- **Unboxing:** Daha önce box edilmiş bir `object` içindeki ham değerin, asıl değer tipi türüne geri çıkartılması işlemidir.
- **Allocation:** Managed Heap üzerinde yeni bir nesne için yer açılmasıdır.

```csharp
int i = 42;
object o = i;     // BOXING -> Heap üzerinde yeni bir nesne ayrıldı!
int j = (int)o;   // UNBOXING -> Değer heap'ten stack'e kopyalandı.
```

### ⚡ Kritik Kurallar
- Unboxing işlemi bir **tür dönüşümü (conversion) değildir**.
  ```csharp
  object o = 10;           // int kutulandı
  long x = (long)o;        // InvalidCastException! Doğrudan tür dönüşümü yapılamaz.
  long x = (long)(int)o;   // DOĞRU: Önce asıl tipe unbox edilir, sonra cast edilir.
  ```
- Generic yapılar (`List<T>`, `Dictionary<TKey, TValue>`), eski tip nesne koleksiyonlarının (`ArrayList`) yarattığı boxing fırtınasını engellemek için geliştirilmiştir.
- Bir value type'ın doğrudan metot içinde tanımlanması tek başına heap allocation üretmez.

### ⚠️ Sık Yapılan Hatalar
- Metot parametrelerinde bilinçsizce `object` kullanmak.
- Generic olmayan koleksiyonları (`ArrayList`, `Hashtable`) tercih etmek.
- Unboxing ile veri tipi dönüşümünü aynı şey zannetmek.
- Bir struct yapısını bir `interface` üzerinden çağırdığında oluşan **gizli boxing** maliyetini kaçırmak:
  ```csharp
  struct MyCounter : ICounter { ... }
  ICounter c = new MyCounter(); // BOXING oluşur!
  ```
- Nadir çalışan kodlardaki mikroskobik boxing işlemlerini optimize etmek için kodun okunabilirliğini feda etmek.

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- Boxing'in asıl tehlikesi CPU süresinden ziyade; **yüksek frekanslı çağrılarda oluşturduğu gereksiz heap nesneleri ve tetiklediği GC baskısıdır (GC pressure)**.
- Loglama kütüphanelerinde yapısal loglama yerine `string.Format("Değer: {0}", counter)` gibi kullanımlar gizli boxing üretir.
- Tahmin yürüterek optimizasyon yapmayın; `BenchmarkDotNet` ile `Allocated Bytes` sütununu inceleyerek karar verin.
- **Temel Mühendislik Prensibi:** Bellek tahsisi (allocation) kendi başına kötü değildir; kötü olan **gereksiz, döngüsel ve yüksek frekanslı tahsisatlardır**.

## 09. Nesne Yaşam Döngüsü, Referanslar ve GC Roots

### 📌 Temel Tanım
- Managed nesneler Heap üzerinde yaşar. Bir değişken, nesnenin kendisini değil yalnızca adresini tutar.
- **GC Roots (Kökler):** Çöp toplayıcının nesne taramasına başladığı başlangıç noktalarıdır.
  - Aktif metotların yerel değişkenleri ve parametreleri (Stack üzerindeki referanslar)
  - Statik değişkenler (`static` alanlar)
  - CPU register'larındaki referanslar
  - Interop / P/Invoke handle'ları (`GCHandle`)
- **Reachable (Erişilebilir):** Köklerden başlayarak referans zinciri takip edildiğinde ulaşılabilen nesnelerdir.
- **Unreachable (Erişilemez):** Hiçbir aktif kök referansından ulaşılamayan, ömrü bitmiş ve toplanmaya hazır nesnelerdir.

```text
[ GC Roots ] (Static Alanlar, Stack Değişkenleri, CPU Register)
     │
     ▼
[ Nesne A ] ───> [ Nesne B ] ───> [ Nesne C ]  (Reachable -> GC DOKUNMAZ)
                                 
[ Nesne D ] ───> [ Nesne E ]                   (Unreachable -> GC TOPLAR!)
```

### ⚡ Kritik Kurallar
- Bir nesneye giden aktif bir referans zinciri olduğu sürece, GC o nesneyi **asla bellekten temizleyemez**.
- Erişilebilir durumdaki bir nesnenin işaret ettiği diğer tüm nesneler de otomatik olarak erişilebilir kabul edilir.
- `static` alanlar uygulama veya AppDomain kapanana kadar yaşadığı için tuttukları nesneleri ömür boyu hayatta tutarlar.
- Bir nesne unreachable hale geldiği anda **anında silinmez**; bir sonraki uygun GC turuna kadar bellekte kalır.
- `Dispose()` çağırmak nesneyi bellekten silmez.
- `GC.Collect()` normal kurumsal uygulama kodlarında manuel olarak **çağrılmamalıdır**.
- Yerel değişkenleri metot sonunda manuel olarak `null`'a eşitlemek modern derleyicilerde gereksizdir.

### ⚠️ Sık Yapılan Hatalar
- "Uygulamada GC var, nasılsa bellek sızıntısı (memory leak) olamaz" yanılgısı.
- `static` koleksiyonlara (`List`, `Dictionary`) sürekli eleman ekleyip temizlemeyi unutmak.
- `Singleton` servisler içinde HTTP request'e özel verileri saklamak.
- Event aboneliklerini (`event += handler`) sonlandırmamak; dinlenen nesnenin dinleyeni kökten bağlı tutması.
- `Dispose()` metodunun nesneyi RAM'den yok ettiğini sanmak.

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- .NET dünyasında **Memory Leak**, işletim sistemindeki pointer sızıntısı gibi değil; **"istenmeyen uzun ömürlü referanslar yüzünden nesnelerin temizlenememesi"** şeklinde gerçekleşir.
- Bellek dökümü (dump) analizinde "En büyük nesne hangisi?" sorusundan ziyade **"Bu nesneyi kim hayatta tutuyor? (Path to Root)"** sorusunu sorun.
- Bellek içi önbelleklerde (`MemoryCache`) mutlaka bir **boyut sınırı (SizeLimit)** ve **yaşam süresi (Expiration)** tanımlayın.

> [!IMPORTANT]
> **Altın Kural:** Bir nesneye GC Root'larından bir referans yolu ile ulaşılabiliyorsa, Garbage Collector o nesneyi kesinlikle canlı kabul eder.

## 10. Garbage Collector, Generations ve GC Modları

### 📌 Temel Tanım & Nesne Ömrü Hipotezi
.NET Çöp Toplayıcısı **Generational (Kuşaksal)** bir mimariye sahiptir. Bu mimari şu bilimsel gözleme dayanır: *"Yeni oluşturulan nesnelerin büyük çoğunluğu çok kısa süre yaşar (Weak Generational Hypothesis)."*

```text
     ┌──────────────┐
     │ Yeni Nesneler│
     └──────┬───────┘
            ▼
   [ Generation 0 ]  ──(Hayatta kalanlar)──> [ Generation 1 ]  ──(Hayatta kalanlar)──> [ Generation 2 ]
   • Çok sık çalışır                         • Geçiş kuşağı                           • Nadir çalışır
   • Çok hızlı ve ucuzdur                    • Gen0 ile Gen2 arasında tampon          • Pahalıdır (Full GC)
   • Ephemeral Segment                                                                • Uzun ömürlü nesneler
```

- **Generation 0 (Gen 0):** Yeni oluşturulan küçük nesnelerin başladığı yerdir. Çok sık ve nanosaniyeler mertebesinde temizlenir.
- **Generation 1 (Gen 1):** Gen 0 temizliğinden sağ kurtulan nesnelerin terfi ettiği (promotion) tampon alandır.
- **Generation 2 (Gen 2):** Uzun süre yaşayan nesnelerin (Singleton servisler, statik veriler, önbellekler) bulunduğu yerdir. Gen 2 temizliğine **Full GC** denir ve maliyeti yüksektir.

### ⚙️ GC Çalışma Modları

| Mod | Kullanım Senaryosu | Özellikler |
| :--- | :--- | :--- |
| **Workstation GC** | Masaüstü ve istemci uygulamaları | Düşük gecikme, kullanıcı arayüzü takılmalarını önleme, tek heap. |
| **Server GC** | ASP.NET Core ve yüksek throughput sunucu sistemleri | CPU çekirdeği başına bağımsız heap ve GC thread'i; maksimum paralel işleme gücü. |
| **Background GC** | Varsayılan olarak etkindir | Gen 2 temizliği yapılırken uygulamanın Gen 0/1 tahsisatlarına devam edebilmesini sağlar (duraklamayı minimize eder). |

### ⚡ Kritik Kurallar
- Gen 0 temizliği ucuzdur; ancak nesneler üst jenerasyonlara terfi ettikçe (promote oldukça) temizleme maliyeti katlanarak artar.
- GC çalışırken managed thread'leri kısa süreliğine durdurabilir (**Stop-the-World pause**).
- Server GC, sistemdeki CPU çekirdeği kadar bellek yığını oluşturduğu için uygulamanın ilk açılışta daha fazla RAM tüketmesine neden olabilir; bu normaldir.

### ⚠️ Sık Yapılan Hatalar
- Kodun arasına rastgele `GC.Collect()` serpiştirmek.
- Gen 2'de nesne bulunmasını bir hata zannetmek (uzun ömürlü nesnelerin yeri orasıdır).
- Uygulamanın RAM kullanımının yüksek olmasını tek başına memory leak kanıtı saymak (GC ihtiyaç duymadıkça işletim sistemine belleği iade etmeyebilir).
- Döngü içinde sürekli kısa ömürlü geçici nesneler oluşturup Gen 0'ı nefes alamaz hale getirmek.

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- Analizlerde yalnızca ayrılan toplam bellek boyutuna (`Heap Size`) değil, birim zamandaki tahsisat hızına (**Allocation Rate**) odaklanın.
- Gen 0 toplama sıklığının anormal artması, kodda aşırı geçici nesne üretildiğinin açık göstergesidir.
- Erken yaşta Gen 2'ye fırlayan nesneler (premature promotion) uzun vadeli bellek darboğazı üretir.
- `dotnet-counters` aracı ile `GC Heap Size`, `Gen 0/1/2 GC Count` ve `% Time in GC` metriklerini canlı ortamda izleyin.

```text
Zihinsel Kısır Döngü:
Yüksek Allocation  ──>  Erken Promotion  ──>  Sık Gen 2 GC  ──>  Stop-the-World Duraklamaları  ──>  Yüksek CPU & İstek Gecikmesi (Latency)
```

## 11. LOH, POH, Pinning ve Memory Fragmentation

### 📌 LOH (Large Object Heap)
- **Eşik Değer:** Boyutu **85.000 byte (~85 KB)** ve üzerindeki nesneler (çoğunlukla büyük `byte[]`, büyük `string` veya büyük diziler) doğrudan LOH üzerine tahsis edilir.
- **Toplanma Zamanı:** LOH, normal nesneler gibi Gen 0 veya Gen 1'de değil; yalnızca **Gen 2 (Full GC)** sırasında temizlenir.
- **Maliyet:** Geçici büyük nesnelerin sürekli oluşturulması, sistemi sürekli pahalı Gen 2 GC çalıştırmaya zorlar.

### 📌 Pinning ve Bellek Parçalanması (Fragmentation)
- **Pinning:** Yönetilmeyen bir API'ye (P/Invoke, soket vb.) bellek adresi geçirilirken, GC'nin o nesneyi defragmentation (sıkıştırma) esnasında bellekte taşımasını engellemek amacıyla adresin kilitlenmesidir.
- **Fragmentation Riski:** GC, serbest kalan alanları birleştirmek için nesneleri kaydırırken pinned nesnelerin etrafından atlamak zorunda kalır. Bu durum bellekte boşluklar oluşturur (**Memory Fragmentation**); toplamda yeterli RAM olmasına rağmen ardışık büyük bir blok bulunamadığı için `OutOfMemoryException` patlayabilir.

```text
Parçalanmış Bellek (Fragmentation):
[ Canlı Nesne ] [ BOŞLUK (40KB) ] [ PINNED NESNE ] [ BOŞLUK (30KB) ] [ Canlı Nesne ]
(Sistemde 70 KB boş yer var; fakat ardışık 50 KB'lık yeni nesne tahsis EDILEMEZ!)
```

### 📌 POH (Pinned Object Heap)
- .NET 5 ile hayatımıza girmiştir.
- Sürekli sabitlenecek (pinned) dizilerin normal heap alanını parçalamasını önlemek için ayrılmış özel heap bölgesidir.
- Kullanım:
  ```csharp
  // Doğrudan POH üzerinde kilitli dizi oluşturma
  byte[] pinnedBuffer = GC.AllocateArray<byte>(4096, pinned: true);
  ```

### ⚡ Kritik Kurallar ve Çözümler
- Büyük dosya, resim veya response işleme süreçlerinde belleğe tek parça devasa `byte[]` dizileri çekmek yerine kesinlikle **Streaming (`Stream`)** kullanın.
- Tekrarlanan büyük buffer ihtiyaçlarında diziyi yeniden üretmek yerine `ArrayPool<T>` ile havuzlayın.
- `GCHandle.Alloc(..., GCHandleType.Pinned)` kullanılıyorsa, kilit mutlaka `finally` bloğu içerisinde `Free()` edilmelidir.
- Parçalanma bir bellek sızıntısı değildir; belleğin diziliş düzeninin bozulmasıdır.

### 🧠 Senior Mühendislik Sıralaması
Bellek optimizasyonuna girişirken şu hiyerarşiyi takip edin:
1. **Allocation'ı Azalt:** Nesneyi hiç üretmemenin bir yolunu bul (Streaming, Slice).
2. **Ömrü Kısalt:** Üretmek zorundaysan işi biter bitmez referansını düşür.
3. **Pooling / POH Kullan:** Büyük ve sürekli tekrarlayan ihtiyaçlarda havuzlama (`ArrayPool<T>`) veya `POH` değerlendir.

## 12. IDisposable, Finalizer ve Deterministic Resource Management

### 📌 Temel Tanım
- **Managed Kaynak:** CLR tarafından yönetilen, çöp toplayıcının tahsis ve temizliğini bildiği bellek alanları.
- **Unmanaged Kaynak:** CLR dışındaki işletim sistemi kaynakları (Dosya tanıtıcıları `IntPtr`, soketler, veritabanı bağlantıları, pencere handle'ları).
- **`IDisposable`:** Bir sınıfın kullanım bittiğinde deterministik olarak (hemen o anda) temizlenmesi gereken kritik bir kaynak barındırdığını ifade eden kontrattır.
- **Finalizer (`~MyClass()`):** Geliştirici nesneyi dispose etmeyi unuttuğunda, GC'nin nesneyi yok etmeden önce çalıştırdığı son çare mekanizmasıdır; çalışma zamanı belirsizdir (non-deterministic).

### ⚡ Kritik Kurallar ve Standart Dispose Deseni
- `Dispose()` metodu nesneyi **bellekten silmez**; nesnenin dış sistemlerde kilitlediği unmanaged kaynağı serbest bırakır.
- `using` ifadesi, derleyici tarafından bir `try-finally` bloğuna dönüştürülür ve hata çıksa dahi `Dispose()` çağrısını garanti eder.
- Asenkron temizlik gerektiren durumlarda `IAsyncDisposable` arayüzü ve `await using` kullanılmalıdır.
- **Her disposable sınıfa Finalizer YAZILMAZ!** Finalizer yalnızca sınıf doğrudan unmanaged bir işaretçiyi (`IntPtr`) yönetiyorsa yazılır.
- Kendi finalizer'ınızı yazmak yerine .NET'in sunduğu `SafeHandle` sınıflarını tercih edin.
- `Dispose()` çağrıldıktan sonra `GC.SuppressFinalize(this)` çağrılmalıdır; böylece GC'ye nesneyi Finalization Queue'ya sokmadan doğrudan temizleyebileceği bildirilir.
- `Dispose()` metodunuz **idempotent** olmalıdır (birden fazla kez çağrılsa bile güvenle çalışmalı, hata vermemelidir).

```csharp
public class ResourceHolder : IDisposable
{
    private bool _disposed = false;
    private SafeHandle _handle = new SafeFileHandle(IntPtr.Zero, true);

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this); // Finalizer kuyruğundan çıkararak GC'yi hızlandır
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // Managed disposable kaynakları temizle
            _handle?.Dispose();
        }

        // Unmanaged kaynakları temizle (varsa)

        _disposed = true;
    }
}
```

### ⚠️ Sık Yapılan Hatalar
- DI (Dependency Injection) konteyneri tarafından yönetilen servisleri (`DbContext` vb.) kod içinde manuel `using` ile dispose etmeye kalkışmak.
- `Finalizer` içerisinde başka yönetilen nesnelere erişmeye çalışmak (o nesneler çoktan GC tarafından toplanmış olabilir).
- "Nasılsa GC temizler" diyerek dosya akışlarını veya SQL connection'larını açık bırakmak.

> [!NOTE]
> **Temel Ayrım:** Garbage Collector **yönetilen belleği** geri kazanır; `Dispose()` ise işletim sisteminin **tükenebilir dış kaynaklarını** zamanında serbest bırakır.

## 13. String Bellek Yönetimi ve String Optimizasyonları

### 📌 String İmmutability (Değişmezlik)
C#'ta `string` bir **reference type**'tır ancak **immutable** olarak tasarlanmıştır. Bir string değişkeni üzerinde yapılan her manipülasyon (`+=`, `Replace`, `Substring`, `ToUpper`), mevcut metni yerinde değiştirmez; **Heap üzerinde tamamen yeni bir string nesnesi oluşturur**.

### ⚡ Pratik String Kuralları ve Çözüm Rehberi

```text
┌───────────────────────────────────────┬────────────────────────────────────────────────────────┐
│ SENARYO                               │ DOĞRU YAKLAŞIM                                         │
├───────────────────────────────────────┼────────────────────────────────────────────────────────┤
│ 2-3 parçayı birleştirmek              │ String Interpolation: $"{name} {surname}"              │
│ Döngü içinde yüzlerce parça eklemek   │ StringBuilder (Başlangıç kapasitesi verilerek!)        │
│ Büyük metinleri dışarı aktarmak       │ Bellekte string tutmak yerine Stream / TextWriter      │
│ Metinden bir bölüm ayırmak/parse etmek│ Substring yerine ReadOnlySpan<char>                    │
│ Kod içi metin karşılaştırma           │ StringComparison.Ordinal / OrdinalIgnoreCase           │
│ Loglama                               │ Interpolation yerine Structured Message Template       │
└───────────────────────────────────────┴────────────────────────────────────────────────────────┘
```

### 🔍 Kritik Hatalar ve Kaçınılması Gerekenler
- **Büyük/Küçük Harf Karşılaştırması:**
  ```csharp
  // KÖTÜ: İki yeni string allocation'ı + kültür bağımlı yavaş çalışma
  if (name.ToLower() == other.ToLower()) 

  // DOĞRU: Sıfır allocation, saf bayt karşılaştırması
  if (string.Equals(name, other, StringComparison.OrdinalIgnoreCase))
  ```
- **Yapısal Loglama (Structured Logging):**
  ```csharp
  // KÖTÜ: Log seviyesi kapalı olsa bile string birleştirilir (Allocation!)
  _logger.LogInformation($"Sipariş tamamlandı. Id: {order.Id}");

  // DOĞRU: Message template kullanımı; log kapalıysa string üretilmez
  _logger.LogInformation("Sipariş tamamlandı. Id: {OrderId}", order.Id);
  ```
- **String Interning Riski:** Kod içindeki sabit literal metinler CLR tarafından string intern havuzunda tutulur. Dışarıdan gelen kontrolsüz dinamik kullanıcı verilerini `string.Intern()` ile havuza atmayın; havuzdaki nesneler uygulama kapanana kadar temizlenemez!

## 14. Span, Memory, ArrayPool ve Bellek Verimli Veri İşleme

### 📌 Span<T> ve ReadOnlySpan<T>
`Span<T>`, belleğin herhangi bir ardışık bölgesine (Managed Heap, Stack veya Native Memory) kopyalama yapmadan doğrudan ve güvenli erişim sağlayan bir **`ref struct`** yapısıdır.
- `Slice()` metodu yeni bir dizi veya string kopyası oluşturmaz; mevcut belleğin üzerine yeni bir pencere açar.
- **Kısıtlama:** `ref struct` olduğu için Stack üzerinde kalmak zorundadır! Sınıf alanı (class field) olamaz, boxing yapılamaz, `async / await` sınırları üzerinden geçirilemez.

```csharp
string log = "2026-09-16 ERROR TimeoutOccurred";

// Sıfır allocation ile ayrıştırma:
ReadOnlySpan<char> span = log.AsSpan();
ReadOnlySpan<char> date = span.Slice(0, 10);
ReadOnlySpan<char> level = span.Slice(11, 5);
```

### 📌 Memory<T> ve ReadOnlyMemory<T>
- `ref struct` değildir; Heap üzerinde yaşayabilir.
- `async` metotlara parametre olarak geçirilebilir ve await sınırları boyunca taşınabilir.
- Senkron işleme yapılacağı an `.Span` özelliği üzerinden hızlı bir `Span<T>` görünümü alınır.

### 📌 ArrayPool<T>
Sürekli geçici diziler oluşturup GC'yi yormak yerine dizileri bir havuzdan kiralayıp geri verme mekanizmasıdır.

```csharp
var pool = ArrayPool<byte>.Shared;
byte[] buffer = pool.Rent(1024); // En az 1024 byte'lık dizi kirala
try
{
    int bytesRead = stream.Read(buffer, 0, buffer.Length);
    // YALNIZCA okunan bölümü işle:
    Process(buffer.AsSpan(0, bytesRead));
}
finally
{
    pool.Return(buffer, clearArray: false); // Kiralanan diziyi mutlaka iade et!
}
```

### ⚡ ArrayPool Kullanımında Hayati Kurallar
1. **Boyut Garantisi:** `Rent(n)` metodu tam `n` boyutunda dizi vermez; genellikle `n`'den büyük veya eşit iki katı boyutunda bir dizi döner. Bu nedenle dizinin `Length`'ine değil, işlenen geçerli bayt sayısına güvenilmelidir (`buffer.AsSpan(0, bytesRead)`).
2. **Veri Temizliği:** Havuzdan gelen dizi sıfırlanmış olmayabilir, içinde önceki çağrıların kirli verisi bulunabilir.
3. **Kullanım Sonrası İade:** Kiralanan dizi kesinlikle `try-finally` içinde iade edilmeli; iade edildikten sonra o dizi referansına **asla tekrar erişilmemelidir**.
4. **Hassas Veriler:** Şifre veya token gibi veriler işleniyorsa iade ederken `pool.Return(buffer, clearArray: true)` parametresi verilmelidir.

> [!WARNING]
> Bu optimizasyon araçlarını sıradan CRUD işlemlerine rastgele uygulamayın. Kod karmaşıklığını artırmadan önce profiler ile sıcak kod yolunda (hot path) bir allocation darboğazı olduğunu kanıtlayın.

## 17. Thread, ThreadPool ve ThreadPool Starvation

### 📌 Temel Tanım
- **Thread (İş Parçacığı):** İşletim sisteminin bir işlemci çekirdeğinde kod yürütmek için zaman dilimi tahsis ettiği en küçük birimdir. Kendi stack alanı (1 MB) ve işletim sistemi kayıtları vardır; oluşturulması ve yok edilmesi pahalıdır.
- **ThreadPool:** CLR tarafından yönetilen, önceden oluşturulmuş ve hazırda bekleyen iş parçacığı havuzudur. Yeni thread açma maliyetini ortadan kaldırır.
- **ThreadPool Starvation (Havuz Açlığı):** Havuzdaki tüm thread'lerin senkron bekleme veya bloklayıcı işlemler yüzünden kilitlenmesi ve yeni gelen işlerin kuyrukta beklemesi sonucu tüm uygulamanın donmasıdır.

### ⚡ Kritik Kurallar
- ASP.NET Core gelen her HTTP isteğini ThreadPool'dan bir thread'e teslim eder.
- `await` anahtar kelimesi kullanıldığında, I/O işlemi sürerken thread bloklanmaz; **havuza iade edilir** ve başka bir isteğe hizmet verir.
- Asenkron bir kodun üzerinde `.Result`, `.Wait()` veya `.GetAwaiter().GetResult()` çağırmak o thread'i kilitler (**Sync-over-Async felaketi**).
- HTTP istekleri içinde `new Thread(...)` açılmamalıdır.
- Asenkron akışta `Thread.Sleep()` kesinlikle kullanılmamalı, yerine `Task.Delay()` tercih edilmelidir.

```text
ThreadPool Starvation Mekanizması:
İstek 1 ──> ThreadPool Thread #1 ──> Task.Result ile kilitlendi (Bloke!)
İstek 2 ──> ThreadPool Thread #2 ──> Task.Result ile kilitlendi (Bloke!)
İstek 3 ──> ThreadPool Thread #3 ──> Task.Result ile kilitlendi (Bloke!)
...
Yeni Gelen İstekler ──> ThreadPool Kuyruğunda Çaresizce Bekler! (Latency Tavan Yapar!)
```

### 🧠 Senior Seviyesinde Dikkat Edilmesi Gerekenler
- Starvation sorununu çözmek için `ThreadPool.SetMinThreads()` değerini ezbere artırmak asıl sorunu maskeler; kök nedendeki bloklayıcı senkron çağrıları temizleyin.
- Uzun süren arka plan işlerini doğrudan istek thread'inde değil; `BackgroundService`, `Channel<T>` veya bağımsız bir kuyruk mekanizması ile yürütün.

## 18. Task, TaskScheduler ve ExecutionContext

### 📌 Temel Tanım
- **Task:** Gelecekte bir zaman diliminde tamamlanacak bir işlemin durumunu, sonucunu veya hatasını temsil eden bir **promise** nesnesidir. Task doğrudan bir işletim sistemi thread'i demek değildir.
- **TaskScheduler:** Bir Task'ın nerede ve hangi iş parçacığı üzerinde çalıştırılacağını organize eden bileşendir (Varsayılan olarak ThreadPool'u kullanır).
- **ExecutionContext:** Güvenlik kimliği (ClaimsPrincipal), kültür bilgisi, telemetri verileri ve özellikle **`AsyncLocal<T>`** gibi bağlamsal değişkenleri asenkron sıçramalar boyunca bir thread'den diğerine taşıyan mantıksal zarftır.

### ⚡ Kritik Kurallar
- `async` metotlar çağrıldıkları anda **hemen senkron olarak çalışmaya başlarlar**; ne zaman ki henüz tamamlanmamış bir `await` ifadesine rastlarlar, kontrol çağıran koda o anda döner.
- `ExecutionContext`, `await` edilen noktalarda otomatik olarak diğer thread'e akar (**Context Flow**). Bu sayede `HttpContextAccessor` veya `AsyncLocal<T>` değerleri kaybolmaz.
- `Task.Run`, senkron bir I/O operasyonunu gerçek anlamda asenkron yapmaz; sadece ThreadPool'dan başka bir thread kiralayarak işi oraya atar (I/O thread tüketmeye devam eder).

### ⚠️ Sık Yapılan Hatalar
- Gerçekten asenkron olan API'leri gereksiz yere `Task.Run(() => ...)` ile sarmak.
- Fire-and-forget (başlat ve unut) şeklinde `_ = Task.Run(...)` çalıştırıp içindeki hataların `UnobservedTaskException` olarak yutulmasına izin vermek.
- `AsyncLocal<T>` içine çok büyük nesneler koyup bellek sızıntısına davetiye çıkarmak.
- HTTP Request scope'una bağlı bir servisi (`DbContext` vb.), request sonlandıktan sonra çalışan arka plan bir Task içine geçirmek (`ObjectDisposedException` kaçınılmazdır).

## 19. Async/Await ve Async State Machine

### 📌 Temel Tanım & Çalışma Mantığı
C# derleyicisi bir metotta `async` anahtar kelimesini gördüğünde, o metodu arka planda `IAsyncStateMachine` arayüzünü uygulayan bir **durum makinesi (State Machine) struct'ına** dönüştürür.

```text
async Metot Yazımı:
public async Task<string> FetchDataAsync()
{
    Log("Başladı");
    var data = await _httpClient.GetStringAsync(url);
    Log("Bitti");
    return data;
}

Derleyicinin Ürettiği Durum Makinesi:
State 0: Log("Başladı") çağrılır. GetStringAsync tetiklenir.
         İşlem henüz bitmediyse Awaiter register edilir ve metottan çıkılır (Thread boşa çıkar).
State 1: HTTP cevabı geldiğinde continuation tetiklenir.
         Log("Bitti") çağrılır ve Task tamamlanır.
```

### ⚡ Kritik Kurallar
- **`await` işlemi hızlandırmaz!** İşlemin süresi yine aynıdır; fark, bekleme süresi boyunca işletim sistemi thread'inin kilitlenmeyip boşa çıkmasıdır.
- **Async All The Way:** Asenkron mimari en alttaki I/O çağrısından (DB / HTTP) en üstteki Controller metoduna kadar kesintisiz devam etmelidir.
- **`async void` Yalnızca Event Handler İçindir!** UI buton tıklamaları haricinde hiçbir yerde `async void` kullanılmamalıdır; çünkü çağıran kod bu metodu bekleyemez ve fırlatılan exception'lar uygulamayı anında çökertebilir. Her zaman `async Task` dönülmelidir.
- Eğer bir Task zaten hafızada tamamlanmışsa (örn: `Task.FromResult` veya cache), state machine devreye girmeden kod tamamen senkron olarak akar.

### ⚠️ Sık Yapılan Hatalar
- Asenkron metodun sonuna `.Result` veya `.Wait()` eklemek.
- Dönen `Task` nesnesini `await` etmeyi unutup işin sonucunu veya hatasını kaybetmek.
- Hataların (Exceptions) metot çağrıldığı anda değil, ancak **`await` edildiği anda ortaya çıktığını** unutmak.

## 21. Task Composition, WhenAll ve WhenAny

### 📌 Temel Tanım
- **Task Composition:** Birden fazla bağımsız asenkron görevi paralel başlatıp sonuçlarını tek bir akışta koordine etmektir.
- **`Task.WhenAll`:** Parametre olarak verilen tüm görevlerin tamamlanmasını bekler.
- **`Task.WhenAny`:** Verilen görevlerden herhangi birisi ilk tamamlandığı anda çözülür.

```csharp
// DOĞRU PARALEL ÇALIŞTIRMA MODELİ:
Task<User> userTask = _userService.GetUserAsync(userId);
Task<List<Order>> ordersTask = _orderService.GetOrdersAsync(userId);

// Her iki I/O işlemi aynı anda ağda koşturulur:
await Task.WhenAll(userTask, ordersTask);

User user = await userTask;
List<Order> orders = await ordersTask;
```

### ⚠️ Kritik Hatalar
- **Sıralı Await Hatası:**
  ```csharp
  // KÖTÜ: Paralel değil, sıralı çalışır! Biri bitmeden diğeri başlamaz.
  var user = await _userService.GetUserAsync(userId);
  var orders = await _orderService.GetOrdersAsync(userId);
  ```
- **EF Core `DbContext` Eşzamanlılık Felaketi:**
  > [!CAUTION]
  > Entity Framework Core `DbContext` nesnesi **thread-safe DEĞİLDİR**. Aynı DbContext örneği üzerinden `Task.WhenAll` ile iki farklı sorgu paralel **ÇALIŞTIRILAMAZ!** Bu durum `InvalidOperationException: A second operation was started on this context instance before a previous operation completed` hatasıyla patlar.
- **Sınırsız Paralellik:** Yüzlerce URL'i veya sorguyu sınır koymadan `Task.WhenAll` ile çalıştırmak downstream servisleri çökertebilir. Eşzamanlılığı `SemaphoreSlim` ile sınırlandırın.

## 22. CancellationToken, Timeout ve Asenkron Exception Yönetimi

### 📌 CancellationToken Nedir?
Asenkron işlemlerde iptal mekanizması **kooperatif (işbirliğine dayalı)** bir yapıdır. Bir thread'i işletim sistemi düzeyinde zorla öldürmez (`Thread.Abort` gibi tehlikeli değildir). Bunun yerine işi yürüten koda *"İstemci bağlantıyı kapattı, artık çalışmana gerek yok"* mesajını iletir.

### ⚡ Kritik Kurallar
- Controller katmanından gelen `CancellationToken`'ı en alt katmandaki Database (`SaveChangesAsync`) ve HTTP (`SendAsync`) çağrılarına kadar zincirleme **iletin**.
- ASP.NET Core API'lerinde istemci isteği iptal ettiğinde bunu yakalamak için `HttpContext.RequestAborted` token'ı kullanılır.
- Bir işlem iptal edildiğinde `OperationCanceledException` fırlatılır; bu beklenen bir durumdur, log sisteminizde "Kritik Sistem Hatası (Error/Fatal)" olarak loglanmamalıdır.
- **Timeout ve İptal Birleştirme:**
  ```csharp
  using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
  using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(timeoutCts.Token, userToken);

  await _httpClient.GetAsync(url, linkedCts.Token);
  ```
- Modern .NET sürümlerinde herhangi bir task üzerinde doğrudan `.WaitAsync(TimeSpan, CancellationToken)` kullanılabilir.

## 23. SynchronizationContext, ConfigureAwait ve Async Deadlock

### 📌 SynchronizationContext Nedir?
Bir asenkron işlem `await` edildikten sonra, devam kodunun (**continuation**) hangi özel iş parçacığı veya bağlam üzerinde çalışacağını koordine eden yapıdır.
- **WPF / Windows Forms:** Devam kodunun mutlaka UI Thread üzerinde çalışması gerekir (Aksi halde cross-thread UI exception oluşur).
- **Eski ASP.NET (Full Framework):** Her isteğe özel bir `AspNetSynchronizationContext` mevcuttu.
- **Modern ASP.NET Core:**
  > [!IMPORTANT]
  > **ASP.NET Core'da varsayılan olarak SynchronizationContext YOKTUR!**

### 🔒 Async Deadlock ve `ConfigureAwait(false)`
Eski context'e sahip sistemlerde (WPF veya eski ASP.NET), asenkron bir metodun üzerinde `.Result` veya `.Wait()` çağrıldığında:
1. Senkron bekleyen ana thread context'i kilitler.
2. `await` bitince continuation aynı context'e dönmek ister.
3. İkisi birbirini bekler ve sistem **Deadlock (Ölümcül Kilitlenme)** olur.

- **`ConfigureAwait(false)`:** "İşim bittiğinde başladığım özel context'e dönmek zorunda değilim; ThreadPool'daki herhangi bir thread üzerinden devam edebilirim" anlamına gelir.
- **ASP.NET Core'da Durum:** ASP.NET Core'da SynchronizationContext olmadığı için klasik context deadlock'u oluşmaz. Ancak `.Result` veya `.Wait()` çağrısı yine de **ThreadPool Starvation** tehlikesi doğurur!
- **Genel Kural:** Yeniden kullanılabilir bir sınıf kütüphanesi (**NuGet / Class Library**) geliştiriyorsanız kütüphane kodlarında `ConfigureAwait(false)` kullanın. Normal ASP.NET Core API iş kodlarında ise her await'in sonuna yazmak zorunlu değildir.

## 24. ValueTask, IAsyncEnumerable ve Asenkron Akışlar

### 📌 ValueTask ve ValueTask<T>
- `Task<T>` bir sınıftır (`reference type`); her çağrıldığında heap üzerinde tahsisat (allocation) yapar.
- `ValueTask<T>` ise bir **`struct`** yapısıdır.
- **Kullanım Amacı:** Eğer bir metot yüksek ihtimalle **senkron** olarak sonuçlanıyorsa (örneğin sonuç in-memory cache'ten dönüyorsa), boş yere bir `Task` nesnesi tahsis etmemek için tasarlanmıştır.

```csharp
public ValueTask<string> GetDataAsync(string key)
{
    // 1. Senkron Tamamlanma -> Sıfır Heap Allocation!
    if (_cache.TryGetValue(key, out var val))
        return new ValueTask<string>(val);

    // 2. Asenkron Yol -> Task oluşturulur
    return new ValueTask<string>(FetchFromDbAsync(key));
}
```

### ⚡ ValueTask Hayati Tüketim Kuralları
> [!CAUTION]
> 1. Bir `ValueTask` **yalnızca BİR KEZ await edilebilir!** Birden fazla kez await etmek tanımsız davranışa yol açar.
> 2. Bir `ValueTask` üzerinde `.Result` veya `.GetAwaiter().GetResult()` kesinlikle çağrılmamalıdır.
> 3. `Task.WhenAll` veya `Task.WhenAny` içine doğrudan `ValueTask` verilemez; gerekirse `.AsTask()` yapılmalıdır.
> 4. Varsayılan tercihiniz her zaman **`Task<T>`** olmalıdır; ancak BenchmarkDotNet ile sıcak kod yolunda allocation problemi tespit edilirse `ValueTask<T>`'a geçilmelidir.

### 🌊 IAsyncEnumerable<T> ve Asenkron Streaming
Büyük bir veri kümesini belleğe tek seferde devasa bir `List<T>` olarak yüklemek yerine, veriler hazır oldukça parça parça tüketiciye aktarmayı sağlar.

```csharp
// Veritabanından satır satır akış üretme:
public async IAsyncEnumerable<Product> GetProductsStreamAsync([EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (var product in _dbContext.Products.AsAsyncEnumerable().WithCancellation(ct))
    {
        yield return product; // Veri geldikçe anında istemciye fırlatılır
    }
}

// Tüketim:
await foreach (var item in GetProductsStreamAsync())
{
    Console.WriteLine(item.Name);
}
```

## 25. Race Condition, Synchronization, Parallelism ve Producer–Consumer Modelleri

### 📌 Temel Kavramlar

```text
┌─────────────────────────┬────────────────────────────────────────────────────────┐
│ KAVRAM                  │ TANIM                                                  │
├─────────────────────────┼────────────────────────────────────────────────────────┤
│ **Race Condition**      │ Birden fazla thread'in paylaşılan bir veriye aynı anda │
│                         │ müdahale etmesiyle sonucun sıraya bağlı bozulması.     │
│ **Synchronization**     │ Paylaşılan kritik kaynağa erişimi kilitlerle düzene    │
│                         │ sokarak veri bütünlüğünü garanti altına alma.          │
│ **Parallelism**         │ Çok çekirdekli CPU üzerinde birden fazla hesaplamanın  │
│                         │ tam anlamıyla aynı anda fiziksel olarak yürütülmesi.   │
│ **Producer–Consumer**   │ İşleri üretenler (producers) ile işleri tüketenleri    │
│                         │ bir arabellek (kuyruk) ile birbirinden ayrıştırma.     │
└─────────────────────────┴────────────────────────────────────────────────────────┘
```

### ⚡ Eşzamanlılık ve Senkronizasyon Kuralları

1. **`lock` Bloğu İçinde `await` KULLANILAMAZ!**
   C#'ta `lock (obj)` anahtar kelimesi işletim sistemi monitörünü kullanır ve aynı thread'e bağlıdır. `await` sonrası iş başka bir thread'de devam edebileceği için `lock` içinde `await` derleme hatası verir. Asenkron koordinasyon için **`SemaphoreSlim`** kullanılmalıdır:
   ```csharp
   private static readonly SemaphoreSlim _semaphore = new SemaphoreSlim(1, 1);

   await _semaphore.WaitAsync();
   try
   {
       await PerformAsyncWork();
   }
   finally
   {
       _semaphore.Release(); // Kilidi mutlaka serbest bırak!
   }
   ```

2. **Basit Sayaçlar İçin `Interlocked`:**
   Basit artırma/azaltma işlemlerinde ağır kilitler yerine CPU seviyesinde atomik işlem yapan `Interlocked` sınıfı tercih edilmelidir:
   ```csharp
   Interlocked.Increment(ref _counter);
   ```

3. **Thread-Safe Koleksiyonların Sınırları:**
   `ConcurrentDictionary` kullanmak, içindeki birden fazla operasyonun atomik olmasını kendiliğinden sağlamaz:
   ```csharp
   // RACE CONDITION RİSKİ VAR:
   if (!dict.ContainsKey(key)) { dict[key] = value; }

   // DOĞRU VE ATOMİK KULLANIM:
   dict.GetOrAdd(key, k => value);
   ```

### 📦 Modern Producer–Consumer Mimarisi: `System.Threading.Channels`
Bellek içi asenkron mesajlaşma ve iş kuyrukları için en modern, performanslı ve bellek dostu yöntem **`Channel<T>`** yapısıdır.

```csharp
// 1. Bounded (Kapasitesi Sınırlı) Kanal Oluşturma -> Backpressure Sağlar!
var channel = Channel.CreateBounded<JobItem>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait // Kuyruk dolarsa üretici bekletilir
});

// 2. Üretici (Producer)
await channel.Writer.WriteAsync(new JobItem { Id = 1 });

// 3. Tüketici (Consumer) - BackgroundService içinde
await foreach (var job in channel.Reader.ReadAllAsync())
{
    await ProcessJobAsync(job);
}
```

### 🧠 Senior Seviye Eşzamanlılık Felsefesi
Çok iş parçacıklı bir sistem tasarlarken şu öncelik sırasını gözetin:
1. **Paylaşılan Durumu Kaldır (Eliminate Shared Mutable State):** Paylaşılan değişken yoksa kilit ihtiyacı da yoktur.
2. **Değişmez (Immutable) Tipler Kullan:** Yalnızca okunan veri doğal olarak thread-safe'tir.
3. **Kilitleri Asgari Düzeyde Tut:** Kilit mekanizmalarını dar bir kapsamda tutun, kilit içinde asla disk veya network I/O yapmayın.
4. **Dağıtık Düşün:** Ölçeklenen çoklu sunucularda uygulama içi yerel kilitler (`lock`, `SemaphoreSlim`) yetersiz kalır; veritabanı düzeyinde **Optimistic Concurrency** (`RowVersion`), **Idempotency** ve dağıtık kuyruklar (`RabbitMQ`, `Redis Distributed Lock`) kullanın.
